#### [Q1] 长上下文优化的核心瓶颈是什么？

截至 2026 年 7 月，长上下文优化已经形成一条清晰的技术链：

$$
\text{输入长度压缩}
\rightarrow
\text{Prefill 注意力加速}
\rightarrow
\text{KV cache 体积压缩}
\rightarrow
\text{KV 选择、淘汰与复用}
\rightarrow
\text{分页、迁移和分布式调度}
$$

**Prefill 的瓶颈**：长序列注意力计算，复杂度近似 $O(T^2)$，随序列长度平方增长。

**Decode 的瓶颈**：每生成一个 token 都要读取历史 KV，受 KV cache 容量和 HBM 访存带宽限制。KV cache 大小约为：

$$
M_{\text{KV}} \approx 2 \cdot L \cdot T \cdot H_{KV} \cdot d_h \cdot b
$$

其中 $L$ 是层数，$T$ 是上下文长度，$H_{KV}$ 是 KV head 数，$d_h$ 是 head dimension，$b$ 是每个元素的字节数。

> [!note] 核心认知
> 对长上下文推理而言，真正有效的方案通常不是单点优化，而是同时降低：**"缓存多少"**（token 数量）、**"读取多少"**（稀疏读取）、**"以什么精度存"**（量化位宽）、**"缓存在哪"**（GPU/CPU/SSD 分层）。

#### [Q2] 经典长上下文架构路线有哪些？

| 技术 | 核心思想 | 代表工作 | 现在的定位 |
| --- | --- | --- | --- |
| **分段循环记忆** | 将上一段 hidden states 作为下一段记忆，突破固定上下文窗口 | Transformer-XL（~6k 引用） | 长上下文"缓存记忆"思想的起点，不是当前主流 LLM serving KV 管理方案 |
| **压缩记忆** | 将更久远的历史状态压缩成低分辨率 memory，而不是直接丢弃 | Compressive Transformer（~1k 引用） | "远端记忆压缩"经典原型，对后续层级缓存、memory token 很有启发 |
| **稀疏注意力** | 用局部窗口、全局 token、随机连接等替代完整 attention | Longformer（~7k）、BigBird（~4k） | 长序列 encoder、文档理解的重要基础；对 decoder-only LLM 直接 retrofit 较有限 |
| **IO-aware attention** | 利用 tile 和 SRAM 复用，不改变注意力语义，减少 HBM 访问 | FlashAttention | **当前 attention kernel 的基础设施**。使长序列 attention 真正端到端加速 |

技术演进脉络：从"减少全注意力复杂度" → 转向"保留全注意力语义但管理 KV cache 生命周期"。

---

**Transformer-XL 具体做法**

标准 Transformer 将序列分成等长 segment，每段之内做 full attention，段间完全隔断，上下文长度被 segment 长度锁死。Transformer-XL 的核心改动有两处：

**1. Segment-level recurrence（分段循环）**：在处理第 $n$ 个 segment 时，将第 $n-1$ 个 segment 的所有层 hidden state **缓存**（stop-gradient，不反传），拼接到当前 segment 的 K、V 里：

$$
\tilde{h}_{n}^{l-1} = \text{concat}[\text{stop\_grad}(h_{n-1}^{l-1}),\ h_n^{l-1}]
$$

这样当前 segment 的每个 token 在做 attention 时，既能看到自己 segment 内的 token，也能看到上一 segment 的 cached hidden states，有效感受野随层数指数增长。

**2. Relative positional encoding（相对位置编码）**：绝对位置编码在跨 segment 复用时会产生位置冲突（上一 segment 的 token 和当前 segment 的 token 可能有相同的绝对位置编号）。Transformer-XL 改用相对位置 $r = i - j$（query 位置与 key 位置之差）来编码，在 attention score 计算时直接用相对距离而非绝对坐标。

---

**Compressive Transformer 具体做法**

在 Transformer-XL 的基础上引入**两级记忆**：

- **Regular memory**（类似 Transformer-XL 的 cache）：存储最近 $n_m$ 个 token 的 hidden states，滑动窗口式更新。
- **Compressed memory**：当 regular memory 被"挤出"（oldest entries 被淘汰）时，不直接丢弃，而是通过**压缩函数** $f_\theta$ 把 $c$ 个连续 hidden states 压缩成 1 个 compressed memory vector：
  $$
  c_t = f_\theta(h_{t-c+1}, \ldots, h_t)
  $$
  $f_\theta$ 可以是 1D 卷积、MLP 或 mean-pooling。

训练时使用**辅助重建损失（auto-encoding loss）**：要求模型能从 compressed memory 重建原始的 regular memory，以防止压缩函数退化。

推理时 attention 同时访问当前 input、regular memory 和 compressed memory，近端高分辨率、远端低分辨率。

---

**Longformer 具体做法**

将标准 $O(n^2)$ attention 替换为三种稀疏注意力模式的组合：

**1. 局部窗口 attention（Sliding window attention）**：每个 token 只与前后 $w/2$ 个 token 做 attention，复杂度 $O(n \cdot w)$。还可以使用**dilated sliding window**（跳步窗口），每隔 $d$ 步取一个，在相同计算量下扩大感受野，类似空洞卷积。

**2. 全局 attention（Global attention）**：针对任务中需要感知全局信息的特殊 token（如 `[CLS]`、问答任务中的问题 token），手动标记为"全局 token"。全局 token 与序列中**所有** token 双向 attention（既能看到所有人，所有人也能看到它），代价仍是 $O(n \cdot k)$，$k$ 是全局 token 数量。

**3. 随机 attention（Random attention）**：每个 token 随机选 $r$ 个非相邻 token 做 attention，理论上帮助信息跨越长距离传播（BigBird 也有类似设计）。

实现上 Longformer 用了自定义 CUDA kernel，三种 pattern 拼合成一个高效的分块矩阵运算。

---

**BigBird 具体做法**

也是三种 pattern 的组合，但**理论动机更完整**：

- **Random**：每个 token 随机 attend $r$ 个 token
- **Local window**：每个 token attend 自身附近 $w$ 个邻居
- **Global**：$g$ 个全局 token（可以是原始 token，也可以是额外插入的可学习 token）

BigBird 从图论和通用近似角度证明了：只要 $r, w, g$ 取合理值，稀疏 attention 是**完整 softmax attention 的通用近似**，且是 Turing-complete 的。

---

**FlashAttention 具体做法**

> [!important] 核心洞察
> 标准 attention 的瓶颈不是 FLOPs，而是 **HBM 带宽**：完整 $N \times N$ attention 矩阵需要写到 HBM 再读回，反复的 HBM 访问才是真正的慢点。

标准 attention 的内存访问路径：

$$
Q, K \in \text{HBM} \xrightarrow{\text{load}} S = QK^\top \in \text{HBM} \xrightarrow{\text{load}} P = \text{softmax}(S) \in \text{HBM} \xrightarrow{\text{load}} O = PV \in \text{HBM}
$$

需要 $O(N^2)$ 的 HBM 读写。

FlashAttention 的做法：将 $Q, K, V$ 按**块（tile）**分割，每次把一个小块 load 进 SRAM（GPU 片上内存），在 SRAM 内完成 attention 的一部分，再把**增量结果**写回 HBM，始终不需要把完整的 $N \times N$ 矩阵写入 HBM。

关键技术是**在线 softmax（online softmax trick）**：

$$
m_i^{\text{new}} = \max(m_i^{\text{old}},\ \text{rowmax}(S_{\text{new block}}))
$$
$$
l_i^{\text{new}} = e^{m_i^{\text{old}} - m_i^{\text{new}}} l_i^{\text{old}} + \text{rowsum}(e^{S_{\text{new block}} - m_i^{\text{new}}})
$$
$$
O_i^{\text{new}} = \frac{l_i^{\text{old}} \cdot e^{m_i^{\text{old}} - m_i^{\text{new}}} O_i^{\text{old}} + e^{S_{\text{new block}} - m_i^{\text{new}}} V_{\text{block}}}{l_i^{\text{new}}}
$$

逐块累积，最终结果与标准 attention 完全等价。内存复杂度从 $O(N^2)$ 降到 $O(N)$，HBM 访问量大幅减少。

**FlashAttention-2** 进一步减少非矩阵乘法 FLOPs，改进 warp-level 并行。**FlashAttention-3** 利用 H100 的异步 Tensor Core（wgmma 指令）和 TMA 数据搬运，进一步隐藏 SRAM load 延迟。

==面试有问FA 真正加速的底层视角的原因：减少 HBM 数据搬运==

#### [Q3] 如何从模型结构上减少 KV cache 体积？

这是最根本的一类方法，从源头减少每个 token、每层需要存储的 KV 状态。

| 技术 | 核心机制 | 代表工作 | 优缺点 |
| --- | --- | --- | --- |
| **MQA** | 所有 query head 共享单一 KV head | Shazeer 2019 | KV 缩减倍数 = H；质量有时损失较大 |
| **GQA** | G 组 query head 各自共享一组 KV head | GQA（~2k 引用） | MHA 和 MQA 的折中；可从 MHA checkpoint 转换；Llama 2/3、Mistral 均采用 |
| **MLA** | K、V 联合压缩为低维 latent，缓存 latent | DeepSeek-V2 | 可将 KV cache 缩减 **93.3%**；需从预训练采用，不能直接套既有模型 |
| **YOCO** | 前半部分生成全局 KV，后半部分跨层复用 | YOCO | "只缓存一次"，架构干净；属于新模型结构，不是部署插件 |

---

**MQA / GQA 具体做法**

标准 MHA 中，$H$ 个 attention head 各自有独立的 $W_K, W_V$ 投影，KV cache 大小正比于 $H$。

- **MQA（Multi-Query Attention，Shazeer 2019）**：将 $H$ 个 KV head 合并为**1 个**，所有 query head 共享同一组 K、V。KV cache 从 $2 \cdot H \cdot d_h$ 降到 $2 \cdot d_h$，缩减 $H$ 倍。训练时所有 query head 对同一个 K/V 矩阵做 attention，quality 通常略有下降。

- **GQA（Grouped Query Attention，Ainslie et al 2023）**：引入 $G$ 组（$1 \le G \le H$），每组包含 $H/G$ 个 query head，共享 1 组 KV head。$G=1$ 退化为 MQA，$G=H$ 退化为 MHA。KV cache 缩减 $H/G$ 倍。

  **从 MHA checkpoint 转换**：将相邻的 $H/G$ 个 K/V 投影权重做 mean-pooling，得到 $G$ 组代表权重，再做少量 fine-tuning（"uptrained"）。实验显示 GQA 用约 5% 的预训练步数 fine-tune 就能恢复 MHA 的绝大多数性能。

---

**MLA（Multi-head Latent Attention）具体做法**

DeepSeek-V2 提出，核心思想是**低秩联合压缩 KV**。

标准 GQA 缓存的是 K、V 矩阵本身（size：$H_{KV} \cdot d_h$ per token）。MLA 改为：

**1. 联合 KV 压缩**：用一个低秩投影 $W^{DKV}$ 将 hidden state $h$ 压缩成低维 latent：
$$
c_t^{KV} = W^{DKV} h_t \in \mathbb{R}^{d_c}, \quad d_c \ll H_{KV} \cdot d_h
$$

缓存时只存 $c_t^{KV}$（而非完整的 K、V）。推理时实时解压：
$$
k_t = W^{UK} c_t^{KV}, \quad v_t = W^{UV} c_t^{KV}
$$

**2. 解耦 RoPE（Decoupled RoPE）**：RoPE 需要对 K 做旋转，但旋转操作不能压缩进 latent（因为 RoPE 依赖绝对位置，无法合并进线性投影）。MLA 为此单独保留一个小的 rope-specific key $k_t^R$（用 $W^{KR}$ 投影 + RoPE），缓存时存 $(c_t^{KV}, k_t^R)$。

**实际压缩量**：DeepSeek-V2 中 $d_c = 512$，而标准 MHA 的 KV 大小约为 $2 \times 128 \times 128 = 32768$ bits（以 FP16），MLA 约为 $512 \times 2 = 1024$ bits，压缩约 **93.3%**，同时因解码时更少的 HBM 访问而提升生成吞吐。

---

**YOCO（You Only Cache Once）具体做法**

将 decoder-only 的 $L$ 层 Transformer 分为两段：

- **前 $L/2$ 层（Self-decoder）**：使用高效 attention（如局部窗口 attention 或线性 attention），生成一组**全局 KV cache** $K^{global}, V^{global}$（对整个输入序列）。
- **后 $L/2$ 层（Cross-decoder）**：不做 self-attention，改做 **cross-attention**，直接 attend 到前半部分生成的全局 KV cache。这部分不需要缓存自己的 KV。

标准 decoder 的 KV cache：$O(L \cdot T)$（每层都要缓存）。YOCO 的 KV cache：$O(L/2 \cdot T)$（只缓存前半段的全局 KV 一次，后半段复用）。理论上将 KV 显存需求减半，且 prefill 时后半段的 cross-attention 可以并行化。

#### [Q4] KV token 选择、淘汰与流式缓存策略有哪些？

这类方法沿 **sequence dimension** 压缩。核心洞察：不是所有历史 token 对未来 decode 都同等重要。

| 方法 | 核心思想 | 代表工作 | 适用场景 |
| --- | --- | --- | --- |
| **Scissorhands** | 重要 token 的重要性具有持续性 | Scissorhands（~500 引用） | 在线固定预算缓存，无需微调；可与低比特量化叠加 |
| **H2O** | 保留近期 token 和历史高贡献 token | H2O（~1.3k 引用） | 最经典的 KV eviction 基线，适合长生成、长对话、固定 cache budget |
| **StreamingLLM** | 保留最开始的少量 sink token + 最近窗口 | StreamingLLM（~2k 引用） | 流式无限上下文；早期 token 承担 attention sink 的归一化作用 |
| **SnapKV** | 用 prompt 尾部投票选重要 KV 位置 | SnapKV（~750 引用） | 超长输入 + 较短输出（RAG、文档问答、长代码理解） |
| **Quest** | 以 KV page 的 min-max key 范围估算 page 重要性 | Quest（~400 引用） | Decode 时稀疏读取，缓存保留，不永久删除 |
| **InfLLM** | 本地窗口 + 外部可检索 memory unit | InfLLM（~180 引用） | 超出训练窗口的流式长上下文外推 |

**关键区别总结：**

| 类型 | 代表方法 | 处理方式 |
| --- | --- | --- |
| 永久删除 / 固定预算 | H2O、Scissorhands、StreamingLLM | 丢弃低重要性 token |
| 一次性 prompt 选择 | SnapKV | decode 前压缩 prompt KV |
| 动态稀疏读取 | Quest | 缓存保留，按需稀疏读取 |
| 可检索外部记忆 | InfLLM | 远端信息转为可检索 memory |

> [!warning] 长推理任务的注意点
> 对推理质量要求高的长推理任务，不建议只用基于早期 attention 的**永久淘汰**。推理过程中的 query 分布会变化，早期不重要的 token 后续可能重新变关键。**Quest** 这类 query-aware read 更适合作为 H2O/SnapKV 的补充。

---

**Scissorhands 具体做法**

**关键假设（Persistence of Importance）**：在最近若干步生成中获得高 attention 权重的 token，在后续生成步骤中仍会持续被高度关注；反之，一直被低关注的 token 在未来也大概率不重要。

**做法**：
1. 维护一个大小为 $B$（budget）的 KV cache。
2. 用一个滑动的"历史窗口"（recent $w$ steps 的 attention 分数）统计每个 cached token 的**累积 attention 接收量**。
3. 当序列增长、需要淘汰 token 时，删除累积 attention 最低的 token。

与 H2O 的区别：Scissorhands 用的是**近期历史窗口**的 attention，而非全程累积，避免早期偶发高 attention 导致的过度保留。论文还展示可以对 heavy hitters 保留 FP16、轻量 token 降到 INT4，与量化叠加。

---

**H2O（Heavy Hitter Oracle）具体做法**

**形式化**：把 KV cache 淘汰建模为**贪心子模优化**问题。定义每个 token $t$ 的重要性分数为其在所有解码步骤中接收到的 **attention weight 的累积和**：

$$
s_t = \sum_{\tau > t} \alpha_{t}^{(\tau)}
$$

其中 $\alpha_t^{(\tau)}$ 是在第 $\tau$ 步生成时 token $t$ 收到的 attention 权重（对所有 head 平均或取最大）。

**淘汰策略**：维护预算 $B$，其中 $H$ 个 slot 给"Heavy Hitters"（累积 attention 最高的 token），$R$ 个 slot 给最近 token（保证序列局部性）。每当新 token 到来时：
1. 更新所有 cached token 的累积 attention 分数。
2. 若 cache 超出预算，驱逐累积分数最低的非近期 token。

论文证明这种贪心策略对次模集合函数是 $(1 - 1/e)$-近似最优，有理论保证。

---

**StreamingLLM 具体做法**

**核心发现**：将 KV cache 设为仅保留最近 $W$ 个 token 的滑动窗口时，性能崩溃——但崩溃的根因**不是最初的 token 语义重要**，而是因为 softmax attention 需要所有位置的 attention 权重之和为 1。

当某个 query 没有特别关注的 key 时（即 attention 分布趋于均匀），softmax 的归一化特性会把多余的 attention 权重"溢出"给最初几个 token——它们成为**"attention sink"**，承担归一化的数值作用，而非语义作用。删掉这些 sink token 后，归一化无处可溢，softmax 分布变得不稳定，性能崩溃。

**解决方案**：始终保留最开始的 **4 个 token**（attention sink）+ 最近 $W$ 个 token（滑动窗口），总 cache 大小固定为 $4 + W$。这样可以无限流式扩展上下文，不需要存所有历史 KV，也没有性能崩溃。

**进一步改进**：在预训练时插入一个**可学习的 sink token**（learnable token，前置于所有输入），专门承担 sink 功能，在线推理时只需保留这 1 个 sink，窗口利用率更高。

---

**SnapKV 具体做法**

针对"超长 prompt + 短输出"的典型场景（RAG、文档问答）。

**关键观察**：prompt 的最后若干 token（如最后 16–64 个，称为"observation window"）与解码阶段的 query 分布最接近——因为这部分通常是问题本身或指令，与解码时的信息需求高度相关。

**流程**：
1. **投票（Voting）**：在 prefill 结束时，对 observation window 内的每个 query token，计算它对所有历史 key 的 attention 权重。把 observation window 内所有 query token 的 attention 权重**按位置求和**，得到每个历史 key 位置的"重要性投票分数"。每个 head 独立计算。
2. **选择（Selection）**：每个 head 选出 top-$k$ 重要位置的 KV，丢弃其余位置。$k$ 是每个 head 的 KV budget。
3. **聚类（Clustering）**：在选出的 $k$ 个位置上，对相邻位置做 pooling，平滑选择噪声，同时保留 observation window 全部 KV（不压缩）。
4. **Decode**：只用压缩后的 KV cache 做自回归生成，无需访问丢弃的历史 KV。

---

**Quest 具体做法**

不永久删除任何 KV，而是 decode 时**按需稀疏读取**，每一步只 load 最相关的 KV page。

**核心机制**：
1. **分页**：KV cache 按页组织，每页 $P$ 个 token（如 $P = 16$）。
2. **预计算 page descriptor**：对每页所有 key 向量，按 channel 维度计算 **min 和 max**，得到一个"key 空间的 bounding box"。
3. **稀疏 page 选取**：在第 $\tau$ 步 decode 时，对于当前 query $q$，估算每个 page 能产生的 attention score **上界**：

$$
\text{upper\_bound}(\text{page } p, q) = \sum_{d} \max(q_d \cdot \max_d^p,\ q_d \cdot \min_d^p)
$$

对每个 query token 维度分别取 $q_d > 0$ 时乘 $\max_d^p$、$q_d < 0$ 时乘 $\min_d^p$，得到 dot product 的上界。

4. **Top-k page 选取**：选上界最高的 $k$ 个 page，仅 load 这些 page 的 KV 做精确 attention。其余 page 不读取。

这样每一步只读 $k/(\text{total pages})$ 比例的 KV，大幅降低 HBM 带宽占用，而且是 per-query 动态决定，不同于 H2O 的全局静态淘汰。

---

**InfLLM 具体做法**

将 KV cache 分为两级：

- **本地上下文（Local context）**：最近 $W$ 个 token 的 KV，常驻 GPU，保证最近信息的精确访问。
- **外部 memory units**：将远端历史 token 按块（block size $B$）组织成 memory unit，存储在 CPU 内存中，每个 unit 有一个代表向量（如 block 内 token hidden states 的均值）用于检索。

**解码时的检索流程**：
1. 用当前 hidden state $h_t$ 作为 query，与所有 memory unit 的代表向量计算 cosine 相似度。
2. 选 top-$m$ 个最相关的 memory unit，从 CPU 搬到 GPU。
3. 当前 token 的 attention 计算：attend 到 local context KV + 检索到的 $m$ 个 memory units 的 KV。

这使得模型能处理超出原始训练窗口的长文本（如 500K token），而不需要整个上下文常驻 GPU。

#### [Q5] KV cache 如何做低比特量化与表示压缩？

这类方法不减少 token 数，而是减少每个 K/V 元素的存储位宽，通常最容易与现有 serving 框架结合。

| 技术 | 核心机制 | 代表工作 | 特点 |
| --- | --- | --- | --- |
| **KIVI** | Key 按 channel 量化，Value 按 token 量化 | KIVI（ICML 2024，~575 引用） | 最常见的低比特 KV 量化基线；针对 K/V 不同分布结构设计 |
| **KVQuant** | Pre-RoPE 量化 + 异常值分离 + 非均匀码本 | KVQuant（NeurIPS 2024，~580 引用） | 面向 3-bit 甚至更低，展示百万 token 级上下文的潜力 |
| **QJL** | JL transform 后做 sign-bit 量化 | QJL | 零 scale/zero-point 存储开销；适合极低比特 |
| **TurboQuant** | 随机旋转 + 在线近优码本量化 | TurboQuant（ICLR 2026） | 已进入 vLLM 量化体系；较新 |
| **工程化低精度 KV** | Runtime 直接使用 FP8 / INT8 / NVFP4 | vLLM、TensorRT-LLM、SGLang | **当前最实用的生产路线** |

> [!tip] 实践建议
> **FP8 KV cache** 是当前最稳妥的工程起点。INT4、INT2、3-bit 压缩率更高，但必须关注量化误差、scale 存储开销、dequant kernel 效率，以及 attention score 对异常值的敏感性。

---

**KIVI 具体做法**

**关键观察**：
- **Key 矩阵**：不同 channel（feature dimension）之间方差差异极大（某些 channel 长期值大，某些长期值小）。因此对 key 做 **per-channel** 量化效果好：同一 channel 所有 token 共享一个 scale。
- **Value 矩阵**：channel 间方差相对均匀，但 token 内（同一 token 不同 channel 之间）存在异常值。因此对 value 做 **per-token** 量化：同一 token 所有 channel 共享一个 scale。

**2-bit 量化流程**：
- Key：按 channel 分组（group size 32），每组用 2-bit 整数量化 + 1 个 FP16 scale。
- Value：按 token 量化，每 token 1 个 FP16 scale。
- 保留最近 $r$ 个 token 的 KV 为 FP16 **残差缓存**（residual cache），避免最新 token 量化误差影响生成。

实验显示 KIVI-2bit 在多数任务上达到 FP16 的 ~99% 性能，且内存减少约 4 倍。

---

**KVQuant 具体做法**

比 KIVI 更激进，针对 3-bit 及以下。四个关键技术：

1. **Pre-RoPE quantization**：RoPE 旋转变换会把不同 channel 的值混合，生成后 channel 间分布更不规则，异常值更多。在 **RoPE 之前**对 K 量化，此时 channel 分布更规整，量化更容易。

2. **Per-channel smoothing**：类似 SmoothQuant，把 K 矩阵的 channel-wise 大值通过乘以缩放因子"平滑"到合理范围，让各 channel 幅值更均衡，减少 outlier 对低比特量化的影响。

3. **非均匀量化（Non-uniform quantization）**：使用类 NF4 的**学习分位数**作为量化码本（codebook），而非均匀分布的整数格点。对于服从高斯分布或 Laplace 分布的 KV，这种非均匀码本能用相同位宽表达更多信息。

4. **异常值分离（Outlier isolation）**：识别少数极端大值 channel，对这些 channel 单独用 FP16 存储，其余 channel 量化到低比特，保留表示能力的同时降低平均位宽。

实验显示可在 1M token 级别的长上下文中保持质量，支持 3-bit 甚至 2.x-bit 的 KV 存储。

---

**QJL（Quantized Johnson-Lindenstrauss）具体做法**

极低比特（1-bit sign quantization）下，传统量化必须存 scale 和 zero-point，当位宽极低时这些元数据反而占据大比例存储空间。QJL 绕过这个问题：

1. **JL 变换**：对 K、Q 先乘一个随机矩阵 $F \in \mathbb{R}^{m \times d}$（Johnson-Lindenstrauss 变换），将它们投影到 $m$ 维空间（$m < d$ 或 $m \approx d$）。
2. **Sign 量化**：对变换后的 key $Fk$ 取符号位：$\hat{k} = \text{sign}(Fk) \in \{-1, +1\}^m$，每维 1-bit，**不需要存储 scale 或 zero-point**。
3. **近似内积**：
   $$
   \text{score}(q, k) \approx \frac{1}{m} (Fq) \cdot \text{sign}(Fk)
   $$
   JL 引理保证：若 $m$ 足够大，内积的期望与方差都可控，即 $\mathbb{E}[(Fq) \cdot (Fk)] = q \cdot k$，估算无偏。

优点：1-bit 存储 + 零元数据开销；缺点：需要额外 FLOPs 做 JL 变换，$m$ 需足够大才能保证精度。

#### [Q6] 如何加速长 Prompt 的 Prefill？

KV cache 优化主要改善 Decode，但长文档、RAG、代码库、多轮 agent 常常首先卡在 **Prefill**。

| 技术 | 核心思想 | 代表工作 | 适用场景 |
| --- | --- | --- | --- |
| **IO-aware exact attention** | Tile + SRAM 复用，语义完全等价 | FlashAttention（见 Q2） | 通用基础设施，几乎所有长上下文模型都应使用 |
| **Dynamic sparse prefill** | 离线分析每个 head 的注意力模式，推理时动态选 pattern | MInference（~360 引用） | 不改预训练，动态稀疏 attention；报告 A100 上百万 token prefill 最高 **10 倍加速** |
| **输入 token 压缩** | 进入主模型前用小 LM 删除冗余 token | LLMLingua（~700 引用）、LongLLMLingua（~560 引用） | 黑盒 API、RAG、ICL、文档问答；同时降低 Prefill、KV cache 和调用成本 |

> [!info] MInference 与 Quest 的区别
> - **MInference** 主要加速 **Prefill**：对长 prompt 内的 $QK^\top$ 做稀疏计算
> - **Quest** 主要加速 **Decode**：对每步 query 相对历史 KV 做稀疏读取
>
> 两者目标不同，可以叠加使用。

---

**MInference 具体做法**

**离线 profiling 阶段**：在代表性长上下文数据上运行模型，记录每个 layer、每个 head 的 attention map。经验发现几乎所有 head 的 attention pattern 可归为三类：

- **A-shape（Vertical-Diagonal）**：既有稀疏的"竖条"（attend 特定 column，即特定 token 被所有 query 关注），又有"对角线"（attend 局部邻近 token）。这类 head 类似 StreamingLLM 的 attention sink + 局部窗口。
- **Vertical-Slash**：竖条（特定重要位置）+ 斜向条纹（与 query 位置有固定偏移的 key 位置）。
- **Block-Sparse**：attention 集中在若干大块（连续 token block）上。

对每种模式，设计对应的**稀疏 attention kernel**（例如 A-shape 只 compute sink columns + diagonal strip，Block-Sparse 只 compute 选出的 block）。

**推理阶段**：对于每个 head，用简单的"前几层 attention 的统计特征"快速判断当前 head 属于哪种 pattern，调用对应的稀疏 kernel，跳过不重要的位置。整个过程不改变权重，即插即用。

**结果**：在 A100 上对 1M token 的 prefill，最高报告 10× 加速；与 FlashAttention 配合使用。

---

**LLMLingua / LongLLMLingua 具体做法**

**LLMLingua（粗→细两阶段压缩）**：

1. **粗粒度过滤（句子级）**：用一个小型 LM（如 GPT-2）计算每个句子的**困惑度（perplexity）**，困惑度低的句子（模型认为"显而易见"、可预测的内容）优先删除。

2. **细粒度压缩（token 级）**：对保留句子，用同一小 LM 计算每个 token 的条件概率 $p(t | \text{context})$，删除概率最高（最易预测、最冗余）的 token，保留概率低（信息量高）的 token。全局 budget controller 控制总压缩率（如压到原始长度的 30%）。

**LongLLMLingua（Question-aware 改进）**：

1. **问题感知打分**：在小 LM 计算 token 重要性时，把**问题（question）** 加入 context，使得与问题相关的 token 获得更低的条件概率（因为问题的存在提供了更多 context，让相关 token 更易预测，paradoxically 留下了更多与问题无关的冗余）。
   
   实际操作：score($t$ | 问题 + 上文) 低 → 此 token 在有问题 context 下是"信息量"高 → 保留。

2. **文档重排序（Document reordering）**：将检索到的最相关文档块放在 prompt **末尾**（靠近问题），利用 LLM 的"近因偏差（recency bias）"提升 RAG 性能，同时配合 token 压缩。

3. **动态压缩率**：根据各文档块与问题的相关度，相关块压缩率低（保留更多），不相关块压缩率高（大力删减），非均匀压缩。

---

#### [Q7] KV cache 如何分页、复用、迁移和系统调度？

这部分的系统级优化常常比算法侧的小幅压缩带来更大的线上吞吐收益。

| 技术 | 核心机制 | 代表工作 | 价值 |
| --- | --- | --- | --- |
| **PagedAttention** | KV 按固定 block 分页管理 | vLLM（~7.4k 引用） | **KV cache 系统管理的事实标准** |
| **Prefix caching** | 共享相同 prefix 的 KV block 直接复用 | vLLM APC、SGLang | 对 system prompt、共享文档、对话历史非常有效 |
| **RadixAttention** | radix tree 组织公共前缀和分支 KV | SGLang | 更适合结构化生成、多分支采样、agent workflow |
| **CacheBlend** | RAG 中非前缀文档 chunk 的 KV 复用 | CacheBlend（EuroSys 2025 Best Paper） | 解决 RAG 场景 prefix caching 命中率低的问题 |
| **CacheGen** | 将 KV 编码成压缩 bitstream 跨网络传输 | CacheGen（SIGCOMM 2024） | 跨节点 KV 复用；报告 KV 大小进一步压缩约3.5–4.3 倍 |
| **Prefill-Decode 解耦** | Prefill 和 Decode 分配不同 GPU 集群 | DistServe（~880 引用） | 分别为 TTFT 和 TPOT 分配资源，互不干扰 |
| **KV-centric 分层 pool** | GPU / CPU / SSD / RDMA 构成分层 KV pool | Mooncake（~220 引用） | Kimi 生产服务代表架构，KV 成为集群级可调度资源 |
| **跨引擎 KV layer** | KV 可持久化、可共享、可迁移 | LMCache | 支持 PD 解耦 + 多级存储 offload |

> [!example] 技术依赖关系（系统栈）
> - **底层内存管理**：PagedAttention
> - **复用层**：Prefix caching / RadixAttention / CacheBlend
> - **压缩传输层**：CacheGen
> - **集群调度层**：DistServe / Mooncake / LMCache

---

**PagedAttention 具体做法**

**传统 serving 的问题**：每个请求在进来时预分配最大序列长度的连续 KV cache 内存（如 2048 tokens）。实际生成可能只用 300 tokens，剩余 1748 tokens 的内存白白浪费（内部碎片）。多个请求同时进来时，内存碎片进一步加剧（外部碎片），GPU 内存利用率只有 20–40%。

**PagedAttention 的设计**：
1. **物理 block 池**：将 KV cache 内存划分成固定大小的物理 block（如每块 16 个 token 的 KV），统一管理在一个 block 池中。
2. **Block table**：每个请求维护一个 block table，将请求的逻辑 token 位置映射到物理 block 号，类似操作系统的页表。
3. **按需分配**：生成过程中，只在需要新 block 时才从 block 池申请，不再预分配。请求结束后立即归还 block。
4. **Copy-on-write（写时复制）**：Beam search 的多条 beam 在分叉前共享相同的物理 block（引用计数 > 1），在需要写入不同内容时才 copy 一个新 block，实现跨 beam 的 KV 共享。
5. **并行采样共享**：同一 prompt 生成多个 sample 时，prompt 部分的 KV block 只存储一份，多个 output 共享，大幅节省内存。

**结果**：KV cache 利用率接近 100%，使同批次可调度的请求数大幅增加，整体吞吐量（tokens/s）显著提升。

---

**Prefix caching（APC）具体做法**

在 PagedAttention 基础上，对每个 KV block 计算**内容哈希**（该 block 包含的 token ids 的 hash）。

当新请求到来时：
1. 对请求 prompt 从头开始，逐 block 计算 hash，查询全局 block cache。
2. **命中**的 block 直接复用（引用计数 +1），跳过这段 prefill 计算。
3. **未命中**的 block 正常计算，计算完成后加入 block cache。

当 block cache 满时，用 LRU 策略驱逐最旧、最少使用的 block。

**典型高命中场景**：
- System prompt：所有用户共享同一 system prompt → 命中率接近 100%
- 多轮对话：历史对话每轮都包含前几轮内容 → 随对话轮数命中率线性增加
- RAG：相同文档被多个 query 检索 → 文档部分 KV 可复用

---

**RadixAttention 具体做法**

SGLang 将 prefix caching 升级为 **radix tree（基数树/前缀树）** 结构：

- Tree 的每条边标注一段 token sequence。
- 每个节点存储对应前缀的物理 KV block 指针。
- 根到叶的路径代表完整的请求 token 序列。

**操作**：
- **插入**：新请求完成后，沿 radix tree 插入其 token sequence，共享已有节点，分叉时创建新节点。
- **查找**：新请求进来时，在 tree 中找最长匹配前缀，复用对应 KV blocks，从分叉点开始计算新 token。
- **驱逐**：LRU 结合引用计数，驱逐叶子节点（无子请求引用的 block）。

RadixAttention 相比 hash-based prefix caching 的优势：支持**任意树状复用**（如 agent 生成多个候选分支，各分支 KV 可通过树结构有效共享），而非只匹配线性的公共前缀。

---

**CacheBlend 具体做法**

**问题**：RAG 的多个检索文档不一定共享同一前缀位置（文档顺序可能不同），传统 prefix caching 命中率很低。

**CacheBlend 的思路**：对每个文档 chunk 独立预计算 KV（以 position 0 开始），存为独立的 KV 缓存片。在组装请求时：

1. **复用预缓存 KV**：直接使用各 chunk 预缓存的 KV，无需重新 prefill（~95% 的 KV 可复用）。
2. **选择性重算（Selective Recompute）**：由于 KV 是以 position 0 计算的，实际拼接后位置编码和跨 chunk 的 attention 依赖都不对。CacheBlend 识别**跨 chunk 依赖最强**的少数 token（通过计算 chunk 间 attention score 的大小确定），只对这些 token 重算 KV（用正确的 position 和跨 chunk context），其余 token 直接使用预缓存。
3. 重算比例约 5%，但能大幅修正 position 和 cross-chunk attention 的误差，恢复绝大部分质量。

---

**CacheGen 具体做法**

把 KV cache 的**跨节点传输**问题类比于视频流传输：

**关键观察**：KV tensor 具有类似视频的时空局部性：
- **层间相似（temporal locality）**：相邻层的 KV 高度相似（Transformer 层间 residual 连接使 hidden state 变化缓慢）。
- **位置间相似（spatial locality）**：相邻 token 的 KV 向量也相对平滑。

**编码方案**：
1. **层间 delta 编码**：计算当前层 KV 与前一层 KV 的差值，只存/传差值（类似视频 P 帧）。
2. **熵编码（Entropy coding）**：对 delta 值用算术编码或 ANS 压缩，进一步减小 bitstream 大小。
3. **流式传输**：编码后的 bitstream 边传边解码，decode worker 可以在 prefill 未完成时就开始解码前几层的 KV，隐藏传输延迟。

报告：在相同传输带宽下，CacheGen 的 KV 大小比原始 FP16 KV 小约 **3.5–4.3×**。

---

**DistServe 具体做法**

**核心发现**：Prefill 和 Decode 对硬件的需求截然不同：
- **Prefill**：处理整段输入的 $QK^\top V$ 计算，是 compute-bound（算力瓶颈），需要高 FLOPs 的 GPU。
- **Decode**：每步只生成 1 个 token，从 HBM 读取全部 KV 和权重，是 memory-bandwidth-bound（带宽瓶颈），需要高内存带宽的 GPU。

把两阶段放在同一 GPU 上会互相干扰：大 batch prefill 会显著拉长 decode 的 TPOT（因为共享计算资源）。

**DistServe 方案**：
1. **分离部署**：Prefill GPU pool 专门处理 prefill（compute-heavy，追求吞吐，优化 TTFT）；Decode GPU pool 专门处理 decode（bandwidth-sensitive，追求低延迟，优化 TPOT）。
2. **KV 传输**：Prefill 完成后，通过 RDMA/NVLink 将 KV cache 传输到 Decode worker。
3. **SLA-aware 调度**：Scheduler 同时考虑 TTFT SLA 和 TPOT SLA，将请求路由到满足 SLA 的 prefill/decode worker；prefill worker 过载时不堆积请求，而是早期拒绝或排队。

---

**Mooncake 具体做法**

Kimi 生产系统中实际部署的架构，将 KV cache 从"请求级临时状态"提升为"集群级可调度资源"：

1. **Conductor 组件**：中心化的 KV cache 调度控制平面，管理整个集群的 KV pool（跨 GPU HBM、CPU DRAM、SSD、远端存储）。
2. **前缀感知路由（Prefix-aware routing）**：调度器记录每个 Prefill worker 当前持有哪些 prefix 的 KV，将新请求优先路由到已有匹配 prefix KV 的 worker，最大化 cache 命中率，最小化重复 prefill。
3. **早期拒绝（Early rejection）**：在 prefill 开始前评估系统负载，若超过阈值直接拒绝请求（返回 429），而非接受后超时，保证已接受请求的 SLA。
4. **分层 KV 迁移**：KV 在 GPU HBM（热）→ CPU DRAM（温）→ SSD（冷）之间自动迁移；RDMA 用于跨节点 KV 传输，带宽瓶颈比 inference compute 更早到来，Mooncake 把 KV 传输路径与 compute 路径解耦。

---

#### [Q8] 超长上下文的多 GPU 并行策略有哪些？

当单卡显存和带宽都不够时，问题转化为如何分布 attention 与 KV。

| 技术 | 核心思想 | 代表工作 | 适用场景 |
| --- | --- | --- | --- |
| **Ring Attention** | sequence block 分布在多设备，环形传递 KV block，通信与计算重叠 | Ring Attention（~500 引用） | 百万 token 级训练和推理 |
| **Sequence Parallelism（Ulysses）** | 按 sequence dimension 切分，all-to-all 完成 attention 头维重排 | DeepSpeed-Ulysses（~260 引用） | 超长序列训练，intra-node NVLink 高带宽场景 |
| **Prefill-Decode 解耦并行** | Prefill 和 Decode 用不同资源池，KV 经网络转移 | DistServe、Mooncake | 线上服务场景，而非单请求纯模型加速 |

> [!note] 并行策略的选择逻辑
> - 单请求序列过长、跨节点 → **Ring Attention**
> - 单节点 intra-machine、head 数多 → **Ulysses（Sequence Parallelism）**
> - 高并发线上 serving → **PD disaggregation**
> - Ring vs Ulysses：Ring 每步通信量 $O(T/N \cdot d)$（point-to-point），Ulysses 每步 all-to-all 通信量 $O(T \cdot d / N)$（更适合 NVLink 高带宽）；Ulysses 要求 $H \geq N$（head 数 ≥ 设备数）。

---

**Ring Attention 具体做法**

将长度为 $T$ 的序列切成 $N$ 块（每块 $T/N$ 个 token），分配给 $N$ 个设备，设备 $i$ 负责 chunk $i$ 的 Q、K、V。

**Ring 通信模式**：在每一轮 step $s$：
1. 设备 $i$ 将自己当前持有的 $(K_s, V_s)$ 发给设备 $(i+1) \mod N$。
2. 同时接收来自设备 $(i-1) \mod N$ 的 $(K_{s-1}, V_{s-1})$。
3. 用**在线 softmax（online attention）** 累积：当前 chunk $i$ 的 query $Q_i$ 对刚收到的 $(K_{s-1}, V_{s-1})$ 计算 partial attention，用 running max / running sum 更新累积结果。

经过 $N$ 轮后，每个设备积累了完整的 attention 结果（$Q_i$ 与所有 $K, V$ 的 attention）。通信与计算完全 pipeline 重叠。

**关键**：使用 FlashAttention 的 online softmax 机制，无需事先知道全局 softmax 分母即可增量累积，这使得 Ring Attention 能在不同 step 逐块接收 K/V 并正确累积。

---

**DeepSpeed-Ulysses（Sequence Parallelism）具体做法**

与 Ring Attention 不同，Ulysses 把 attention head 和 sequence 的切分分开处理：

**初始状态**：设备 $i$ 持有 token chunk $[T/N \cdot i, T/N \cdot (i+1))$ 的 全部 $H$ 个 head 的 Q、K、V。

**Attention 前 all-to-all**：将 $(T/N \text{ tokens}, H \text{ heads})$ → $(T \text{ tokens}, H/N \text{ heads})$ 的重排：每个设备得到全序列 $T$ 个 token 的 $H/N$ 个 head 的 Q、K、V。

**各设备独立做完整 attention**：设备 $i$ 对自己分到的 $H/N$ 个 head，在完整序列 $T$ 上做 full attention（可用 FlashAttention），每个 head 都能看到所有 token。

**Attention 后 all-to-all**：将 $(T \text{ tokens}, H/N \text{ heads})$ → $(T/N \text{ tokens}, H \text{ heads})$ 的重排，恢复每设备处理自己的 sequence chunk。

**优势**：all-to-all 比 Ring 的 send/recv 在 NVLink（intra-node）下效率更高；单设备上的 attention 是完整 full attention，不需要 online softmax 的分块累积。**限制**：要求 $H \geq N$，通常适合同一节点 8 卡并行（H100 NVLink）。

#### [Q9] 当前最值得采用的长上下文优化组合是什么？

**对于已有 Transformer 模型的长上下文部署，比较现实的基础组合是：**

$$
\text{FlashAttention / FlashInfer}
+
\text{PagedAttention}
+
\text{FP8 KV cache}
+
\text{prefix caching}
+
\text{H2O 或 SnapKV 或 Quest}
$$

**按场景细分：**

| 场景 | 推荐组合 |
| --- | --- |
| 长对话、流式输入 | StreamingLLM + H2O |
| RAG、文档问答、长代码库 | LongLLMLingua 或 MInference + SnapKV + prefix caching / CacheBlend |
| 超长生成或推理链 | Quest（query-aware sparse read，比静态淘汰更稳定） |
| 新模型预训练 | GQA（稳妥工业基线）或 MLA（更激进的长期方向） |
| 多节点 serving | PagedAttention + PD disaggregation + Mooncake / LMCache / CacheGen |
| 工程落地起点 | FP8 KV cache，之后再尝试 INT4、INT2、TurboQuant 等极低比特方案 |

**核心研究空白与方向：**

最有价值的方向不是再提出一个静态 token importance score，而是**联合优化**：

$$
\text{token 保留}
+
\text{位宽分配}
+
\text{KV page 读取}
+
\text{GPU/CPU/SSD 放置}
+
\text{跨请求复用}
$$

> [!warning] 静态方案的局限
> 长推理、agent、RAG、医疗时间序列等 query 会不断变化的任务中，KV 的"未来价值"是动态的。静态淘汰、固定量化位宽和固定缓存位置都容易失效，因为：
> - 早期不重要的 token 后续可能变关键
> - 不同推理步骤对 KV 的访问模式差异显著
> - 长推理链的 query 分布会持续漂移

> [!summary] 一句话总结
> **用结构压缩（GQA/MLA）减少 KV 总量，用量化（FP8/INT4）减少存储位宽，用选择/淘汰（H2O/SnapKV/Quest）减少读取量，用分页和复用（PagedAttention/prefix caching）提高系统效率，用 PD 解耦和分层存储（Mooncake/LMCache）完成集群级调度——五个维度缺一不可。**

---

**推荐核心文献清单（按技术链顺序）：**

*长上下文与记忆基础：* Transformer-XL → Compressive Transformer → Longformer / BigBird → FlashAttention

*KV cache 结构与压缩：* GQA → DeepSeek-V2（MLA）→ H2O → Scissorhands → StreamingLLM → SnapKV → Quest → KIVI → KVQuant

*长上下文 Prefill 与 serving：* MInference → PagedAttention / vLLM → RadixAttention / SGLang → DistServe → CacheGen → Mooncake → CacheBlend
