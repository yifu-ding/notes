### 全参数微调资源需求

#### [Q1] 如果想要在某个模型基础上做全参数微调，究竟需要多少显存？

一般经验法则：$n$ B 参数的模型，全参数微调最低需要 **16-20×n GB** 显存（CPU offload 基本不开的情况下）。

**经验来源**

以 Vicuna-7B 为例，官方训练样例配置为 **4×A100 40G**，实测确实能占满显存（global batch size 128，max length 2048）。该配置同时使用了 **FSDP、梯度累积、梯度检查点（gradient checkpointing）** 等方式降低显存占用，否则实际需求会更高。

**16-20n GB 大致来自哪里**

全参数微调时显存主要由以下几部分构成（以 $n$ B 参数、混合精度 + Adam 优化器为例）：

| 组成部分 | 每参数字节数（近似） | 说明 |
| --- | --- | --- |
| 模型权重（fp16/bf16） | 2 bytes | 前向/反向使用的低精度权重 |
| 梯度（fp16/bf16） | 2 bytes | 与权重精度一致 |
| Adam 一阶矩 $m$（fp32） | 4 bytes | 优化器状态 |
| Adam 二阶矩 $v$（fp32） | 4 bytes | 优化器状态 |
| 权重主副本（fp32，混合精度训练常见） | 4 bytes | 用于精确更新 |

$$
\text{显存（不含激活）} \approx n\times(2+2+4+4+4)\ \text{GB} = 16n\ \text{GB}
$$

再加上激活值（activations）、临时 buffer 及框架开销，经验上会达到 **16-20n GB**，与实测的 4×A100 40G（共 160GB）训练 7B 模型基本占满显存的现象一致。

**降显存的常见手段**

- **FSDP / ZeRO**：将权重、梯度、优化器状态切分到多卡，单卡只保存一部分（详见 [[12 并行与分布式#[Q7] 什么是 ZeRO？|ZeRO]] 与 [[12 并行与分布式#[Q8] 什么是 FSDP？与 ZeRO 是什么关系？|FSDP]]）；
- **梯度累积（Gradient Accumulation）**：用多个小 micro-batch 模拟大 batch，不增加峰值显存；
- **梯度检查点（Gradient Checkpointing）**：以重新计算换显存，反向传播时重新前向计算被丢弃的中间激活；
- **CPU Offload**：把优化器状态或权重移到 CPU 内存，可进一步降低显存，但会显著拖慢训练速度（题注中"基本不开"即指此项）。

> [!note] 16-20n GB 是经验范围，而非精确公式
> 实际显存需求还受 batch size、序列长度、是否开启梯度检查点、并行策略（FSDP/ZeRO stage）、框架实现等因素影响。该经验法则适用于"不开 CPU offload"的常见配置，仅用于快速估算训练预算（例如需要几张、多大显存的 GPU）。

> [!example] 激活值显存大概什么量级？
> 经验数据点：以 **hidden size = 1024、共 32 层** 的模型为例，一条长度 **4096 token** 的序列，其激活值大致占用 **~1GB** 显存（不含权重/梯度/优化器状态，且与是否开启梯度检查点、精度等实现细节有关）。这部分开销随序列长度、层数、hidden size、batch size 近似线性增长。==多卡训练把权重/梯度/优化器状态切分出去后腾出的显存，最直接的用法就是增大 batch size==（或序列长度），而不是让它闲置。

> [!tip] Batch Size 增大后，学习率和 Warmup 要怎么跟着调？
> - **学习率：平方根缩放（sqrt scaling rule）**——经验法则是 batch size 扩大 $N$ 倍时，学习率扩大 $\sqrt N$ 倍（也有场景用线性缩放 Linear Scaling Rule，按 $N$ 倍放大，常见于超大规模预训练；微调场景下 $\sqrt N$ 更保守、更常用，避免大 batch 下训练不稳定）：
>
> $$
> \eta_{\text{new}} = \eta_{\text{base}} \cdot \sqrt{N}, \quad N = \frac{\text{batch\_size}_{\text{new}}}{\text{batch\_size}_{\text{base}}}
> $$
>
> - **Warmup 步数**：经验上取总训练步数的 **~1%** 作为 warmup 步数，让学习率从很小值线性增长到目标学习率，避免训练初期大 batch、大学习率组合下梯度方向不稳定导致的发散。
>
> 这两条都是经验法则，不是严格理论，实际效果仍需结合验证集表现微调。

##### [Q1.1] 梯度累积、梯度检查点、CPU Offload 分别是什么？

这三种是单卡/少卡场景下最常用的降显存手段，原理都比较直接：

- **梯度累积（Gradient Accumulation）**：不直接用大 batch 训练，而是连续跑多个 micro-batch 的前向 + 反向，梯度在显存中累加，累积到设定步数后才执行一次 `optimizer.step()` 并清空梯度。本质是用"多次小 batch 的梯度求和"模拟一次大 batch 的梯度，不增加单步的峰值激活显存，但会增加总的前向/反向次数（训练时间变长）。
- **梯度检查点（Gradient Checkpointing / Activation Checkpointing）**：前向传播时不保存全部中间激活值，只保留少数"检查点"；反向传播需要用到某段被丢弃的激活时，重新对该段做一次前向重算。本质是** 用计算时间换显存**：激活显存大幅降低，但反向时多了一次局部前向计算，训练速度变慢。
- **CPU Offload**：把暂时不参与计算的参数、梯度或优化器状态从 GPU 显存搬到 CPU 内存（甚至 NVMe），用到时再传回 GPU。可以进一步压低显存占用，但受 PCIe 带宽限制，频繁的 GPU-CPU 数据搬运会明显拖慢训练速度，因此通常只在显存极度紧张、且能接受速度损失时才开启——这也是 Q1 题注中"CPU offload 基本不开"的原因。

##### [Q1.2] 混合精度训练里的 Loss Scaling 是什么？为什么会影响训练稳定性？

**动机**：在 FP16/FP8 混合精度训练中，很小的梯度值在低精度格式下容易** 下溢（underflow）成 0**——FP16/FP8 能表示的最小正规数远大于 FP32，一旦梯度值落在表示范围之外，就会被直接舍入为 0。**Loss Scaling** 的做法是反传前先把 loss 乘一个较大的缩放系数 $s$，让梯度整体被放大、留在低精度可表示的范围内，进入优化器前再除回来：

$$
g_{\text{scaled}} = s \cdot g, \qquad g_{\text{optimizer}} = \frac{g_{\text{scaled}}}{s}
$$

> [!warning] $s$ 设太小会发生什么？
> 如果缩放系数 $s$ 偏小，本来就很小的梯度（尤其是**靠近输入端的浅层**，梯度经过多层反传后通常更小）在 FP16/FP8 表示、跨卡通信规约或精度转换时仍可能下溢：
>
> $$
> g \approx 10^{-8} \xrightarrow{\text{FP16}} 0
> $$
>
> 梯度一旦被舍成 0，对应参数这一步就不会更新：
>
> $$
> \theta_{t+1} = \theta_t - \eta \cdot 0 = \theta_t
> $$
>
> **"浅层梯度长时间不更新"** 指的是：浅层梯度本来就偏小，更容易连续多个 step 都被舍成 0，导致这些层的参数相对其他层"滞后"，模型内部不同层的学习进度不同步。
>
> **与 Loss Spike 的关系**：链条大致是 长期小梯度下溢 → 部分层长期滞后 → 训练状态失衡 → 某次梯度恢复或数据分布变化触发较大更新 → loss 突然升高。==这不是说"$s$ 太小一定导致 loss spike"==，而是说它会** 增加训练不稳定的风险**，尤其在深网络、长训练、学习率较激进、FP8 路径较多的场景下更明显。

> [!note] 一个容易忽略的细节
> 如果梯度从头到尾都用 BF16/FP32 累积，只在部分 GEMM 的输入/输出处临时转换为 FP8，那么 $s$ 设小未必会直接导致进入优化器前的梯度下溢。真正要看的是：梯度在哪一步被 cast 到 FP16/FP8、是否做了低精度的 All-Reduce、以及优化器状态（Adam 的 $m,v$）是否始终保持 FP32——这些细节决定了 loss scaling 设置不当的实际影响有多大。

### SFT 数据构建与领域适配

#### [Q2] SFT 指令微调数据如何构建？

构建 SFT 指令微调数据时，核心原则是**覆盖面要广，但单任务数据量要克制**：

1. **代表性**：应选择多个有代表性的任务，覆盖目标场景下的主要指令类型，而不是只堆砌某一类任务；
2. **数据量**：每个任务的实例数量不应太多（经验上数百个量级即可），否则容易导致模型在该任务上** 过拟合**，反而影响通用指令遵循能力；
3. **不同任务的数据量占比**：应平衡各任务之间的比例，并限制整个数据集的总容量（通常几千到几万条），避免某个数据量特别大的任务压倒整体分布，导致模型在其他任务上表现退化。

> [!note] 为什么单任务数据量要"克制"而不是越多越好？
> SFT 阶段的目标是**激发** 预训练阶段已经具备的能力，让模型学会"以指令-回答的格式响应"，而不是重新教会模型新知识。单个任务给的样本过多，容易让模型记住该任务的具体模式（过拟合），挤占其他任务的指令遵循能力，且边际收益迅速下降。

> [!note] 数据量级与 Padding 处理
> Fine-tuning（尤其全参数 SFT）的训练数据规模通常是**几百到几万条**（与上面"单任务数百、总量几千到几万条"的量级一致）；训练时同一个 batch 内的样本长度往往不一致，需要先** 做 Padding 对齐长度**（通常 padding 到 batch 内最长样本或固定的 max_length），并配合 attention mask 屏蔽 padding 位置，避免 padding token 参与 loss 计算和注意力交互，影响训练效果。

#### [Q3] 领域数据训练后，通用能力往往会有所下降，如何缓解模型遗忘通用能力？

**动机**：仅使用领域数据集进行训练，模型很容易出现** 灾难性遗忘**（catastrophic forgetting），即领域能力提升的同时，原有的通用对话、推理等能力明显下降。

**解决方法**：通常在领域训练过程中** 混入通用数据集**一起训练，而不是单独用领域数据训练。

**领域数据与通用数据的比例**：目前没有一个准确的答案，主要与领域数据量有关——当领域数据量没有那么多时，一般 ** 领域数据 : 通用数据 ≈ 1:5 到 1:10** 之间比较合适。

> [!warning] 经验法则，没有严格的理论依据
> 1:5~1:10 是社区实践中常见的取值范围，并没有严格的理论推导支撑，本质上是"灾难性遗忘程度 vs. 领域拟合程度"的权衡，需要结合具体领域数据规模、任务难度和验证集表现做实际调整，不能直接当作通用公式套用。

> [!tip] 直觉理解
> 领域数据占比越高，模型对领域任务的拟合越强，但也越容易在通用任务上漂移；混入足够比例的通用数据，相当于持续给模型“复习”原有分布，是缓解灾难性遗忘的最直接做法。具体比例需要结合领域数据规模和实际验证集表现调整，而不是固定公式。

> [!question] 案例辨析：ChatGLM-6B 微调 CSC 任务后"失眠怎么办"答非所问，这是不是灾难性遗忘？是不是学习率的问题？
> **场景**：ChatGLM-6B 已经走完 预训练 → SFT → RLHF，SFT 阶段见过上千种指令任务；现在只新增一类很窄的任务（如拼写纠错 CSC）做微调，微调数据量不大、任务类型单一。微调后模型在"失眠怎么办"等原本能正确回答的通用问答上开始答非所问。有同学认为：数据量小 + 任务单一 + 模型已有大量 SFT 经验，不应该导致灾难性遗忘，真正原因是** 学习率设置过高**，应调低（如 $\le 2\times10^{-5}$，且不超过预训练学习率）。
>
> **这个判断哪里需要修正**：“数据小、任务单一就不会导致灾难性遗忘”这一推理本身有问题——恰恰相反，** 数据小、任务单一时模型更容易在很少的训练步内把输出分布"拉偏"到新任务的固定格式上**，因为损失函数完全由这一种任务主导，没有其他任务的梯度来"稀释"或"对抗"这个方向。如果学习率偏高、训练轮数偏多，模型会在不大的数据量上被迅速、强烈地拉向"无论输入是什么，都倾向输出纠错式/格式化结果"的状态——这正是 [[08 预训练#[Q19] 为什么 SFT 后模型会更会对话，但有时基础能力反而下降？|《预训练》Q19]] 中列出的典型诱因（"SFT 数据分布过窄"+"学习率过高或训练轮数过多"）共同作用的结果，而不是"数据小所以不会遗忘"。
>
> **更准确的描述**：这种现象更贴切的名字或许是** 任务过拟合 / 输出格式坍缩**，而不是传统意义上"预训练知识被擦除"的灾难性遗忘——"失眠怎么办"背后的医学常识很可能仍然编码在参数里，只是模型的** 输出策略**被新任务的格式/行为模式覆盖了，不再"愿意"以正常问答的方式输出。但在行为表现层面，它和灾难性遗忘是同一类问题（用户可感知的能力下降），用同一套缓解手段（见下方 [[#[Q3.1] 缓解通用能力遗忘，有哪些经典或知名的技术？|Q3.1]]）同样有效。
>
> **学习率确实是最直接的杠杆，但不是唯一手段**：降低学习率（不超过预训练阶段、通常落在全参数 SFT 常见的 $10^{-6}\sim5\times10^{-5}$ 区间，详见 [[08 预训练#[Q13] 微调时如何防止遗忘预训练知识（灾难性遗忘）？|《预训练》Q13]]）和减少训练轮数确实能显著缓解这个现象，这与本题作者的实践经验一致；但更稳妥的做法是** 降学习率 + 减轮数 + 混入少量通用指令数据（Replay）**三者同时使用，单独依赖调小学习率在数据极窄、训练步数仍然较多时未必充分。

##### [Q3.1] 缓解通用能力遗忘，有哪些经典或知名的技术？

除了最朴素的"混入通用数据（Replay/数据重放）"，还有几类有代表性的技术路线：

- **正则化约束类**：
  - **EWC（Elastic Weight Consolidation）**：经典持续学习方法，给每个参数估计一个"重要性权重"（基于 Fisher 信息），微调时对重要参数施加额外的二次惩罚，抑制它们偏离原值，从而保护原有能力。详情参见 [[11 模型适应与上下文学习#[Q16] Continual Learning 有哪些代表性技术和工作？|《模型适应与上下文学习》Q16]]；
  - **L2-SP（L2 to Starting Point）**：更简单的变体，直接对"当前参数 - 原始参数"做 L2 正则，约束整体不要离预训练权重太远；
  - **KL 约束 / 蒸馏正则**：训练时额外加一项损失，让微调后模型在通用数据上的输出分布（logits）保持接近原模型（teacher），即对原模型做知识蒸馏式的约束；RLHF 中对参考模型的 **KL 惩罚** 本质上也是同一类思想，用来防止策略模型离原始分布太远。
- **参数高效微调（PEFT）类**：
  - **LoRA / Adapter**：只训练新增的低秩矩阵或小模块，绝大部分原始权重被冻结，天然限制了对原有知识的覆盖范围，遗忘问题通常比全参数微调更轻；
  - **Block Expansion（如 LLaMA Pro）**：在原模型基础上插入新的可训练层，冻结全部原始层，只用新增层学习领域知识，理论上完全不触碰原有参数，从结构上避免遗忘。
- **权重空间操作类**：
  - **模型权重插值 / Model Soup / WiSE-FT**：把微调后权重和原始权重按一定系数线性插值（$\theta = \alpha\theta_{\text{ft}} + (1-\alpha)\theta_{\text{base}}$），在领域性能和通用性能之间找折中点，不需要额外训练；
  - **Task Arithmetic（任务向量运算）**：把"微调权重 - 原始权重"看作一个"任务向量"，可以通过加减任务向量的方式组合/抵消能力变化，是模型编辑（model editing）方向的代表性思路。详细操作见 [[#[Q3.2] 模型编辑（Task Arithmetic）具体是怎么做的？数据重放有哪些常见规则？|Q3.2]]。

> [!example] LoRA 加在 Attention 和加在 MLP 里，效果上有什么区别？工业界怎么选？
> **效果上的区别**：
> - **Attention 模块（$W_q,W_k,W_v,W_o$）**：低秩增量主要影响** 注意力模式**，即 token 之间"看谁、看多少"的路由方式。调整 Attention 更容易改变模型"关注什么信息""如何在上下文里检索/对齐"，对** 指令遵循、句法结构调整、跨 token 关系**类任务比较敏感。
> - **MLP/FFN 模块（$W_{\text{up}}, W_{\text{down}}$，部分结构还有 $W_{\text{gate}}$）**：FFN 的参数量和"知识容量"占比通常更大（一般是 Attention 部分的 2-4 倍参数量），普遍被认为是存储事实性知识、做特征变换的主要载体。在 MLP 上加 LoRA，对** 知识注入、领域风格/术语适配、内容层面的改变**通常更有效。
>
> **工业界的择优经验与主流实践**：
> - 如果**只能选一处** 且参数预算紧张，更常见的做法是**优先在 MLP/FFN 上加 LoRA**（或 Attention+MLP 都加，但给 MLP 分配更大的 rank），因为单纯调 Attention 的 $q,k,v,o$ 往往学习容量不够，尤其是需要注入新知识/新领域内容时。
> - 如果任务更偏**格式控制、推理链路调整、检索式上下文利用**（偏"程序性"而非"事实性"的能力），只调 Attention 也能有不错效果，且参数量更小。
> - ==当前主流实践（如 PEFT 库默认配置、多数开源微调脚本）已经趋向于同时对 Attention 和 MLP 的线性层都加 LoRA==（`target_modules` 常见配置覆盖 `q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj` 等），这已经是事实上的默认习惯；单独"只调 Attention"或"只调 MLP"更多用于消融实验或极端参数预算下的取舍。

> [!example] Block Expansion（如 LLaMA Pro）具体是怎么做的？
> 以 **LLaMA Pro**（在 LLaMA2-7B 基础上做 Block Expansion）为例，回答几个关键细节：
>
> 1. **插入位置**：新的 Transformer Block 不是只加在模型最后，而是** 按固定间隔插入到原始层序列中间**——把原始的 $N$ 层均分成若干组，每组之后插入 1 个新 Block。
> 2. **插入数量/间隔**：LLaMA2-7B 原本有 32 层；论文按** 每 4 层一组**（间隔 $P=4$）插入新 Block，$32/4=8$ 组，对应新增 **8 个 Block**，扩展后总层数变为 $32+8=40$ 层（对应模型规模从 7B 增至约 8B）。
> 3. **新层的大小**：新增 Block 与原始 Block ** 结构、宽度（hidden size）完全一致**，是标准的完整 Transformer Block，而不是缩小版，因此每个新 Block 带来的参数量与一个原始层相当。
> 4. **初始化方式**：新 Block 先** 复制相邻原始 Block 的权重**作为起点，再把该 Block 内 Attention 的输出投影 $W_o$ 和 MLP 的下投影 $W_{\text{down}}$ ** 置零初始化**。这样在训练开始时，新 Block 的输出恰好退化为恒等映射（输出 = 输入），整个扩展后模型在初始化时刻的行为与原模型完全一致，不会一开始就破坏原有能力——这与 [[18 生成模型与可控生成#[Q8] 什么是 ControlNet？如何实现对生成结构的精细控制？|ControlNet 的 Zero Convolution]] 是同一类"零初始化保证初始恒等"的设计思路。
> 5. **训练方式与数据量**：训练时** 冻结全部原始 Block**（包括 embedding 等原有参数），** 只训练新插入的 Block**；在领域语料（LLaMA Pro 使用代码和数学语料）上做** 继续预训练（Continued Pre-training，标准 next-token loss）**，规模是数十 B token 量级的语料（论文中为代码+数学语料的继续预训练规模），并非小数据微调；之后还会在此基础上再做一次指令 SFT，得到 LLaMA Pro - Instruct。
>
> > [!note] 与 Q3.1 整体逻辑的关系
> > 因为训练时原始 Block 全程冻结、且新 Block 初始化为恒等映射，模型在原有任务/通用能力上的输出路径理论上完全不受新增训练干扰，这是它"结构上避免遗忘"的根本原因——与 LoRA"冻结大部分参数、只训练少量新增参数"的思路一致，只是 LoRA 在已有层内部插入低秩增量，Block Expansion 是在层间插入全新的层。

> [!tip] Continued Pre-training 大致需要多少 token？
> 经验上，领域/通用**继续预训练（Continued Pre-training）** 通常需要 **数 B 到数十 B token** 量级的语料才能看到稳定的领域适应效果，远超 SFT 阶段的数据规模（SFT 通常是几百到几万条指令样本，详见 [[#[Q2] SFT 指令微调数据如何构建？|Q2]]）。这也是为什么 LLaMA Pro 等 Block Expansion 方法在新增 Block 上做的是"继续预训练"而不是小数据微调——量级差了好几个数量级，训练目标和数据规模都不在同一个范畴。

> [!tip] 怎么选
> 数据重放最简单、最常用，是默认首选；如果训练成本敏感或希望尽量不触碰原模型，优先考虑 LoRA/Adapter 类方法；如果已经有训练好的领域模型和原始模型两个 checkpoint，模型插值（Model Soup/WiSE-FT）是几乎零成本的"事后补救"手段，值得作为基线对比。这些方法可以叠加使用（例如 LoRA + 数据重放）。

##### [Q3.2] 模型编辑（Task Arithmetic）具体是怎么做的？数据重放有哪些常见规则？

**Task Arithmetic（任务向量运算）的具体做法**

定义**任务向量** 为某个任务上微调前后的参数差：

$$
\tau = \theta_{\text{ft}} - \theta_{\text{base}}
$$

即“为了学会这个任务，参数相对原始模型移动的方向和距离”。任务向量可以像普通向量一样做加、减、缩放，操作直接作用在参数空间：

- **任务相加（组合多个能力）**：如果分别在任务 A、任务 B 上微调得到任务向量 $\tau_A$、$\tau_B$，可以不重新联合训练，直接把两个方向都加回基座模型：

$$
\theta_{\text{multi}} = \theta_{\text{base}} + \tau_A + \tau_B
$$

  得到一个粗略同时具备 A、B 两种能力的模型——这是"组合"。

- **任务相减（抵消/抑制某种行为变化）**：如果 $\tau_{\text{unwanted}}$ 代表一种不想要的能力或偏移（例如某次领域微调引入的、对通用能力有害的偏移；或想"消除"模型的某种有毒/偏见行为），可以反向减去：

$$
\theta_{\text{new}} = \theta_{\text{base}} - \tau_{\text{unwanted}}
$$

  从参数空间里"扣掉"这部分行为变化——这是"抵消"，常用于模型遗忘（machine unlearning）、去毒、去偏见等场景。

- **按系数缩放（在能力之间找折中）**：也可以只取任务向量的一部分：

$$
\theta_{\text{final}} = \theta_{\text{base}} + \alpha \cdot \tau_{\text{domain}}, \quad \alpha \in [0,1]
$$

  $\alpha=1$ 即完整的领域微调模型，$\alpha=0$ 即原始模型，中间值在"领域能力"与"保留通用能力"之间权衡。

> [!note] 与 Model Soup / WiSE-FT 插值的关系
> 这个按系数缩放的写法和 Q3.1 提到的**权重插值（Model Soup/WiSE-FT）本质是同一个操作**：$\theta = \alpha\theta_{\text{ft}} + (1-\alpha)\theta_{\text{base}} = \theta_{\text{base}} + \alpha(\theta_{\text{ft}}-\theta_{\text{base}}) = \theta_{\text{base}} + \alpha\tau$。可以理解为：** 权重插值是"单个任务向量、按比例线性混合"的特例**；Task Arithmetic 是更通用的表述，支持** 多个**任务向量的任意加减组合，而不只是两个 checkpoint 间的简单插值。
>
> 这种"参数向量的线性运算能近似对应能力的组合/抵消"并不是严格的理论保证，而是经验上在很多场景（同结构、同初始化、微调幅度不大）下成立的近似性质，类似词向量空间里 "king − man + woman ≈ queen" 的线性类比，效果会随任务差异变大、微调幅度变大而衰减。

**数据重放（Replay）确实是最简单、最常用的默认方式**，原因是：不需要修改模型结构或训练目标，只需要调整训练数据构成；实现成本最低，效果通常作为其他方法的基线。常见的 Replay 规则包括：

1. **随机重放（Random/Uniform Replay）**：从历史/通用数据池中均匀随机抽样，按固定比例（如 Q3 提到的 1:5~1:10）混入新任务数据，是最朴素、最常用的默认做法；
2. **分层/均衡重放（Stratified/Balanced Replay）**：按任务类型或类别分层抽样，保证重放集覆盖原有各类任务的比例，避免整体随机抽样导致某些旧任务在重放数据中代表性不足；
3. **代表性样本重放（如 iCaRL）**：不随机抽，而是为每个旧类别/任务挑选最具代表性的样本（如类别均值附近的样本）保留并重放，用更少的样本达到更好的保留效果；
4. **基于梯度约束的重放（如 GEM）**：不只是把旧样本混入同一个 loss 里训练，还用旧样本算出的梯度构造约束，要求新任务的参数更新方向** 不能增加**旧任务的损失（即在梯度层面做投影修正），是比"混入数据"更强的约束形式；
5. **生成式重放（Generative Replay）**：不保存真实历史数据（节省存储、规避数据隐私问题），而是用一个生成模型（甚至模型自身）采样出"伪造的旧数据"用于重放。

> [!tip] 与 Continual Learning 已有分类的对应
> 这些 Replay 规则与 [[11 模型适应与上下文学习#[Q16] Continual Learning 有哪些代表性技术和工作？|《模型适应与上下文学习》Q16]] 中 Replay 方法一栏的 Experience Replay、GEM、iCaRL 一一对应；LLM 微调场景中最常用的仍是最简单的"随机/分层重放"，更复杂的梯度约束或生成式重放方法因实现和计算成本较高，目前在 LLM 规模下的工程应用相对少见。

#### [Q4] 进行 SFT 操作的时候，基座模型选用 Chat 还是 Base？

经验法则：**仅用 SFT 做领域模型时，资源有限就在 Chat 模型基础上训练；资源充足就在 Base 模型上训练。**（这里的"资源"＝数据 + 显卡）

- 资源充足时，可以更好地拟合自己的数据：
  - 若只拥有**小于 10k** 数据，建议选用 **Chat 模型** 作为基座进行微调；
  - 若拥有约 **100k** 数据，建议在 **Base 模型** 上进行微调。

> [!warning] 经验法则，没有严格的理论依据
> "<10k 用 Chat、~100k 用 Base"以及阈值本身都来自实践经验总结，没有严格的理论证明；不同模型的对齐强度、领域与通用分布的差异、具体任务类型都会影响最优选择，实际使用时应结合自有数据规模和验证集效果做判断，而不是机械套用阈值。

> [!question] 为什么数据量决定 Chat / Base 的选择？
> Chat 模型已经在通用指令数据上对齐过，指令遵循能力和对话格式已经具备，适合在**小数据** 场景下少量微调即可获得较好效果，且不容易在格式和基础对话能力上"跑偏"。
>
> Base 模型没有经过指令对齐，前期需要更多数据让模型重新学会"按指令格式回答"，但也因此**没有 Chat 阶段引入的对齐偏好/格式限制**，当自有数据量足够大（如 100k 级别）时，在 Base 模型上训练可以更充分、更自由地拟合目标分布，不会受到原 Chat 模型已有对齐风格的牵制。

#### [Q5] 领域词表扩增真正解决的是什么问题？

领域词表扩增（扩充 tokenizer，加入领域高频词或子词）**真正解决的是解码效率问题，而不是直接提升模型的领域理解能力** 。

**原理**

- 通用 tokenizer 对领域专有词（如医学术语、化学式、专业代码标识符）往往要切成多个子词甚至字符级 token，导致同样的文本占用更多 token；
- 扩充词表后，这些高频领域词可以被编码为**更少的 token**，单条样本的序列长度变短；
- 序列变短直接带来：
  - 训练 / 推理时**计算量和显存占用降低**（Attention 复杂度与序列长度强相关）；
  - **解码（生成）速度更快**——自回归生成是逐 token 进行的，token 数越少，生成同样内容所需的前向次数越少；
  - 相同的 context window 能装下更多"有效信息"。

> [!warning] 容易混淆的误区
> 扩词表本身**不会** 让模型"更懂"该领域知识——领域知识的获取仍然依赖于在领域语料上继续预训练或微调。扩词表只是改变了文本到 token 的切分方式，新增的 embedding 行也需要从头训练（或用相近词向量初始化）才能获得有意义的表示。把"加词表"等同于"模型学会了领域知识"是常见的错误归因。
