### 基础问题与优化方向

#### [Q1] 传统 Attention 存在哪些问题？

1. **上下文长度受限。** 对长度为 $n$ 的序列，标准 Attention 需要计算大小为 $n\times n$ 的注意力矩阵。计算复杂度约为 $O(n^2d)$，注意力矩阵的显存复杂度约为 $O(n^2)$；序列越长，计算量和显存占用增长越快。
2. **训练速度和显存受限。** 训练时需要同时处理整段序列，并为反向传播保存中间激活值，长序列的成本很高。
3. **自回归推理受 KV cache 限制。** 推理时通常缓存历史 token 的 Key 和 Value，避免重复计算。KV cache 大小随层数、序列长度、batch size 和 KV 头数线性增长，容易造成显存容量及显存带宽瓶颈。

---

#### [Q2] Attention 有哪些主要优化方向？

1. **支持更长上下文：** 改进位置编码、使用稀疏或滑动窗口 Attention、压缩历史信息等。
2. **减少计算量：** 避免显式计算完整的 $n\times n$ 注意力矩阵，或限制每个 token 关注的位置数量。
3. **减少训练显存和数据搬运：** 使用 FlashAttention 等 IO-aware 实现。
4. **减少推理 KV cache：** 使用 Multi-Query Attention（MQA）、Grouped-Query Attention（GQA）、KV 压缩或量化。

---

### 位置编码改进

#### [Q3] 改进位置编码有哪些代表性工作？

位置编码方法主要解决两个问题：让模型感知 token 的顺序和相对距离，以及提升模型在训练长度之外的长度外推能力。

| 方法 | 核心思想 | 特点 |
| --- | --- | --- |
| 相对位置编码 | 将 token 间的相对距离加入 Attention | 比只使用绝对位置更自然地表示相对关系 |
| RoPE | 通过旋转变换将位置信息注入 Q、K，使内积包含相对位置信息 | 被 LLaMA 等大量现代 LLM 使用 |
| ALiBi | 根据 Query、Key 的距离，向 Attention score 加入线性负偏置 | 不需要位置 embedding，强调邻近 token，具有一定长度外推能力 |
| Position Interpolation（PI） | 将超出训练长度的位置索引压缩回模型见过的范围，再进行少量微调 | 可扩展已有 RoPE 模型的上下文 |
| NTK-aware RoPE scaling | 调整 RoPE 不同频率维度的缩放方式 | 尽量同时保留短距离分辨率和长距离能力 |
| YaRN | 结合不同 RoPE 频率的插值策略和 Attention 缩放 | 以较少的长上下文微调扩展 RoPE 模型 |

需要注意：改进位置编码主要解决“模型能否理解更大的位置编号和距离”，本身通常**不会消除标准 Attention 的 $O(n^2)$ 计算复杂度** 。模型即使能够表示 128K 的位置，也仍需要其他方法控制 Attention 的计算量和显存占用。

---

### 稀疏与滑动窗口 Attention

#### [Q4] 稀疏、滑动窗口与历史信息压缩有哪些代表性工作？

| 类别 | 代表性工作 | 核心思想 |
| --- | --- | --- |
| 固定稀疏模式 | Sparse Transformer | 使用预先设计的局部或跨步稀疏连接 |
| 滑动窗口 + 全局 token | Longformer | 普通 token 只关注局部窗口，少量任务相关 token 执行全局 Attention |
| 局部 + 随机 + 全局 Attention | BigBird | 使用三种稀疏连接兼顾局部信息和长距离通信 |
| 滑动窗口 Attention | Mistral | 每层只直接关注最近窗口中的 token；通过堆叠多层扩大感受野 |
| 跨片段缓存 | Transformer-XL | 缓存前一片段的隐藏状态，让后续片段能够读取更早的信息 |
| 历史压缩 | Compressive Transformer | 保留近期详细记忆，并将更早的历史压缩后存入压缩记忆 |

滑动窗口本身会丢弃窗口外的直接连接。为了仍能传递远距离信息，常见做法包括增加全局 token、加入随机或跨步连接、堆叠多层扩大感受野，或者将窗口外历史压缩成更小的记忆。

---

#### [Q5] “避免显式计算完整注意力矩阵”和滑动窗口有什么区别？

“避免显式计算完整注意力矩阵”可能指两类完全不同的方法：

1. **只避免物化矩阵，但仍计算完整 Attention。**  
   例如 FlashAttention 不把完整的 $n\times n$ score 和概率矩阵写入 HBM，而是分块计算精确 Attention。它减少显存占用和数据搬运，但所有 Query、Key 对仍然参与计算，因此计算复杂度仍约为 $O(n^2d)$。

2. **从算法上不计算所有 Query、Key 对。**  
   滑动窗口 Attention 属于这一类。若窗口大小为 $w$，每个 token 只关注附近约 $w$ 个 token，计算复杂度可由 $O(n^2d)$ 降至约：

   $$
   O(nwd)
   $$

   当 $w\ll n$ 时可以显著减少计算，但窗口外 token 无法直接互相关注，因此它改变了 Attention 的连接模式，可能损失全局信息。

线性 Attention 也从算法上避免完整注意力矩阵，但它通常通过核函数和结合律重排计算，而不是限制每个 token 只能关注固定窗口。它理论上仍可聚合全局信息，但不再等同于标准 Softmax Attention。

---

#### [Q6] 限制每个 token 关注位置数量有哪些代表性工作？

- **Sliding Window / Local Attention：** 每个 token 只关注相邻窗口。代表工作包括 Longformer 和 Mistral。
- **Dilated / Strided Attention：** 除局部 token 外，按固定间隔关注更远位置，以较少连接扩大感受野。Sparse Transformer 和 Longformer 使用过类似设计。
- **Local + Global Attention：** 大多数 token 使用局部 Attention，少量全局 token 可关注整个序列。代表工作是 Longformer。
- **Local + Random + Global Attention：** 使用随机连接帮助远距离信息传播。代表工作是 BigBird。
- **基于内容选择位置：** 根据 token 内容动态寻找值得关注的位置，而非使用固定连接模式。代表工作包括 Reformer 的 LSH Attention 和 Routing Transformer。

这些方法真正减少了参与计算的 Query、Key 对数量。代价是 Attention 不再完全稠密，需要在计算效率、硬件友好性和全局信息召回能力之间权衡。

### Attention 变体

#### [Q7] Attention 的常见变体有哪些？

- **稀疏 Attention：** 只计算部分 token 对之间的注意力，从而降低计算量。
- **线性 Attention：** 利用核函数或结合律改变计算顺序，避免显式构造完整注意力矩阵，目标是将序列长度方向上的复杂度降至近似线性。
- **原型或内存压缩：** 压缩 Key、Value 或外部记忆，减少注意力需要处理的状态数量。
- **低秩 Attention：** 使用低秩结构近似注意力矩阵。
- **Attention 与先验：** 将局部性、相对位置或其他先验引入注意力机制。
- **改进多头机制：** 使用 MQA、GQA 等方式减少 KV 头数量。

---

#### [Q8] 压缩 Key、Value 或外部记忆有哪些代表性工作？

这类方法不一定删除原始输入 token，而是先将大量历史状态变成更少或维度更低的状态，再让 Attention 读取压缩后的表示。可以沿两个维度进行压缩：

1. **压缩状态数量，即序列长度维度。**

   - **Compressive Transformer：** 保存近期的细粒度记忆，并将更早的历史状态压缩成数量更少的粗粒度记忆。
   - **Set Transformer：** 使用少量可学习的 inducing points 汇总输入，再通过这些摘要状态间接建模输入元素之间的关系。
   - **Perceiver：** 使用 Cross-Attention 将很长的输入压缩到固定数量的 latent tokens，后续主要在较短的 latent sequence 上计算 Self-Attention。
   - **Linformer：** 沿序列长度维度投影 K、V，将 $n$ 个状态压缩成 $k$ 个状态，其中 $k\ll n$。

2. **压缩每个状态的特征维度或 KV 头数量。**

   - **MQA / GQA：** 通过让多个 Query 头共享 K、V，减少每个 token 需要缓存的 KV 状态数量。
   - **DeepSeek Multi-head Latent Attention（MLA）：** 将每个 token 的多头 K、V 联合压缩为低维 latent vector；推理时主要缓存压缩后的 latent KV，从而大幅减少 KV cache。

两类压缩解决的问题不同：

- 沿序列长度压缩，会减少 Attention 需要读取的历史位置数量，因此可能减少长序列 Attention 计算量，但可能丢失细粒度历史信息。
- 沿特征维度或 KV 头压缩，主要减少 KV cache 和显存带宽；如果仍然读取所有历史 token，其 Attention 在序列长度方向上仍可能是线性的单步解码成本。

#### [Q9] Attention 的“先验”是什么？

先验（prior）或归纳偏置（inductive bias），是指在查看具体训练数据之前，模型架构预先假设“哪些关系更可能重要”。标准全局 Attention 的结构先验较弱：原则上每个 token 都可以关注其他所有 token，并主要依靠数据学习关注模式。

常见 Attention 先验包括：

- **局部性先验：** 相邻 token 通常关系更强，因此优先关注附近位置。滑动窗口 Attention 和卷积都包含这种先验。
- **距离衰减先验：** 距离越远，默认相关性越低。例如 ALiBi 会根据距离向 Attention score 加入更大的负偏置。
- **因果先验：** 生成当前位置时不能查看未来 token，即 causal mask。
- **层级或分块先验：** 同一段落、窗口或层级中的 token 更可能交互。
- **图结构先验：** 只允许图中相邻节点或特定关系类型之间进行 Attention。
- **全局 token 先验：** 预先指定少量 token 负责汇总或广播全局信息，例如 Longformer 和 BigBird 的全局 token。

先验可以减少模型需要从数据中学习的搜索空间，并提高计算效率；但错误或过强的先验也可能限制模型发现真实的远距离关系。

---

#### [Q10] 使用低秩结构近似注意力矩阵，是 DeepSeek 的 MLA 吗？

**两者都使用了低秩思想，但不是同一种方法。**

经典的“使用低秩结构近似注意力矩阵”通常指 **Linformer** 一类方法。标准 Attention 的权重矩阵形状为：

$$
A=\operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d_k}}\right)
\in\mathbb R^{n\times n}
$$

Linformer 假设这个沿序列位置展开的 $n\times n$ 矩阵可以用较低秩结构近似，并沿序列长度维度将 K、V 从 $n$ 个状态投影到 $k$ 个状态：

$$
K'=E K,\qquad V'=F V,\qquad k\ll n
$$

其主要目标是避免关于序列长度的完整二次 Attention，将复杂度从 $O(n^2)$ 降低到近似 $O(nk)$。

DeepSeek-V2/V3 使用的 **Multi-head Latent Attention（MLA）** 则对每个 token 的多头 K、V 进行低秩联合压缩：

$$
c_t^{KV}=x_tW^{DKV}
$$

其中 $c_t^{KV}$ 是需要缓存的低维 latent KV。需要使用 K、V 时，再通过上投影进行恢复或通过矩阵吸收避免显式恢复。MLA 的主要目标是减少自回归推理中的 KV cache 和显存带宽。

因此：

| 方法 | 主要压缩维度 | 主要目标 | 是否仍关注所有历史 token |
| --- | --- | --- | --- |
| Linformer | 序列长度维度 | 降低完整 Attention 的二次复杂度 | 压缩为较少的序列状态 |
| DeepSeek MLA | 每个 token 的 KV 特征维度 | 减少 KV cache 和解码带宽 | 是，通常仍读取所有历史 token 的压缩 latent |

所以可以广义地说 MLA 是一种低秩 Attention；但它**不是**“用低秩矩阵直接近似 $n\times n$ 注意力矩阵”的 Linformer 路线。

### 多头机制：MHA、MQA、GQA

#### [Q11] Multi-Head Attention 存在什么问题？

Multi-Head Attention（MHA）中，每个注意力头都有各自的 Query、Key 和 Value：

$$
Q_i=XW_i^Q,\qquad K_i=XW_i^K,\qquad V_i=XW_i^V
$$

- **训练阶段：** MHA 通常能够提供较强的表达能力，但每个头独立计算 K、V，会增加参数量和计算量。
- **自回归推理阶段：** 每个头都需要保存自己的 K、V。反复从显存加载巨大的 KV cache，容易使解码过程受显存容量和带宽限制。

MHA 的主要问题不是显著拖慢训练，而是其较大的 KV cache 会严重影响长上下文、大 batch 推理。

---

#### [Q12] 什么是 Multi-Query Attention？

Multi-Query Attention（MQA）保留多个 Query 头，但所有 Query 头共享同一组 Key 和 Value：

$$
Q_i=XW_i^Q,\qquad K=XW^K,\qquad V=XW^V
$$

第 $i$ 个 Query 头使用共享的 $K$、$V$：

$$
\operatorname{head}_i
=\operatorname{Attention}(Q_i,K,V)
$$

因此，MQA 中 Query 头数量 $n_q$ 可以很大，但 KV 头数量固定为：

$$
n_{kv}=1
$$

---

#### [Q13] MHA 和 MQA 有什么区别？

| 类型 | Query 头 | KV 头 | KV cache | 表达能力 |
| --- | --- | --- | --- | --- |
| MHA | 每个头拥有独立 Query | 每个头拥有独立 K、V | 最大 | 通常最强 |
| MQA | 每个头拥有独立 Query | 所有 Query 头共享一组 K、V | 最小 | 可能略有损失 |

若其他条件相同，MQA 相比 MHA 的 KV cache 理论缩减比例约为：

$$
\frac{\operatorname{KVCache}_{\mathrm{MQA}}}
{\operatorname{KVCache}_{\mathrm{MHA}}}
=\frac{1}{n_q}
$$

---

#### [Q14] MQA 有什么好处和代价？

**好处：**

1. 大幅减少 KV cache 的大小。
2. 减少解码时从显存读取 K、V 的数据量。
3. 提升自回归推理吞吐量，并支持更大的 batch 或更长的上下文。

**代价：**

所有 Query 头共享同一组 K、V，会降低 KV 表示的多样性，可能造成轻微的模型质量损失。训练速度通常不会像推理速度一样获得显著提升，因为训练中的主要成本仍是大规模矩阵乘法和 Attention 计算。

为了在比较不同架构时保持总参数量大致一致，模型设计者有时会把 MQA 节省出的参数分配给隐藏维度、Attention 输出投影或 FFN。这是模型设计选择，并不是 MQA 的必要组成部分。

---

#### [Q15] 哪些模型使用了 Multi-Query Attention？

代表性模型包括 PaLM、ChatGLM2-6B，以及部分 Falcon 模型。不同规模或版本的同一模型系列可能采用不同的注意力结构，应以具体模型配置中的 `num_attention_heads` 和 `num_key_value_heads` 为准。

---

#### [Q16] 什么是 Grouped-Query Attention？

Grouped-Query Attention（GQA）介于 MHA 和 MQA 之间。它保留多个 KV 头，并让一组 Query 头共享一组 K、V：

$$
1<n_{kv}<n_q
$$

若有 $n_q$ 个 Query 头和 $n_{kv}$ 个 KV 头，则每组通常包含：

$$
\frac{n_q}{n_{kv}}
$$

个 Query 头。三种结构可统一表示为：

| 类型 | KV 头数量 |
| --- | --- |
| MHA | $n_{kv}=n_q$ |
| GQA | $1<n_{kv}<n_q$ |
| MQA | $n_{kv}=1$ |

GQA 在 MHA 的模型质量和 MQA 的推理效率之间进行折中。若其他条件相同，其 KV cache 相对 MHA 的比例约为：

$$
\frac{\operatorname{KVCache}_{\mathrm{GQA}}}
{\operatorname{KVCache}_{\mathrm{MHA}}}
=\frac{n_{kv}}{n_q}
$$

---

#### [Q17] 哪些模型使用了 Grouped-Query Attention？

代表性模型包括 LLaMA 2 34B/70B 等。是否使用 GQA 以及 KV 头数量取决于具体模型规模和版本，不能仅根据模型系列名称判断。

### FlashAttention

#### [Q18] 什么是 FlashAttention？

FlashAttention 是一种 **IO-aware 的精确 Attention 实现** 。它不会改变标准 Attention 的数学结果，也不是使用近似的“分块 Softmax”替代原始 Softmax；其核心是通过分块、online softmax、重计算和 kernel 融合，避免将完整的 $n\times n$ 注意力矩阵反复写入和读出高带宽显存（HBM）。

标准 Attention 为：

$$
\operatorname{Attention}(Q,K,V)
=\operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d_k}}\right)V
$$

FlashAttention 将 Q、K、V 分块加载到速度更快但容量更小的片上 SRAM 中计算，从而减少 HBM 与 SRAM 之间的数据搬运。

**主要优点：**

1. 减少 HBM 读写和训练显存占用。
2. 提高训练和推理速度。
3. 保持精确 Attention 的结果，不需要稀疏或低秩近似。

**关键词：** HBM、SRAM、tiling、online softmax、重计算、kernel 融合。

### Attention Sink 与流式推理

#### [Q19] 什么是 Attention Sink？

Attention Sink（注意力汇）是指：某些 token 会持续吸收大量 Attention 权重，即使这些 token 本身没有重要语义。它们像“水槽”一样，接收其他 token 暂时不需要分配给有效上下文的注意力质量。

Attention 权重经过 Softmax 后，每个 Query 的权重之和必须为 $1$：

$$
\sum_j
\operatorname{softmax}\left(
\frac{q_i k_j^\top}{\sqrt{d_k}}
\right)=1
$$

即使当前 Query 没有特别值得关注的历史 token，也不能把总 Attention 权重降低到小于 $1$。模型因此可能学习将多余的注意力集中到某些相对稳定的位置上，这些位置便成为 Attention Sink。

**常见现象：**

1. Sink 经常出现在序列最前面的几个 token。最典型的是 BOS token，或者输入被分块、packing 后每个训练序列的第一个 token。
2. Sink token 获得高 Attention 权重，不代表其文本语义重要。
3. 不同 Attention 头和层出现 Attention Sink 的程度不同。
4. Attention Sink 与 massive activation 经常同时出现，但二者不是完全相同的概念：前者指 Attention 权重集中，后者指隐藏状态中出现极大的激活值。

---

#### [Q20] Attention Sink 中的“某些 token”具体是哪些 token？

它们通常不是某几个固定词汇，而是由 **token 所在的位置、训练数据格式和损失函数** 共同决定：

- 对标准自回归语言模型，最常见的是序列第一个 token 或最前面的少量 token。
- 如果每个训练样本都以 BOS token 开始，BOS 很容易成为稳定的 Sink。
- 即使第一个 token 的内容被随机替换，Sink 仍可能出现在第一个位置，说明位置往往比语义更重要。
- 如果在固定的第二或第三位置放置特殊 token，Sink 可以转移到对应位置。
- 在 prefix LM 中，Sink 可能分散在多个 prefix token 上。

因此，Sink 更像是模型学习到的一个稳定 **Key bias / Attention 落点**，而不一定是负责存储重要语义的 Value。

---

#### [Q21] Attention Sink 在训练的哪个阶段出现？

Attention Sink 通常在 **pre-training 过程中逐渐涌现**，而不是等到 mid-training 或 post-training 才突然产生。研究观察到：

1. 随机初始化时通常没有稳定的 Attention Sink。
2. 模型经过有效优化并见过足够多的预训练数据后，Sink 逐渐明显。
3. 学习率、weight decay、训练数据量、数据格式和损失函数都会影响 Sink 的形成及位置。
4. Mid-training、SFT 和 RLHF 等后续训练可能改变其强度或分布，但通常是在 pre-training 已形成的 Attention 结构上继续调整。

所以更准确的说法是：**Attention Sink 是在预训练优化中学出来的结构性现象，并在训练完成后的推理阶段被观察和利用。**

**为什么直接使用滑动窗口可能失败？**

普通滑动窗口推理只保留最近 $w$ 个 token 的 KV cache，并删除更早的 token。如果最前面的 Sink token 也被删除，模型失去了训练时依赖的稳定“注意力落点”，Attention 分布会明显改变，导致困惑度上升和生成质量下降。

StreamingLLM 的核心做法是同时保留：

1. 最前面的少量 Attention Sink token；
2. 最近滑动窗口内的 token。

其保留的 KV cache 可表示为：

$$
\underbrace{\text{initial sink tokens}}_{\text{固定保留}}
\quad+\quad
\underbrace{\text{recent window tokens}}_{\text{持续滑动}}
$$

这样可以在 KV cache 大小近似固定的情况下进行很长的流式生成。需要注意，保留 Sink token 主要维持模型稳定性，并不意味着模型能够完整回忆所有被窗口删除的历史内容。

#### [Q22] StreamingLLM 保留多少个 Sink token？滑动窗口多大？

不存在适用于所有模型的固定数值，应根据模型和任务验证：

- StreamingLLM 原论文发现，保留最前面的 **4 个 token** 通常足以恢复稳定性能，因此 `start_size=4` 是常见默认值。
- Sink token 数量通常很小，例如 1～4 个；模型未显式训练专用 Sink token 时，保留几个开头 token 往往比只保留一个更稳妥。
- 滑动窗口大小由 KV cache 预算和任务需要决定。常见实验值包括 1024、2048 或 4096 个 token；窗口越大，近期上下文保留越完整，但显存和单步 Attention 成本越高。
- 如果总 KV cache 预算为 $C$，保留 $s$ 个 Sink token，则最近窗口约保留 $C-s$ 个 token：

  $$
  \operatorname{cache}
  =
  \underbrace{s\text{ 个初始 Sink token}}_{\text{固定}}
  +
  \underbrace{(C-s)\text{ 个最近 token}}_{\text{滑动窗口}}
  $$

应通过困惑度、下游任务质量、吞吐量和显存占用共同选择 $s$ 与 $C$，不能仅照搬一个默认值。

#### [Q23] 显式加入专用 Sink token 后，为什么仍有 Sink？这样做有什么用？

加入专用 Sink token 的目的**不是消除 Attention Sink 现象**，而是主动控制 Sink 出现在哪里。

如果不加入专用 token，模型仍可能把普通的 BOS 或前几个真实文本 token 当作 Sink。这会带来两个问题：

1. Sink 位置和数量可能因模型、输入格式而变化，流式推理时需要猜测应固定保留多少个开头 token。
2. 普通文本 token 同时承担语义表示和“吸收多余 Attention”的系统功能，两种角色可能互相干扰。

> [!important] Attention Sink 主要由位置和训练机制产生，而非 token 的特殊语义
> Attention Sink 通常不是系统工程师预先手动设置的规则，而是模型在使用 **causal mask、Softmax Attention、自回归训练目标和固定数据格式** 进行预训练时自然涌现的系统性现象。
>
> - 同一个词出现在普通位置时，通常不会自动成为 Sink。
> - 即使不断随机替换序列第一个 token 的实际内容，模型仍可能把第一个位置学成 Sink。
> - 如果把一个固定特殊 token 放在第二或第三位置，Sink 也可能转移到该位置。
>
> 因此，成为 Sink 的主要原因通常是该 token 占据了一个稳定、所有后续 token 都能访问的位置，而不是它表达了特殊语义。模型将这个位置学习成类似 **Key bias** 的稳定注意力落点，用于接收 Softmax 必须分配出去但当前没有明确语义目标的注意力权重。
>
> BOS token 之所以经常成为 Sink，并不主要因为“序列开始”这一语义特别重要，而是因为它始终位于第一个位置、对所有后续 token 可见，并且在不同训练样本中非常稳定。

> [!question] 是什么训练机制导致 Attention Sink？
> Attention Sink 不是由某一个单独机制产生的，而是以下机制在预训练优化中共同作用的结果：
>
> 1. **Softmax 强制 Attention 权重和为 1。**  
>    对每个 Query，模型必须把总计为 1 的权重分配给可见 Key。某个 Attention 头若暂时不需要从任何历史 Value 读取信息，也无法直接输出“全部权重为 0”；于是模型可以学习一个稳定 Key，承接这些权重。
>
> 2. **Causal Mask 造成位置可见性的长期不对称。**  
>    序列第一个 token 对之后所有 token 都可见，而后面的 token 只能被更晚的位置看到。因此，第一个位置在训练中收到最稳定、最广泛的 Attention 连接，最容易被优化成公共落点。
>
> 3. **固定的数据格式提供稳定位置。**  
>    预训练样本通常以 BOS 或固定前缀开始。不同样本中的正文不断变化，但开头位置始终存在，使模型容易将其 Key 学成与具体语义无关的稳定偏置。
>
> 4. **自回归 next-token loss 间接奖励这种行为。**  
>    训练目标不会直接要求模型产生 Sink；但只要将无用 Attention 分配到稳定位置能够降低 next-token loss，梯度下降就会保留并强化这种内部策略。
>
> 5. **充分训练使该模式逐渐涌现。**  
>    随机初始化时通常不存在稳定 Sink。模型在足够数据上被有效优化后，Sink 才逐渐明显；实验还发现学习率、weight decay、数据格式和损失定义会影响其强度和位置。
>
> 可以将其理解为：**Softmax 提供了“必须分配权重”的需求，Causal Mask 和固定开头位置提供了最稳定的候选落点，next-token loss 再通过梯度下降把这种策略学习出来。**
>
> “承接多余 Attention”是一种直观解释，并不代表模型显式判断某部分 Attention 是多余的。更严格地说，Sink token 的 Key 常表现得像一个学习得到的 Attention bias，而其 Value 对最终输出可能贡献很小。

> [!question] 专用 Sink token 的 ID 和个数如何设计？
> **Sink token 没有统一规定的 ID。** 如果要显式设计专用 Sink token，通常在 tokenizer 中新增一个特殊 token，例如 `<|sink|>`，并将它分配到词表中尚未使用的 ID。假设原词表大小为 $V$，一种常见做法是将其 ID 设为 $V$，再将模型的输入 Embedding 和输出词表扩展到 $V+1$。具体 ID 取决于 tokenizer 和模型配置，不能固定认为它是某个数字。
>
> 每个训练序列通常在最前面插入 **1 个专用 Sink token**：
>
> $$
> [\texttt{<|sink|>},x_1,x_2,\ldots,x_n]
> $$
>
> 该 token 必须参与 Transformer 前向传播，使后续 token 能够关注它；但通常不要求模型预测它，其位置可在 loss 中被 mask。训练和推理时都必须使用相同的插入规则，并在流式推理期间永久保留它的 KV cache。
>
> 专用 Sink token 的个数也是超参数。通常先尝试 **1 个**；如果一个 token 无法稳定承接不同层和 Attention 头的 Sink 行为，可以通过消融实验增加到少量多个 token。增加数量会占用更多 KV cache，因此不是越多越好。
>
> 需要区分两种情况：
>
> - **显式专用 Sink token：** 模型从预训练开始就插入 `<|sink|>`，通常保留 1 个；其 ID 是人为新增并写入模型配置的。
> - **StreamingLLM 应用于已有模型：** 不新增任何 token，也没有专门的 Sink ID；它直接保留原序列最前面的若干真实 token 的 KV cache。论文中常保留前 4 个 token，这些 token 的 ID 完全由实际输入决定。

若在每个预训练序列开头显式加入一个无语义、始终存在的专用 Sink token，模型可以稳定地把多余 Attention 分配给它。这样：

- 推理时只需固定保留这个专用 token，Streaming KV cache 的管理更明确。
- Sink 不再占用普通文本 token，语义 token 可以更专注于表达内容。
- 专用 token 从预训练开始就被模型学习和依赖，删除其他旧 token 时 Attention 分布更稳定。
- 理想情况下，一个专用 Sink token 就可能替代原本需要保留的多个初始 token，从而略微节省 KV cache。

因此，**专用 Sink token 是把不可控的自然涌现 Sink，变成位置固定、语义隔离、便于推理系统保留的受控 Sink。**

### KV Cache 系统实现

#### [Q24] 面试中 PagedAttention 的 KV Cache 怎么写？

面试通常**不要求** 完整实现 PagedAttention CUDA kernel，而是要求写清楚三部分：KV block 的物理存储、每个请求的 block table、以及如何根据 token 位置找到对应的物理 KV 地址。

**基本假设：**

- block size 为 $B$；
- 每个物理 block 存固定数量 token；
- KV pool 提前分配；
- 每个请求维护逻辑 block 到物理 block 的映射。

**1. 数据结构**

```python
class PagedKVCache:
    def __init__(
        self,
        num_blocks: int,
        num_layers: int,
        block_size: int,
        num_kv_heads: int,
        head_dim: int,
    ):
        self.num_blocks = num_blocks
        self.num_layers = num_layers
        self.block_size = block_size
        self.num_kv_heads = num_kv_heads
        self.head_dim = head_dim

        # 实际实现中位于 GPU HBM
        self.k_cache = torch.empty(
            num_layers,
            num_blocks,
            block_size,
            num_kv_heads,
            head_dim,
            device="cuda",
            dtype=torch.float16,
        )
        self.v_cache = torch.empty_like(self.k_cache)

        self.free_blocks = list(range(num_blocks))
        self.block_tables = {}  # request_id -> list[physical_block_id]
        self.seq_lens = {}
```

> [!note] 物理布局可以不同
> 这里使用 `[num_layers, num_blocks, block_size, num_kv_heads, head_dim]`，实际实现（如 vLLM）也可能采用 `[num_blocks, num_kv_heads, head_dim, block_size]`，具体取决于 Attention kernel 的访存模式。

**2. 分配新 block**

```python
def allocate_block(self, request_id: str) -> int:
    if not self.free_blocks:
        raise RuntimeError("KV cache is full")

    block_id = self.free_blocks.pop()

    if request_id not in self.block_tables:
        self.block_tables[request_id] = []
        self.seq_lens[request_id] = 0

    self.block_tables[request_id].append(block_id)
    return block_id
```

**3. 写入一个新 token 的 KV**

对于序列中位置为 $t$ 的 token，地址映射公式为：

$$
b_{\text{logical}} = \left\lfloor \frac{t}{B} \right\rfloor, \qquad
o = t \bmod B, \qquad
b_{\text{physical}} = \text{block\_table}[r,\, b_{\text{logical}}]
$$

```python
def append_token_kv(
    self,
    request_id: str,
    layer_id: int,
    k: torch.Tensor,
    v: torch.Tensor,
):
    token_pos = self.seq_lens[request_id]

    logical_block = token_pos // self.block_size
    block_offset  = token_pos % self.block_size

    table = self.block_tables[request_id]

    if logical_block == len(table):
        self.allocate_block(request_id)

    physical_block = self.block_tables[request_id][logical_block]

    self.k_cache[layer_id, physical_block, block_offset].copy_(k)
    self.v_cache[layer_id, physical_block, block_offset].copy_(v)
```

> [!note] seq_len 的更新时机
> 实际实现中，`seq_lens` 不应在每层写完后立即递增，而应在**所有层完成该 token 的写入后统一更新** 。上面代码仅用于展示地址映射逻辑。

**4. Decode 时读取历史 KV**

```python
def read_kv_blocks(self, request_id: str, layer_id: int):
    seq_len = self.seq_lens[request_id]
    num_logical_blocks = (seq_len + self.block_size - 1) // self.block_size

    table = self.block_tables[request_id]
    blocks = []

    for logical_block in range(num_logical_blocks):
        physical_block = table[logical_block]
        valid_tokens = min(
            self.block_size,
            seq_len - logical_block * self.block_size,
        )
        k_block = self.k_cache[layer_id, physical_block, :valid_tokens]
        v_block = self.v_cache[layer_id, physical_block, :valid_tokens]
        blocks.append((k_block, v_block))

    return blocks
```

> [!important] 真正的 PagedAttention kernel 不拼接 block
> 实际 kernel 不会先把所有 block 拼成一个连续 tensor，而是**边查 block table、边加载、边计算 Attention**，以避免额外的显存分配和数据搬运。

**5. PagedAttention kernel 的核心寻址逻辑**

面试中写出以下伪代码通常即可：

```
for each request r in batch:
    seq_len = seq_lens[r]

    for token_idx in [0, seq_len):
        logical_block = token_idx / BLOCK_SIZE
        block_offset  = token_idx % BLOCK_SIZE

        physical_block = block_table[r][logical_block]

        K = k_cache[layer][physical_block][block_offset]
        V = v_cache[layer][physical_block][block_offset]

        score = dot(Q[r], K)
        update_online_softmax(score, V)
```

真正高效的 kernel 以 **block 为粒度** 处理，而非逐 token 循环：

```
for each logical KV block:
    physical_block = block_table[request][logical_block]

    load K tile from k_cache[physical_block]
    compute QK scores
    update online softmax statistics

    load V tile from v_cache[physical_block]
    accumulate weighted V
```

**地址公式总结：**

$$
b_{\text{logical}} = \left\lfloor \frac{t}{B} \right\rfloor, \qquad
o = t \bmod B, \qquad
b_{\text{physical}} = \text{block\_table}[r,\, b_{\text{logical}}]
$$

$$
K_{r,t} = K_{\text{pool}}[b_{\text{physical}},\, o], \qquad
V_{r,t} = V_{\text{pool}}[b_{\text{physical}},\, o]
$$
