**Q：MoE 多专家并行**

- **Grouped GEMM Library API** 
	- 理论上支持把不同 Shape、转置方式和缩放系数的多个 GEMM 合并到一次 kernel launch。
	- vLLM 和 SGLang 等框架是基于Grouped GEMM实现的，但是要求 intermediate dimension 完全一致。token 数量可以不同。
		- token 数不同容易并行：N 是 GEMM 的输出空间维度，可以并行拆分（直接拆成相互独立的输出 Tile 并行计算）。MMA Tile、寄存器分配、Shared Memory、Stage 数都可以共用。
		- intermediate dim 不同不容易并行：这个是底层 GEMM 的 K 维，是tiling looping 的维度，如果不同 GEMM 的 K 维有大有小的话，warp 计算完成先后会差很多 (下面一问具体解释了)
- **Persistent Kernel** 
	- CUTLASS （Grouped Kernel Scheduler）、Grouped GEMM、grouped convolution、Hopper 的高性能 GEMM Kernel 大量使用、batched GEMM
	- **做法** 固定数量的 CTA （Cooperative Thread Array）常驻 SM（Streaming Multiprocessor，流式多处理器），数量和 SM 数量几乎相当
		> CTA 是 Thread Block，是一组 warp。例如：kernel<<<grid, 256>>>(); 也就是 256 线程，即 256/32=8 个 warp	
	- **作用** 减少 Kernel Launch，改善不规则 workload 的负载均衡（CUTLASS 文档 - Grouped Scheduler 和 Problem Sorting）；缺点是常驻并占据 SM。
	- **原理** 不同专家产生的 Tile 数量和单 Tile 计算量可能不同，静态分配容易让部分 CTA 提前结束。这个方法动态任务领取，把剩余 Tile 持续分配给已经空闲的 CTA。
	- **例子** 通常一个 GEMM 有一个 kernel，但 Persistent Kernel 可以驻留 SM 并处理多个 GEMM，适合连续处理多个小 GEMM。通常一次领取一批任务也就是多个 tile，防止原子操作成为计算瓶颈。
- PyTorch 的 **torch.nn.functional.grouped_mm**
	- 要求专家 weight shape 相同，token 数量可以不同（底层可以改，但改了不代表性能一定好）

**Q： 不同专家宽度不一致时，标准 Grouped GEMM 的执行效率会受到影响，原因是什么**

**K 维（reduction 维）不同** 会直接影响主循环迭代次数、Pipeline Stage。一个 Kernel Configuration 很难同时适配所有 Shape，并产生边缘 Tile、负载不均衡、权重布局不规则和更多 Kernel Variant。


| 每专家 Token 数  | 典型情况                | 性能特征                    |
| ----------------: | ------------------- | ----------------------- |
|             1 至 8 | 小 Batch Decode      | 极小 GEMM，Launch 和访存开销占主导 |
|            8 至 64 | Decode 或低 Batch     | Tensor Core 利用率较低       |
|          64 至 256 | 中等 Batch 或短 Prefill | 开始能够形成较多 Tile           |
|            256 以上 | Prefill 或训练         | 更容易获得较高利用率              |

1. 宽度离散化
2. 分桶执行 grouped GEMM，相似 shape 分到一桶执行
3. Shape-Aware Pruning

#### 底层/系统相关问题

**Q：All-to-All 为什么比 All-Reduce 难优化？**
- All-Reduce 通常每个 rank 发送相同规模数据，模式规整。
- All-to-All：GPU 之间通信数据量不同；路由结果动态变化；需要额外重排和元数据管理

**Q：通信与计算重叠手段**
- 多 CUDA stream：提供并发执行的基础机制。
- 分块 All-to-All：把一次大通信拆成多个小通信，使通信可以分阶段完成。
- NCCL group：批量提交多个 NCCL 操作，主要减少启动开销并协调多卡通信，本身不等于重叠。
- CUDA event：负责不同 stream 之间的依赖和同步。
- 通信与 Grouped GEMM 流水化：最终形成真正的通信计算重叠。

**Q：内部碎片和外部碎片分别是什么**
- 内部碎片是已分配 block 内部没有用满的空间，例如最后一个 KV block 未填满
- 外部碎片是空闲空间被切成多个不连续小块，无法满足大块连续分配【Paged KV解决的】

**Q：Occupancy 低但性能高的可能原因**
1. Tensor Core 指令吞吐已经接近峰值，少量 warp 即可填满计算流水线。
2. 单个 warp 有足够 ILP，通过多级流水和双缓冲隐藏延迟。
	> ILP 是 Instruction-Level Parallelism，指令级并行性。意思是：同一个 warp 内存在多条彼此没有数据依赖的指令，GPU 可以让它们的执行过程重叠，从而隐藏指令延迟。

3. Kernel 是 compute-bound，而不是依靠大量 warp 隐藏访存延迟。
4. 寄存器使用较高导致 occupancy 下降，但减少了 shared memory 或 global memory 访问。
5. Tile 较大，单个 CTA 工作效率高，数据复用充分。
6. 问题规模较小，更多 occupancy 本身没有实际收益。

> 结论：不能为了提高 occupancy 而盲目减小寄存器或 tile，这可能反而降低性能。

**Q：如何判断算子性能低，是否接近极限**
1. **计算上界**（实际FLOPs  除以 kernel time）和该数据类型的 Tensor Core 峰值
2. **带宽上界**  （实际读写字节数​ 除以 kernel time）与实际可达到的 HBM 带宽比较
3. 两者都低
	- 通常存在访存不合并（有效带宽低）
	- 流水线气泡（load 和 compute 无法重叠）
	- 同步等待（`__syncthreads()`需要等其他线程都完成）
	- 分支发散（**if else** 硬件上接近串行执行、**稀疏计算**大部分 lane 是空闲）
	- tile 不合理（例如权重 tile 太小，加载后只计算一次，显存带宽利用率可能不高；太大，可能 register 过高，活跃 warp少）
	- 并行度不足（SM 闲置）
	- launch overhead（解决办法：Kernel Fusion、cuda graph、Persistent Kernel、合并小 GEMM等）
4. 看 Nsight Compute 
	- Tensor Core utilization / SM throughput
	- DRAM throughput
	- L2 hit rate
	- Warp stall reason
	- Register、shared memory、occupancy
	- 指令数量与数据搬运比例

**Q：结构化剪枝减少了 FLOPs，为什么不一定加速？**

因为端到端速度不仅由 FLOPs 决定，还受到 GEMM Shape、Tensor Core 对齐、每专家 Token 数、Kernel Launch、HBM 带宽和 Grouped Scheduler 负载均衡影响。剪枝后如果产生大量窄而不规则的专家，GPU 利用率下降可能抵消部分 FLOPs 收益。因此需要做宽度对齐、Shape 离散化、按宽度分组以及实际端到端 Benchmark。

**Q：B卡特性**
1. **双 Die** 上层逻辑是 1 个 GPU，实际存储容量和算力是 2 个 GPU，通过约 10 TB/s 的片间互联（Die：裸硅芯片本体）
	1. 两个 Die 共享统一地址空间和一致的 L2 访问语义
	2. 高性能 kernel 需要考虑跨 Die 的数据位置和带宽差异，仍需考虑数据局部性
2. **新数制** 原生支持 FP4、microscaling 格式、E3M2 或 E2M3 的 MXFP6（主要支持 Tensor Core 的 GEMM 计算）；Tensor Core 计算吞吐变快 *-> 非 Tensor Core 的路径会容易变成 memory bound、通信 bound、launch bound、同步等待*
3. **显存大** 单卡 B200 最多 180G 显存 -> 最佳 TP 方式会变，通信拓扑会变
4. **缓存大** L2 Cache 增加到约 126 MB，每个 SM 最多有 228 KB shared memory *-> 更大 tile、多级流水、缓存中间结果、减少 global memory 往返*
5. **通信快** 机架内高带宽低延迟（不是机架间）：NVLink 带宽 1.8 TB/s，是 hopper 的两倍；NVL72可以把 72 个 B 卡放到一个domain，总 GPU 通信带宽约 130 TB/s *-> TP 并行的 all-reduce、EP并行的 all-to-all、PP 并行的传输激活、分布式 KV、参数共享、PD 分离的 KV 迁移* 会更实用，但调度、拓扑、负载均衡仍关键
6. **更灵活共享内存** hopper 的 Distributed Shared Memory 依然沿用：Thread Block Cluster 里的多个 CTA 可以访问彼此的 shared memory 

**Q：CPU 的存储结构？**
- **局部性** CPU cache line 是 64 bytes：例如读取一个 int 时，CPU 通常会把它所在的整个 64 Bytes Cache Line 载入缓存，因此连续访问有比较好的空间局部性；随机访问会Cache Miss。
	> cache line ：cache 中搬运和存储的基本单位。部分架构中 cache line 被拆成更小的 sector，用于减少无效数据传输
- **缓存一致性协议** 多核 CPU 中，每个核有私有 Cache：一个核修改数据，别的核不能再用旧缓存副本
- **目的** 单次访存更快。强调缓存命中率。
- CPU 的缓存结构如表所示

| 层级       | 归属          |           典型容量 | 特点             |
| -------- | ----------- | -------------: | -------------- |
| Register     | 每个 CPU 核    |     几百 B 到几 KB | 最快，由指令直接访问     |
| L1 Cache | 每个核私有       | 32 KB 到 128 KB | 通常分为 L1I 和 L1D |
| L2 Cache | 每个核私有或少量核共享 |    数百 KB 到数 MB | 比 L1 大，但更慢     |
| L3 / LLC | 多核共享        |    数 MB 到数十 MB | 缓存跨核共享数据       |
| DRAM     | 整个处理器共享     |           GB 级 | 容量大，延迟高        |

> [!note] coding 题：单线程 CPU 上实现矩阵乘 C=A×B，A 为 row-major、B 为 column-major，N 维远大于 M 和 K。如何优化？
>
> **问题分析**：朴素 i→j→k 三重循环中，B 是 column-major，固定 k 沿 j 访问时步长为 K（cache miss 密集）；N 很大意味着 B 的列数多，这个问题最突出。A 是 row-major，沿 k 连续，访问友好。优化目标：**提高 B 的访存局部性 + 提高寄存器复用**。
>
> **循环顺序 i → j-block → k**：调整为 j 在外、k 在内，每次同时持有 NR 个 `C[i,j]` 的累加器（NR = register block，如 4、8）。同一个 `A[i,k]` 对 NR 个 j 都有贡献，只需 load 一次，寄存器复用率提高 NR 倍：
>
> ```cpp
> for (int i = 0; i < M; ++i) {
>     for (int jj = 0; jj < N; jj += NR) {   // 外层：j 方向按 NR 分块
>         float acc[NR] = {0};                // C[i, jj..jj+NR-1] 的寄存器累加器
>
>         for (int k = 0; k < K; ++k) {
>             float a = A[i * K + k];         // A[i,k]：row-major，沿 k 连续，load 一次
>             for (int jr = 0; jr < NR; ++jr)
>                 acc[jr] += a * B[(jj + jr) * K + k]; // 朴素：B 仍 col-major，不连续
>         }
>
>         for (int jr = 0; jr < NR; ++jr)
>             C[i * N + jj + jr] = acc[jr];  // 写回 C（row-major，连续）
>     }
> }
> ```
>
> **Pack B**：上面 `B[(jj+jr)*K + k]` 固定 k、遍历 jr 时步长为 K，cache miss 密集。解法：在对每个 j-block 计算前，先把 `B[:, jj:jj+BN]` 重新打包为 k-major、j-contiguous 的小矩阵 `B_pack`，之后内层沿 j 访问连续，可向量化：
>
> ```cpp
> float B_pack[K * BN];  // 打包缓冲区，固定 k 时 j 连续
>
> for (int jj = 0; jj < N; jj += BN) {
>     int bn = min(BN, N - jj);
>
>     // --- Step 1: Pack B[:, jj:jj+bn] ---
>     // 原布局 B[k][j] = B[k + j*K]，固定 k 遍历 j 步长为 K（不连续）
>     // 打包后 B_pack[k][j] = B_pack[k*bn + j]，固定 k 遍历 j 步长为 1（连续）
>     for (int k = 0; k < K; ++k)
>         for (int j = 0; j < bn; ++j)
>             B_pack[k * bn + j] = B[k + (jj + j) * K];
>
>     // --- Step 2: 计算 C[:, jj:jj+bn]，使用 B_pack ---
>     for (int i = 0; i < M; ++i) {
>         for (int k = 0; k < K; ++k) {
>             float a = A[i * K + k];             // A[i,k]，寄存器复用
>             float* bp = &B_pack[k * bn];        // B_pack 这一行：j 连续
>             float* cp = &C[i * N + jj];         // C 对应行：j 连续
>
>             // 内层：bp 和 cp 都连续，编译器/手写可 SIMD
>             for (int j = 0; j < bn; ++j)
>                 cp[j] += a * bp[j];
>         }
>     }
> }
> ```
>
> 整体结构：**遍历 j 的 cache block → Pack B block（一次拷贝）→ 遍历 i → 遍历 k → 沿 j SIMD**。Pack 代价 O(KN)，收益是后续所有 M 行的计算都走连续访存。


**Q：GPU 的存储结构？**
- 所有常驻线程共享寄存器文件，寄存器文件属于整个 SM
- shared memroy 每个 CTA 私有，线程间共享，程序显式管理
- L1 Cache 是每个 SM 私有，硬件自动管理
- L2 Cache 是整个 GPU 共享，支持原子操作，跨 SM 共享
- **目的** 通过大量 Warp 隐藏延迟，不看单次访存。强调数据并行、重用、访存合并。

| 层级                  | 归属                       | 特点          |
| ------------------- | ------------------------ | ----------- |
| Register            | 每个线程私有                   | 最快，但容量有限    |
| Shared Memory       | 每个 Thread Block / CTA 共享 | 程序员显式管理     |
| L1 Cache            | 每个 SM 私有                 | 自动缓存全局内存访问  |
| L2 Cache            | 全 GPU 共享                 | 所有 SM 共享    |
| Global Memory / HBM | 全 GPU 共享                 | 容量大、带宽高、延迟高 |


**Q：CUDA Graph 和 Persistent Kernel 的关系？**

- CUDA Graph 管的是 Kernel 之间的调度。把一串 Kernel launch、依赖关系和参数记录成图，后续直接 replay，主要*降低CPU launch overhead*、调度开销、CUDA Driver 提交开销、kernel 之间的空隙。
- Persistent Kernel 管的是单个 Kernel 内部的任务调度。主要降低小任务调度开销、降低不规则任务的均衡负载、降低 CTA 反复创建和初始化的开销、kernel launch 开销。


**Q：Shared Memory 设计原则**
1. 不适合使用 shared memory 的情况：数据只使用一次、线程之间没有复用、数据量太大、shared memory 搬运和同步成本大于复用收益、global memory 访存已经合并（global memory一次读取一个 cached line，一个线程读的本来就是连续对齐的 global memory，这样只需要很少的内存事务就能完成一批数据读取，地址分散就需要分别发起独立内存读取事务）
2. 设计流程：a. 确定线程块处理的 tile；b. tile 越大，数据复用越高，但shared memory占用也越大，每个 SM 可驻留 CTA 下降；c. 确定线程如何协同加载，一个 warp 的访问尽量合并；d. 设计 shared memory 布局，避免冲突、满足 Tensor Core 指令布局、满足向量化加载、量化的话通常要求地址至少 16 字节对齐；e. Shared Memory 需要围绕复用次数设计。
3. 只在 warp 内通信的话，可能不需要 CTA 级同步。


**Q：shared memory bank conflict **

smem 上的 bank 布局：

```
                          Bank
地址轮次    0       1       2       ...    31
------------------------------------------------
第 0 轮   smem[0]  smem[1]  smem[2] ... smem[31]
第 1 轮  smem[32] smem[33] smem[34] ... smem[63]
第 2 轮  smem[64] smem[65] smem[66] ... smem[95]
```

- 如图，shared memory 的 bank 映射是按“地址对 32 取模”来循环分配的。
- 如果只读 `smem[0]~smem[31]` 的话不会产生 bank 冲突，而且能 32 个线程并行访问。但读 `smem[0]` 和 `smem[32]` 就会bank conflict，因为都读的是 bank0（的不同地址）。一个 bank 内，一次读写的地址数量有限。
- 寄存器也可能有 bank conflict，但是通常编译器会做分配和调度，程序员通常不能直接指定变量放到哪个物理寄存器。常见解法是改写指令顺序、减少依赖、改变数据布局。
- 两个线程访问同一个地址通常可以 broadcast。
- half、float、double 的 bank conflict 可能不一样，因为每个线程访问的字节数不同，一个元素可能覆盖一个或多个 bank。
- 可以通过 Swizzle（XOR）地址重排分散 bank 访问。也可以 padding 增加 stride 来处理二维矩阵 conflict 问题，但是 swizzle 可以更灵活，因为还要满足地址对齐（例如对齐到 32 的倍数、使用`ldmatrix`等）

**Q：ILP 和 TLP 有什么区别？**
- TLP，Thread-Level Parallelism：通过更多线程或 warp 隐藏延迟
- ILP，Instruction-Level Parallelism：同一个线程或 warp 内存在多个独立指令，可以并行推进。比如几个乘法，互相不依赖，可并行，ILP 高；存在长依赖链，ILP 低。高 ILP 可能 occupency 低也性能很好。

**Q：断言和分支的区别？**

简单条件可能被编译成断言（断言不会跳转），条件路径较长的话会形成分支，太长的话会让大量线程执行无效指令。

#### 端侧相关问题

**Q: Systolic Array 是什么？**
 - **1 个线程** 整个计算阵列由一条指令流或 command stream 控制，不采用 GPU 那种几千个 CUDA thread 的编程模型。
 - **多个计算单元执行相同计算** 但阵列内部并不是只有一个计算单元，而是有大量并行的 PE 或 MAC 单元。硬件自动将矩阵切成 tile，然后送入整个 PE Array。
 - **为什么适合端侧芯片？** 它的数据可以在相邻 PE 之间复用，不需要每做一次乘法都重新访问 SRAM 或 DRAM，因此能耗低、控制逻辑简单，适合卷积和矩阵乘等规则计算。
 - **和 CUDA 的区别？** 
	 - CUDA 用大量线程驱动 GPU 并行计算，NPU 的 Array 用少量指令控制大量硬件并行计算。Array 不需要有完整的线程管理，不需要独立调度 PE 
	 - **优缺点：** 控制简单、能效高。但灵活性较差，遇到不规则 shape、稀疏访问或复杂控制流时利用率可能下降。

**SP 序列并行**
作用于：
- LayerNorm 输入激活
- Dropout、Residual 等非张量并行区域的激活显存
- 训练时的中间激活存储

**EP，Expert Parallelism**
- MoE 单层内部，按专家切分参数

**TP，张量并行**
-  QKV Projection 按列切（每张卡拿到完整 head 可独立计算）、Output Projection 按行切（每张卡只拥有 head 对应的 hidden dim）
- All-Reduce 合并结果

**PP，Pipeline Parallelism**
- 缺点：流水线气泡
- 缓解手段：一个 batch 切成多个 micro-batch，但由于**前向和反向之间存在全局依赖顺序**，仍然无法完全消除气泡，就是一开始 fill 和最后反向的几个 micro-batch 会有部分 stage 空闲

> 例子：BLOOM-176B 使用 Megatron-DeepSpeed，主体依靠张量并行 + 流水线并行

**DP： ZeRO/FSDP（全切分数据并行）**

| ZeRO Stage | 切分内容 | 单卡显存（相对未切分） | 例子 | 
| --- | --- | --- | --- | 
| Stage 1 | 仅优化器状态（如 Adam 的 $m, v$） | 优化器状态部分降为 $1/N$ | LORA | 
| Stage 2（FSDP: SHARD_GRAD_OP） | 优化器状态 + 梯度 | 上述两项都降为 $1/N$ |  8×A100 上微调 7B~13B 级别模型 | 
| Stage 3 （FSDP: FULL_SHARD）| 优化器状态 + 梯度 + 模型参数 | 三项均降为 $1/N$ |  数十张 GPU，Vicuna-65B、LLaMA-65B/70B 微调，==1000+GB 显存== | 

- 传递内容：完整参数分片（All-Gather）、梯度（Reduce-Scatter）
- FSDP 按照 unit 识别子模块，比如 transformer block；zero-3 由 deepspeed-engine 统一管理
- DeepSpeed 的 cpu offload 支持的层级（NVMe）更丰富； ZeRO-Offload / ZeRO-Infinity（支持 NVMe）
- DeepSpeed 与 Megatron-LM 的官方集成 更成熟


**并行 transformer block**
- Attn 和 FFN 读同一个 Norm(x) 并行计算
$$
y=x+\operatorname{Attention}(\operatorname{Norm}(x))
 +\operatorname{FFN}(\operatorname{Norm}(x))
$$
- 改变了模型结构，可能影响模型质量
- 可以由单张 GPU 上的不同 kernel 或 stream 执行（只表示可并发，不保证实际更快）
- 可以拼接 attn 的 qkv proj 和 ffn 的 up proj  组成大 GEMM，但是 weight 变宽【宽度过大也可能增加权重读取、临时输出、寄存器压力和后续重排成本】
- 只融合 Q、K、V；融合 SwiGLU 的 gate projection 与 up projection 更常见
- 代表工作：PaLM、GPT-J

#### 各种分离

**AF 分离**（Attn 和 FFN 分离）
- Attn：依赖 KV Cache，通信和显存访问压力较大
- FFN：主要是大规模 GEMM，计算密集
- RPC 或高速互连传输 hidden states

**PD 分离**（Prefill 和 Decode 分离）
- *核心问题*： Prompt 很短、KV 很大、网络较慢时，传输收益可能覆盖不了开销
- *隐藏传输开销*：==KV 分块传输==、计算 / 传输 / Decode ==调度重叠==
- KV Cache 怎么传输？==点对点数据传输==
	- 同节点：NVLink 或 GPU P2P
	- 跨节点：GPUDirect RDMA ：直接从一张 GPU 显存写入另一张 GPU 显存，避免经过 CPU 内存
	- 使用 PagedAttention 的话还要传 block table，否则无法正确寻址

> **NCCL 和 RDMA 是什么关系？** RDMA 是底层远程内存访问能力，NCCL 是 GPU 集合通信库。NCCL 可以基于 NVLink、PCIe 或 InfiniBand/RDMA。

> [!NOTE] 什么时候不用 PD 分离？
> 1. 输入很短，Prefill 本身很快，拆分后的调度和传输成本反而占主导。
> 2. KV Cache 很大但网络带宽不足，例如跨节点网络较慢。
> 3. 请求并发低，单机本身没有明显的 Prefill 和 Decode 干扰。
> 4. 模型很小，GPU 利用率本身较低，分离增加的系统复杂度大于收益。
> 5. 业务对首 token 延迟极其敏感，而 KV 传输位于 Prefill 和 Decode 的关键路径上。


**VL 模型分离**

- Vision 节点：==只执行一次。== 运行图像或视频 Encoder、视觉 Token 压缩、Projector
- Language 节点：==持续多步。== 运行 LLM Prefill 和 Decode
- VL 分离后，LLM 部分仍可继续做 P/D 分离

上述所有分离方式：

**Q：分离标准？**  看计算特征、显存占用、执行频率、资源需求和通信量

**Q：分离收益？** 独立扩缩容、减少资源相互干扰、提升 batching 效率、异构硬件部署

**Q：代价？** 跨节点通信、状态管理、调度复杂度、故障恢复和负载不均衡

#### **设计一个支持 Continuous Batching、Paged KV Cache 和 Speculative Decoding 的 LLM 推理引擎**

1. 前端接收请求并进入 waiting queue
2. PD 分离
	1. Prefill 与 Decode 的执行比例： Scheduler 根据 token budget 和显存容量决定  
	2. Prefill 和 Decode 分别形成执行 batch
		- 长 Prompt 使用 Chunked Prefill，避免阻塞 Decode
3. PagedAttention
	1. KV Cache 使用固定 block 分配和 block table 映射
		- 减少动态序列带来的外部碎片
		- 固定大小物理 block 管理 KV：KV pool 一般预分配，避免频繁 cudaMalloc
		- Block table、sequence length 等元数据应放在 GPU，避免 kernel 中访问 CPU
4. Continuous Batching
	- 每个 Decode step 后更新请求状态并重组 batch
5. Speculative decoding
	1. 先由 draft model 生成候选 token
	2. Target model 批量验证并更新 KV
	3. 临时 KV 使用 commit 和 rollback 机制管理
	4. 完成请求释放 block，未完成请求继续调度
6. 图执行层
	1. 为常见 batch size 预准备 CUDA Graph
	2. 通过固定 slot 和静态 buffer 保持地址稳定；将稳定部分静态化，将动态部分参数化
7. 显存不足时
	1. Scheduler 根据重计算成本和传输成本选择等待、抢占、swap（offload 到 cpu DRAM） 或 recompute kv
	2. 延迟新请求
	3. 暂停部分运行中的请求，释放其 KV block
8. 整体设计原则
	1. 在 TTFT、TPOT 和 P99 SLA 约束下最大化有效 token 吞吐
	2. 保证显存状态和请求状态一致

#### KV Cache 可以怎么压缩

> KV 压缩不仅影响显存，还会改变 Attention Kernel 的数据类型、反量化开销和访存模式，因此必须看端到端吞吐，而不能只看压缩率。

1. KV 量化，例如 FP16 到 FP8、INT8、INT4
	- 难点：1️⃣ K 和 V 对误差的敏感性不同，K channel-wise 量化（outlier），V token-wise 量化（softmax 是 tok 维度加权聚合，不同 token 的 V 动态范围可能差异较大）
2. Token Drop （eviction），只保留重要历史 token
3. GQA、MQA
4. Low-rank compression （MLA）
	- Q、K 沿 hidden_dim 维度拆成两部分，不做 RoPE 是为了==不需要显式恢复完整的 K 矩阵==，直接把 K 的上投影乘给 q（吸收）；如果做了 RoPE 的话就没法用结合律吸收上投影
	- ![[Pasted image 20260715221357.png|500]]
	- partial RoPE：RoPE 不一定要作用于全部 head dimension 才能表示位置
5. Prefix deduplication 共享前缀
6. 跨层共享或层选择
7. 稀疏 Attention 与 KV 裁剪
8. 分层存储和按需加载
9. 分布式 KV Store
	1. *Cache hit rate* 高不等于系统性能一定好，还要看*命中的 KV 是否足够大*，以及*传输成本*

#### Speculative Decoding 问题

- 标准 rejection sampling 版本在算法正确实现时，不改变 target model 的输出分布。某些工程近似方法可能牺牲严格一致性换取速度。
- 不同 Speculative 方法
	- 小模型 Draft：接受前缀中与大模型分布一致的 token
	- Medusa，多预测头，每个头负责预测未来不同位置的 token
	- EAGLE，预测 hidden states 得到 token -> hidden state 包含的信息比离散 token 更丰富，一般接受率更高
	- Tree-based speculation：保留多个可能分支，主模型通过 tree attention 同时验证多条路径
	- N-gram speculation：直接复制可能的后续 token 作为草稿（代码、重复文本和固定模板）
	- Self-speculative decoding：草稿阶段跳过部分 Transformer 层、提前退出

#### 框架推理问题

**Q：指标解释**
- 吞吐和延迟：更大的 batch 能提高 GEMM 效率和吞吐，但会提高延迟（TTFT 和 TPOT 可能变差）
- TTFT：排队时间、Prefill 时间、Prefix Cache 命中、调度策略
- TPOT：batch size、KV 长度、Attention 访存、GPU 利用率

**Q：vllm 为什么不用 PagedAttention 了？**
1. KV Cache 管理层仍然是 paged 的：通过 block table 将每个 sequence 的逻辑 token 映射到物理块。【这块需要会写 python】
2. PagedAttention 被替换为 FlashAttention，但其实FlashAttention本身也支持了 Paged *-> 所以其实只是换了 kernel backend，本质原理没换*。换 kernel 的原因：
	- 早期 paged_attention_v1/v2 主要针对单 token decode，性能不佳
	- FlashAttention 持续对新 n 卡优化，新技术跟进快（例如 FP8 KV、MLA、稀疏 attention 等）==但不一定在所有场景都比 Pagedattn 快==
	- 新的 FlashAttention feature：
		1. 更好的 memory coalescing：线程映射设计更好。vllm 对布局做了向量化，并不是随机访存，但是线程布局和 cache layout 比较固定。
		2. Q-stationary + k 和 v tile 会同时与多行计算：Q 的一小块可以在 CTA 的整个 KV 循环期间保持在 register / smem 中 + GQA 跨 query head 合并
		3. 根据 tile 大小控制数据的实际复用次数：本质是根据 head dimension、dtype 和shared memory 容量设置 Block size (B_q 和 B_k)
		4. 更好的流水线：在Hopper上，Q/K/V tile 的异步搬运、WGMMA、非矩阵运算，由不同 warp 负责，==重叠读写、矩阵乘和非矩阵运算==。

**Q：推理框架选择**
- vLLM：模型生态和通用性优先，它的开源 feature 倾向是*尽快支持新模型*，通常是新模型上线的默认起点，接入成本低。
- SGLang：*复杂请求复用和大规模执行*效率优先。风险是某些组合的成熟度可能不均匀
	- **请求结构** RadixAttention，组织跨请求的前缀 KV Cache，擅长：多轮对话、Agent、RAG 等前缀高度重复的任务、RL rollout
	- **缓存命中** HiCache：多层级 kv cache 管理
	- **分布式拓扑** 激进的分布式方案（PD分离、DP、EP）
	- 热门模型和特定 workload 有端到端性能优化
- TensorRT-LLM：完整优化链。但只面向 NVIDIA、自定义算子、动态模型结构和非标准 attention 的接入成本。
	- 优先使用 Hopper、Blackwell 等 NVIDIA 新硬件能力（FP8、NVFP4、MXFP4 等 NVIDIA 数据路径）
	- 通过编译、kernel specialization 和 CUDA Graph 获得稳定性能
	- 面向固定模型、固定集群的生产部署

**新模型部署时的选择原则**
- 模型结构是否原生支持
- 实际 workload 任务
- 是否频繁修改 runtime：例如需要开发新的 attention、KV Cache、推测解码或调度算法，则 vllm 或 sglang

#### 量化相关

**Q：非对称量化为什么快？**
- 非对称量化的整数值里需要减去 zero-point，做矩阵乘法时必须把它减掉。
- 真正由 Tensor Core 或整数 MMA 高效计算的只有QxQw 乘法。
- 其他的向量矩阵乘、向量向量乘 需要额外计算 Query/Activation 的行和、Weight 的列和，再做加减和广播。

假设浮点矩阵近似为：

$$
X \approx s_x(Q_x-z_x),\qquad W \approx s_w(Q_w-z_w)
$$

那么：

$$
XW \approx s_xs_w(Q_x-z_x)(Q_w-z_w)
$$

展开得到：

$$
XW \approx s_xs_w\left(Q_xQ_w-z_wQ_x-z_xQ_w+Kz_xz_w\right)
$$

其中 $K$ 是矩阵乘法的 reduction dimension。

这里真正由 Tensor Core 或整数 MMA 高效计算的只有：

$$
Q_xQ_w
$$

剩下三项都是 **zero-point correction**：

$$
-z_wQ_x,\qquad -z_xQ_w,\qquad Kz_xz_w
$$

它们需要额外计算 Query/Activation 的行和、Weight 的列和，再做加减和广播。

**Q：Kimi K2 到 K3 从 int4 转向 mxfp 数制的原因？效率和 accuracy 上的 tradeoff 他们是怎么考虑的？**

|        | K2 Thinking                  | K3                                                       |
| ------ | ---------------------------- | -------------------------------------------------------- |
| 权重     | 对称 INT4，group size 32        | MXFP4，group size 32                                      |
| 激活     | 不量化，BF16/FP16                | Expert 输入使用 MXFP8                                        |
| 量化范围   | MoE Expert 权重                | MoE Expert 权重和输入激活                                       |
| QAT 阶段 | **只在 Post-training** 阶段             | 从 **SFT 开始**，贯穿 SFT 和 RL                                     |
| 主要目标   | 主要解决 decode 时的权重带宽                    | 同时降低带宽并提高低精度 GEMM 算力                                     |
| 混精   | Attention、Shared Expert 等高精度 | Attention、LatentMoE Projection、Shared Expert、Router 等高精度 |

> 对于分布规则、group 很小、经过 QAT 的静态权重，INT4 的均匀量化可能同样好，甚至局部误差更小。

**Q：mxfp8一级 scale，nvfp4 两级 scale，为什么？**
1. MXFP8 的 scale 是 E8M0 的，加上 FP8 的 exponent 的部分，基本上能够等于 FP32 的 exponent，也就是表示范围基本覆盖。
2. NVFP4 的 scale 是 E4M3，FP4本身是E2M1，不能覆盖原始  FP32 tensor 数值范围。因此有一个 per-tensor global scale，主要是因为它只负责提供一个全局指数基准，细粒度的点已经由 NVFP4 自己的 scale 支持了。
	- NVFP4 的分布式 all-gather 要求数据使用一致的 global scale。
	-  Transformer Engine 当前提供了 row-scaled activation 变体，每行保存一个 FP32 amax，但收益有限。per-block 更没必要。

**Q：MLA 如何做量化？key 和 value 是同一个 tensor，但是 key 和 value 的最优量化粒度（规约维度）不同，如何解决这个冲突？**

**矛盾点**
- K 用于 $QK^\top$，量化误差会直接影响 attention logit，通常更关注 channel 间的幅值差异
- V 用于 $PV$，误差沿 token 维被 attention probability 加权累积，通常更适合 per-token 量化
- 同一份 latent 要*同时服务* QK 和 PV，无法让 K、V 分别使用完全独立的最优量化表示

**常见做法：Per-Token-Head-Tile-128**

`step 1` 以 $C\in\mathbb{R}^{N\times512}$ 为例：每个 token 沿 channel 切成4个 128-dim block，每个 block 单独量化、保存一个 scale：

$$
c_{t,g}\approx s_{t,g}\hat{c}_{t,g},\qquad g=0,1,2,3
$$

`step 2` 同一份近似 latent $\tilde c_{t,g}=s_{t,g}\hat c_{t,g}$ 同时用于两条路径：

$$
\operatorname{score}_t\approx\sum_gs_{t,g}(q_g^\top\hat c_{t,g}),\qquad
o_g\approx\sum_t p_t s_{t,g}\hat c_{t,g}
$$

**规约维度**
- *QK*：在 head dim 维度 reduction。所以在算 QK 的时候，每个 block 是 128 的 dim 这个尺寸去算底层的 int8 的 GEMM，然后再把 query scale 左乘（对输出矩阵按行缩放），key scale 右乘（对输出矩阵按列缩放）就可以。*-> 最终得到 FP32 的 attn score (即 P)* 【这里必须把 P 变成 FP32 的，因为 score 的计算就是 online softmax 的步骤，必须是 Float32 的计算】 
- *PV*：在 token 维度 reduction
	- **prefill 阶段** value 先dequant，然后 scale 可以和 value 乘，在数学上完全等价。因为 prefill 阶段一个 value tile 反量化之后可能被多个 query 一起用，所以算完 scale 的 value tile 可以复用给整个 query tile。
		- 但如果说 query token 比较少（query tile 的 block size 比较小），可能还是倾向于 scale 先和 P 乘（就是下面的这个方案）
	- **decode 阶段** 倾向于Scale 先和 P 相乘，得到 FP32 的结果（*可能*会再转成 FP16）。value（在 cache 中是 INT8）会先被 dequant 到 FP16/FP32，然后 PV 再做浮点GEMV。因为在 decode 阶段 query=1，所以先和 P 乘的话只需乘一次，计算量比较小。


**为什么不分别量化 K 和 V ？**
1. 保存两份量化结果：可以分别优化 QK、PV 误差，但相当于保存两份 KV Cache
2. 共享 INT8 值、只保存两套 scale ：更省空间，但增加 scale 存储和 kernel/layout 复杂度；并且*同一组整数值无法同时对两套 scale 都最优*
3. 因此实际采用一份 block-quantized latent，在缓存占用、kernel 复杂度和精度之间折中。

**底层效率**
1. *算子融合* scale 读取和反量化融合到 attn kernel 中，直接读 INT8，先完成 online softmax（包括 PV 相乘），再把结果反量化到 BF16
2. 以 512-dim INT8 latent、每 128-dim 一个 FP32 scale 为例：latent 为 512 Bytes，scale 为 16 Bytes，scale 额外开销约 $3.125\%$；仍显著小于原始 BF16 latent 的 1024 Bytes。

**Q：如果要做 KV 的 4bit 量化的话，会怎么做**
- key 是 per-channel-group 量化，v 是 per-token-group 量化。
- 追求算子效率时使用对称 INT4，否则非对称。
- sliding window，保留一部分高精度token
- 将反量化融合进 Attention 内核 
- group size = 32 和 64 更常用，128 偏效率


**Q：Delayed scaling**

- FP8 训练 的时候用之前的a_max 预测当前 scale，有滞后性
- NVFP4 训练用随机 hadamard 处理 outlier，对 gradient 使用 stochastic rounding，因为一直确定性四舍五入会让小梯度反复舍入为零，产生系统性偏差。随机舍入使量化值在期望意义上满足：
$$
E[Q(x)]=x
$$
它不能减小方差，但可以避免长期有偏更新。
- 对 weight 使用二维 scaling，因为前向反向的分块边界会改变

#### Post-Train 问题

**Q：训推不一致的原因**

**同权重训推不一致原因（大多是 infra 层面）：**

1. SGLang 和 Megatron 算子实现不同
	- SGLang 的 attn 是 flash attn, paged attn, 或融合 QKV-RoPE attn，Megatron 是 Transformer Engine 的 fused attention，存在 softmax 分块方式、规约顺序、中间精度不同  *-> 差异可能明显*
	- RMSNorm、SwiGLU、cross-entropy、log-softmax 可能融合/未融合
	- 浮点加法不满足结合律、Softmax 对接近的 logits 比较敏感
2. 并行方式不同
	- 训练是 TP=8 + PP=8 + EP=16，rollout 是 TP=16 + EP=8；不同 TP 切分会改变累加/归约顺序 
3. 精度配置不同 
	- rollout GEMM/KV Cache  FP8 ，训练是 BF16  *-> 差异可能明显* 
4. 批处理和缓存路径，例如 continuous batching、Paged KV Cache、prefix cache，不保证 bitwise identical
5. Top-k expert（MoE）、topk token （采样），随后误差被放大  *-> 差异可能明显* 

**不同权重训推不一致原因（大多是 RL 策略层面）：**
1. 异步造成的 policy staleness ，比同权重数值差异更系统性、更严重

**Q：为什么 OPD 没有大规模取代 off-policy distillation**
1. off-policy 可以先生成一批答案后反复训练学生，OPD 在线教师推理，成本高，可能成为瓶颈
	- 解决方法：小教师 or 多级教师、只在高价值 token、步骤或轨迹上调用教师
2. 教师 logits 的通信和存储
	- 解决方法：只保存 teacher top-k logits、只蒸馏关键前缀（已有工作发现 OPD 信号可能集中在输出前缀）、高带宽互联师生模型
3. 严格 on-policy 是：student rollout → teacher inference → student update，三个步骤严格先后依赖，很难高效流水
	- 解决方法：teacher inference 与 student rollout 流水化、近似 OPD 的 two-step off-policy
4. 训练初期学生生成内容可能低质量，不值得学习
	- 解决方法：通常先 off-policy 冷启动，让学生和教师思维模式差不多，再 OPD、只在有价值轨迹和步骤用 teacher logits 监督（Reward-Gated OPD）、师生差异过大时降低监督（SOD）、只在教师监督可靠的区域 OPD（Trust-region OPD，TrOPD）、分难度、成功轨迹优先
5. 教师和学生的 reasoning pattern 可能差很多：高熵 token 可能有多个下一步都正确，也可能教师自己不确定
	- 解决方法：高熵 token 降低蒸馏权重、高 KL 区域 mask、gradient clipping、仅蒸馏 top-k
	- TrOPD 明确研究了在可靠区域做 OPD，在 outlier 区域采用 clipping、masking 或 forward-KL，并通过 teacher prefix 把学生引导回可靠区域。
6. 主要传递教师已有能力，不直接优化任务奖励。教师监督并不等于正确性。这一点 off-policy 也存在，没有本质区别。

#### 指标含义

**Q：ROUGE-L （DA-KD 纯语言指令跟随 task）**

ROUGE-L 是‌基于最长公共子序列（LCS）计算的文本生成任务评估分数‌，以‌F1 值‌为核心结果，*衡量生成文本与参考文本在‌词序保持和内容覆盖‌上的重合程度*，取值范围 ‌[0, 1]‌，越接近 1 表示质量越高 。‌‌

- ‌含义‌："L"代表 Longest Common Subsequence（最长公共子序列），不要求词语连续匹配，但必须保持相对顺序一致；
- ‌计算逻辑‌：先统计生成文本与参考文本的 LCS 长度，据此算出‌精确率（P）‌和‌召回率（R）‌，算为F1 分数‌作为最终 ROUGE-L 得分；部分实现默认偏重召回率（设β极大），但标准用法通常取β=1 平衡 P 与 R；
- ‌应用场景‌：广泛用于机器摘要、机器翻译、大模型生成等任务的自动评测，能反映句子级结构保留能力；
- ‌局限‌：仅依赖单一最长子序列，忽略其他潜在匹配路径，且对同义词、语义等价不敏感。‌‌

**Q：VBench 上的指标有哪些**

*VBench-1.0（基础版，16 个维度）* 主要评估“表面真实性”，分为==视频质量==与==条件一致性==两类：
- 视频质量类：成像质量 (Imaging Quality)、美学评分 (Aesthetic Quality)、运动平滑度 (Motion Smoothness)、动态幅度 (Dynamic Degree)、时序闪烁 (Temporal Flickering)
- 条件一致性类：主体一致性 (Subject Consistency)、背景一致性 (Background Consistency)、文本一致性 (Text Alignment)、物体类别 (Object Class)、多物体生成 (Multiple Objects)、人类动作 (Human Action)、色彩 (Color)、空间关系 (Spatial Relationship)、场景 (Scene)、时序风格 (Temporal Style)、外观风格 (Appearance Style)、整体一致性 (Overall Consistency) 

*VBench-2.0（进阶版，5 大维度/18 项细粒度能力）* 聚焦“内在保真度”，新增物理、常识、人体结构等==深层认知评估==：
1. 人体保真度 (Human Fidelity)：解剖结构正确性、动作连贯性、身份/衣物跨帧一致性
2. 可控性 (Controllability)：相机运动遵循度、实体位置精准度、复杂指令执行力
3. 创造性 (Creativity)：场景组合想象力、情节拓展能力、构图多样性
4. 物理规律 (Physics)：重力/浮力/碰撞模拟、力学状态变化合理性、材料形变真实性
5. 常识推理 (Commonsense)：因果逻辑合理性、运动合理性 (Motion Plausibility)、实例存续稳定性 

*VBench++（扩展版，16 维 + 新任务/新属性）* 在保留 VBench-1.0 核心 16 维基础上，增加==图生视频任务、任务泛化与安全评估==：
- 任务扩展：支持图像到视频 (I2V) 评测，引入自适应图像套件 (Image Suite)
- 新增维度：可信度 (Trustworthiness)，涵盖跨文化一致性、偏见检测、内容安全性
- 核心保留：仍沿用 16 个基础技术指标作为质量底座，但评估流程更适配多模态输入 

注：VBench-2.0 与 VBench++ 指标体系不直接互通。具体榜单数据可查阅 [HuggingFace VBench Leaderboard](https://huggingface.co/spaces/Vchitect/VBench_Leaderboard)。
