> [!abstract] 核心思想
> 用小模型（Draft Model）串行生成 $\gamma$ 个候选 Token，大模型（Target Model）**一次并行验证**，在严格采样算法下保持目标模型输出分布不变，利用 GPU memory-bound 的特性提升吞吐。


#### [Q16] 投机采样为什么在理论上完全无损？

> [!abstract] 无损的含义
> 输出序列的分布与"只用 Target Model 自回归采样"**完全一致**：Sampling 下是逐位分布一致（统计上不可区分），Greedy 下是逐 Token 完全一致。这里的"无损"指的是**分布无损**，不是每次采样结果相同。

**naive 版本（Chen et al., 2023 原始算法，单步视角）**

1. Draft 从 $q(x)$ 采样一个候选 Token $x$
2. 以概率 $a(x) = \min\!\left(1,\ \dfrac{p(x)}{q(x)}\right)$ 接受 $x$
3. 若被拒绝，从修正分布重新采样：
   $$p_{\text{res}}(x) = \frac{\max(0,\ p(x) - q(x))}{\sum_y \max(0,\ p(y) - q(y))}$$

**核心证明（为什么边缘分布精确等于 $p$）**

$$
\begin{aligned}
P(\text{out} = x) &= \underbrace{q(x)\cdot a(x)}_{\text{直接接受}} + \underbrace{\sum_y q(y)\big(1 - a(y)\big)}_{\text{拒绝总概率 } Z} \cdot p_{\text{res}}(x) \\
&= \min(q(x), p(x)) + Z \cdot \frac{\max(0, p(x) - q(x))}{Z} \\
&= \min(q(x), p(x)) + \max(0, p(x) - q(x)) = p(x) \quad \checkmark
\end{aligned}
$$

关键恒等式：$Z = \sum_y q(y)\big(1 - a(y)\big) = \sum_y \max(0, q(y) - p(y)) = \sum_y \max(0, p(y) - q(y)) = 1 - \sum_y \min(p(y), q(y))$（由 $\sum q = \sum p = 1$）。

**核心直觉（面试表述）**

- 这是**精确的接受-拒绝采样（rejection sampling）**，不是近似：Draft 负责"提出"，Target 的接受规则负责"纠偏"，两步合起来的边际分布恒等于 $p$。
- **$q$ 与 $p$ 差多远只影响接受率（效率），完全不影响正确性**。Draft 再差，输出分布依然是 $p$ —— 这就是"无损"的含义。
- 直觉：$q > p$ 的 Token 被按比例随机拒绝（把多出的频率还给残差分布）；$q < p$ 的 Token 接受率 $= 1$，不足的部分由残差分布补足。

**扩展到完整序列（归纳）**

验证第 $i$ 个位置时，接受/拒绝全部基于**已接受的公共前缀**，即第 $i$ 步使用 $p_i(\cdot \mid \text{prefix}_i)$ 与 $q_i(\cdot \mid \text{prefix}_i)$。由归纳法：前缀的分布已等于 Target 的条件分布，当前步的输出分布又等于 $p_i(\cdot \mid \text{prefix}_i)$，因此整条序列与 Target 独立自回归采样**不可区分**。Bonus Token 直接从 $p$ 采样，天然来自正确分布。

> [!tip] 与工程实现的关系
> 工程实现（如 vLLM）通常写成"逐位置 $\min(1, p_i(d_i)/q_i(d_i))$ 接受，第一个拒绝位置从 $p_{\text{res}}$ 重采样"，与 naive 版本（几何停止 + 重采样）在数学上完全等价。

#### [Q17] 投机采样真正减少的是计算吗？

**不是。投机采样不减少 FLOPs，总计算量反而增加。**

| 额外开销 | 说明 |
|---|---|
| Draft 阶段 | 每轮串行生成 $\gamma$ 个 Token 的完整前向 |
| Verification 阶段 | Target 的 $q\_len$ 从 1 变成 $\gamma + 1$，Attention / MLP / LM Head 的计算同步放大 |
| 拒绝浪费 | 被拒绝 Token 的验证计算完全浪费 |
| 系统开销 | 额外 KV 预留、树管理、Compaction、调度状态 |

**真正减少的是：**

1. **权重从 HBM 读取的次数（内存带宽压力）**：Decode 是 memory-bound，每步瓶颈是把权重从 HBM 搬到片上。Verification 一次 Forward 服务 $\gamma + 1$ 个 Token、权重只读一次 → 每个 Token 摊到的权重读取量下降，arithmetic intensity 提高。
2. **串行步数 / 墙钟延迟（wall-clock latency）**：原本 $\gamma + 1$ 次串行 Decode 才能产生的 Token，现在 1 轮完成，TPOT / ITL 显著下降。
3. **Target Model 调用次数**：同样多的输出 Token，Target Forward 次数从 $N$ 次降到约 $N / (\gamma + 1)$ 次（接受率 1 的理想情况）。

**本质：以算力换带宽、以并行换串行。**

适用边界（呼应 Q3 / Q6）：

- 只有 GPU 处于 **memory-bound（低 QPS、小 Batch）** 时，多出的 FLOPs 才能被空闲算力隐藏，墙钟时间才真正下降；
- Batch 增大、GPU 进入 **compute-bound** 后，额外 FLOPs 无处隐藏，投机采样反而变慢（高 QPS 下通常关闭投机）。

> [!tip] 面试表述
> 先纠正问题本身："投机采样不减计算，FLOPs 是增加的；它优化的是 memory-bound 场景下的**墙钟时间 / 每 Token 延迟**——通过减少权重读取次数和串行步数实现，本质是**以算力换带宽、以并行换串行**。"

#### [Q1] 自回归 Decode 为什么是 memory-bound？投机采样如何加速？

标准 Decode 每步只生成 1 个 Token，但需要读取大模型大部分权重。单 Token GEMM 的 $M$ 很小，计算密度低，GPU 大量时间花在从 HBM 读权重，而非 Tensor Core 计算。

投机采样的改进：

- Draft Model 串行生成 $[d_1, d_2, \ldots, d_\gamma]$
- Target Model **一次 Forward** 验证全部候选
- 同一批权重服务多个 Query Token → 提高 arithmetic intensity
- 减少生成相同 Token 数所需的 Target Model 调用次数

---

#### [Q2] Verification 一次处理多个 Token，为什么比 Target 连续跑多次快？

Verification 本质是小 $q\_len$ 的多 Token Forward，权重只需加载一次；连续 Decode 需重复加载多次权重。Verification 仍比单 Token Decode 贵，但通常远小于多次单 Token Decode。

> [!note] 注意
> Verification 不是普通大 Batch Prefill，其特点是 $q\_len = \gamma,\ kv\_len \gg \gamma$，需专门优化 small-query attention。

#### [Q3] 什么时候投机采样不能加速（负优化场景）？

| 负优化原因 | 具体说明 |
|---|---|
| Draft Model 太大 | $\gamma T_d$ 过高，Proposal Cost 超过收益 |
| 接受率低 | 大量候选被拒绝，计算浪费 |
| Batch Size 已经很大 | 标准 Decode 已充分利用 GPU，进入 compute-bound |
| TP All-Reduce 开销 | 小 Draft Model 做 TP 时，通信比计算还贵 |
| 输出很短 | 初始化和调度开销无法摊销 |
| 高 QPS | 投机请求挤占其他请求的 Token Budget |
| Tree Attention 开销过高 | KV 回滚、Compaction 代价超过收益 |

> [!warning] 关键结论
> **接受率高 ≠ 性能一定好。** 优化目标是最大化端到端速度，而非最大化接受率。
> $$\max \frac{E[\text{accepted tokens per round}]}{T_{\text{draft}} + T_{\text{verify}} + T_{\text{overhead}}}$$

#### [Q4] Greedy 模式下如何保证输出分布不变？

Target Model 计算每个位置的预测 $t_i = \arg\max\, p_\theta(x_i \mid x_{<i})$，从左向右比较：

- $d_i = t_i$ → 接受
- 第一次不一致 → 拒绝该位置及后续，输出 Target 预测的修正 Token
- 全部接受 → 再输出一个 Bonus Token

```python
accepted = []
for i in range(gamma):
    target_token = target_logits[i].argmax()
    if draft_tokens[i] == target_token:
        accepted.append(draft_tokens[i])
    else:
        accepted.append(target_token)
        break
else:
    accepted.append(target_logits[gamma].argmax())
```

> [!question] 为什么不能跳过错误 Token 继续接受后面的？
> 后续 Draft Token 的条件上下文已经错误。$d_{i+1}$ 是基于错误的 $d_i$ 生成的，不能认为它来自正确条件分布。

#### [Q5] Sampling 模式下如何保证 Lossless 输出分布？

设 Draft 分布为 $q(x)$，Target 分布为 $p(x)$。

**接受概率：**
$$a(x) = \min\left(1, \frac{p(x)}{q(x)}\right)$$

> [!note] $q(x)$ 的口径
> 这里的 $q(x)$ 是 Draft 对**它实际采样出的那个 Token** 赋予的概率（$x \sim q$），不是最大概率 Token。实现中取 Draft Logits 中 $d_i$ 对应的概率即可，但归一化仍需要完整词表。

**拒绝后从残差分布采样（不能直接从 $p$ 采样！）：**
$$p_{\text{res}}(x) = \frac{\max(0, p(x) - q(x))}{\sum_y \max(0, p(y) - q(y))}$$

最终输出 Token 的边缘分布严格等于 $p$。

> [!danger] 为什么拒绝后不能直接从 Target $p$ 采样？
> 接受-拒绝的本质是**精确修正 $q$ 与 $p$ 的偏差**。若拒绝后再从 $p$ 直接采样，输出分布会变成
> $$P(x) = \underbrace{\min(q(x), p(x))}_{\text{直接接受路径}} + \Big(1 - \sum_y \min(q(y), p(y))\Big) \cdot p(x)$$
> $p(x)$ 在两条路径中被重复计入，$q(x) \ll p(x)$ 的 Token 会被过度采样，结果 $\neq p$。
> 例：$p = 0.6/0.4,\ q = 0.9/0.1$ 时，"cat" 的频率会变成 $0.6 + 0.3 \times 0.6 = 0.78 \neq 0.6$。
> 只有从修正分布 $p_{\text{res}}$ 采样，才能把"多出的概率"精确补偿回去。

> [!warning] 工程陷阱：Logits Processor 必须逐位置正确对齐
> 以下 Processor 很容易出错，必须按"前缀 + 前面已提出的 Draft Token"逐位置计算：
> - repetition penalty / no-repeat n-gram
> - grammar constraint / bad words
> - min length / position-dependent logits processor

#### [Q6] 投机采样的性能如何建模？

**每轮生成的期望 Token 数**（设每位置条件接受率均为 $\alpha$）：
$$E[L] = \frac{1 - \alpha^{\gamma+1}}{1 - \alpha} \qquad (\alpha \to 1 \text{ 时 } \to \gamma + 1)$$

> [!note] 公式口径
> 这个 $E[L]$ **包含最后一个 Bonus Token**（Bonus 位置直接由 Target 采样，无条件生成）。若只数被接受的 Draft Token，期望是 $\dfrac{\alpha(1 - \alpha^\gamma)}{1 - \alpha}$。面试时把口径说清楚即可。

**近似加速比：**
$$S \approx \frac{E[L] \cdot T_t(1)}{\gamma \cdot T_d(1) + T_v(\gamma) + T_o}$$

其中 $T_t(1)$ 为 Target 单 Token Decode 延迟，$T_d(1)$ 为 Draft 单步延迟，$T_v(\gamma)$ 为一次验证延迟。**memory-bound 下 $T_v(\gamma) \ll \gamma \cdot T_t(1)$（权重只读一次）**，这是加速的根本来源。

**低 QPS vs 高 QPS 的差异：**

- **低 QPS**：Target Decode Batch 小，明显 memory-bound，投机采样可显著提高 arithmetic intensity → 同时改善延迟和吞吐
- **高 QPS**：Continuous Batching 已充分聚合请求，GPU 利用率高，额外 FLOPs 和 KV 开销得不偿失 → 可能负优化

> [!tip] 面试表述
> vLLM 将 speculative decoding 定位于**中低 QPS、memory-bound 场景**的延迟优化。

#### [Q7] 不同投机采样方法有哪些，各有什么特点？

**独立 Draft Model（原始方法）**

- ✅ 不修改 Target Model；严格保持目标分布；可独立训练
- ❌ 需额外模型权重和 KV Cache；Draft 阶段仍串行；TP 通信可能成瓶颈
- 选型核心指标：$\frac{\text{accepted tokens}}{\text{draft latency} + \text{verification latency}}$，而非参数量

**Medusa**

多个预测头附加在 Target Model 上，组成候选树，用 Tree Attention 一次验证。

- 需 Tree Attention Mask；候选压平为一段 Token；Verification 后选最长接受路径
- 静态树过大会浪费 Verification 计算

> [!question] Medusa 为什么不能预测一条准确的 Token 链？
> 各 Head 基于同一 Backbone Hidden State 预测不同未来位置，缺少完整自回归依赖，需 Top-k 分支和树验证覆盖不确定性。

**EAGLE / EAGLE-2**

EAGLE 预测接近 Target 顶层的 **Hidden Feature**（而非直接预测 Token），结合提前一位的 Token 信息。EAGLE-2 根据 Draft 置信度动态构造候选树。

- ✅ Feature 预测比 Token 预测更容易匹配 Target
- ❌ 需提取中间层 Hidden State，框架耦合强；动态树使 CUDA Graph 管理更复杂

**MTP（Multi-Token Prediction）**

训练时加入多个未来 Token 的预测目标，推理时将 MTP Module 作为轻量 Draft。DeepSeek-V3 使用此策略。与 Medusa 区别：MTP 有更强顺序依赖；Medusa 通常是附加独立/弱依赖预测头。

**N-gram / Prompt Lookup**

在 Prompt 或已有输出中寻找重复 N-gram，后续 Token 作为候选。Draft Cost 几乎为零，但泛化有限，适合代码补全、文档摘要、文本改写等任务。

**Self-speculative Decoding**

同一模型用浅层提前退出/跳层作为 Draft，完整模型作 Target。共享部分参数，无需额外完整模型，但 Draft 和 Verification 对同一模型资源存在依赖，实现复杂。

#### [Q8] 投机采样如何与调度器和 Continuous Batching 集成？

**调度器状态扩展：**

```python
RequestState:
    committed_seq_len      # 已确认提交的序列长度
    speculative_seq_len    # 投机阶段的暂定长度
    draft_tokens           # Draft Token 列表
    draft_probs            # Draft 各位置概率
    accepted_count         # 本轮接受数
    draft_kv_blocks        # Draft KV 的 Block Table
    target_kv_blocks       # Target KV 的 Block Table
    phase                  # DRAFT or VERIFY
```

**Token Budget 计算：** 投机请求一次 Verification 消耗 $q\_len = \gamma$ 个 Token。调度器需同时限制最大 Sequence 数、最大 Batched Token 数、可用 KV Blocks、CUDA Graph 支持的 Shape 以及 Prefill 和 Decode 优先级。

**与 Continuous Batching 的冲突：** 每个请求接受长度不同（如 A 接受 5 个、B 接受 1 个、C 接受 0 个），调度器必须：

1. 对不同请求执行独立 acceptance
2. 更新各自 committed length
3. 回收被拒绝 Token 对应的 KV Slot
4. 对输出 Token 做 Compaction
5. 保持每个 Request 的 RNG 和 Sampling State 独立

**Prefill 与投机 Decode 冲突：** 高负载下投机 Decode 消耗多个 Token Budget，可能阻塞新请求 Prefill，导致 TTFT 恶化。常见策略：限制每轮最大 speculative tokens；根据负载动态减小 $\gamma$；高 QPS 时关闭投机；根据 SLO、Batch Size、GPU 利用率动态切换模式。

> [!tip] 面试表述
> 投机采样不是全局静态开关，而应该是**负载感知的调度策略**。

#### [Q9] Draft 和 Target 的 KV Cache 能共享吗？如何提交和回滚？

**不能共享。** 两者的 Hidden Size、Head 数、层数和权重都不同，K/V Tensor 无法共享（Token ID 可共享）。

**Target Verification 产生的 KV 如何提交？**

假设 Draft Token 为 $[d_1, d_2, d_3, d_4]$，若 $d_1, d_2$ 被接受，$d_3$ 被拒绝：

- $d_1, d_2$ 对应 Target KV 有效 → 提交
- $d_3, d_4$ 对应 Target KV 无效 → 回滚
- 修正 Token $c_3$ 的 KV 需要在**下一轮 Forward** 中计算

| 实现方式 | 优点 | 缺点 |
|---|---|---|
| 预留后回滚 | 实现简单 | 可能产生短暂 KV 峰值和碎片 |
| 临时区后提交 | 隔离性好 | 提交逻辑复杂 |

**Block 内部只接受一部分怎么办？** 不能释放整个 Block（Block 中可能有历史有效 Token）。只需修改 Sequence Length 和 Block Metadata，不需要清零物理显存，新 Token 可直接覆盖无效区域。

#### [Q10] Acceptance Kernel 在 GPU 上如何实现？Sampling 模式为什么需要随机数？

**Greedy 模式**是完全确定性的，只看 argmax 是否一致：

```python
accept = (draft_token[i] == target_logits[i].argmax())
```

**Sampling 模式**不能只看"logits 够不够大"，原因是 Sampling 的目标是让输出 Token 的**频率分布**等于 $p(x)$，而不是每次输出概率最大的那个。

举例说明：假设 Target 分布 $p(\text{"cat"}) = 0.6,\ p(\text{"dog"}) = 0.4$，但 Draft 过于自信 $q(\text{"cat"}) = 0.9,\ q(\text{"dog"}) = 0.1$。Draft 采样到了 "cat"。若直接因为 $p(\text{"cat"}) = 0.6$ 够大就接受，那 "cat" 被接受的概率 ≈ 90%（Draft 采样到它的频率），**远超 Target 分布的 60%，输出分布已被污染**。

随机数的作用是**纠正 Draft 过度采样带来的频率偏差**：

$$a(\text{"cat"}) = \min\!\left(1,\ \frac{p(\text{"cat"})}{q(\text{"cat"})}\right) = \min\!\left(1,\ \frac{0.6}{0.9}\right) = 0.67$$

最终 "cat" 出现的频率 $= 0.9 \times 0.67 = 0.6 = p(\text{"cat"})\ \checkmark$（被拒绝时从残差分布采样，本例 $p_{\text{res}}$ 只支持 "dog"，故 "dog" 频率 $= 0.1 \times 1 + 0.3 \times 1 = 0.4\ \checkmark$）

随机数 $u \sim \text{Uniform}(0,1)$ 用于执行伯努利试验：$u < a(x)$ 则接受。$p > q$ 时（Draft 低估了 Target），直接接受；$p < q$ 时（Draft 高估了 Target），随机拒绝一部分，把多余的频率"还给"残差分布。

> [!tip] 一句话总结
> Greedy 关心「哪个 Token 最大」→ 确定性比较。Sampling 关心「按正确**频率**输出每个 Token」→ 必须用随机数纠偏。

**完整 Kernel 流程：**

```python
ratio = target_prob / draft_prob                      # [B, gamma]
ratio = torch.clamp(ratio, max=1.0)                   # min(1, p/q)

u = torch.rand_like(ratio)                            # GPU 上生成，避免 D2H 同步
accept_mask = u < ratio                               # [B, gamma]，True = 接受

# cumprod 一旦遇到 0，后面全变 0，对应第一个 reject 之后全部无效
cumulative = accept_mask.cumprod(dim=1)               # [[T,T,F,T],...] → [[1,1,0,0],...]
accepted_lengths = cumulative.sum(dim=1)              # 每个 Request 实际接受数
```

GPU 上执行：读取 Draft Token 和对应的 $p(d_i)$、$q(d_i)$，生成随机数（cuRAND），用 `cumprod` / Warp ballot / Prefix scan 找每个 Request 第一个 reject 位置，Compact 输出 Token，更新 Sequence Metadata。

**Verification Attention 特点：** $q\_len = \gamma$，$kv\_len \gg \gamma$。需要 Paged Attention + 局部 Causal Mask 组合；Tree Draft 需要 Tree Attention Mask（子节点看到祖先，不看兄弟分支）。

#### [Q11] LM Head 是否是瓶颈？如何优化？

> [!warning] 常见误解
> "只提取 Draft Token 对应的 $p(d_i)$"**不代表只计算一个词的 Logit**。对于严格无损的 speculative sampling，得到归一化概率 $p(d_i)$ 仍然需要全词表的归一化因子（LogSumExp）。

LM Head 的 Shape 是小 $M$、大 $N$ 的 $[\gamma, d] \times [d, V]$ GEMM。以 $V=128\text{K},\ d=4096,\ \gamma=4$ 为例，LM Head 权重（BF16）约 1 GiB，主要问题是：小 $M$ GEMM Tensor Core 利用率低 + 1 GiB 权重读取 = **memory-bound**，且 Softmax 和 Logits Processor 会二次读取 Logits。

**"仅提取 $p(d_i)$"到底省了什么？**

分子只需一个 Token 的 Logit，但分母 $\sum_u \exp(z_i(u))$ **依赖整个词表**。只计算 $W_{\text{lm}}[d_i]$ 这一行无法得到准确的 $p_i(d_i)$。真正节省的是：不保存 $[\gamma, V]$ Logits Tensor，不启动完整 Softmax Kernel，不把完整概率分布写回显存。

**优化方向：**

1. 不物化完整的 $[\gamma, V]$ Logits Tensor
2. 将 LM Head、LogSumExp、Acceptance 融合为一个 Kernel（在线 Softmax 融合）：

```
Fused: LM Head Tile + Online LogSumExp + Candidate Gather
→ 直接输出 log p_i(d_i)（每个位置一个标量）
```

3. 只在发生 Reject 的位置执行完整 Residual Sampling（延迟两阶段执行）
4. Greedy 模式不计算 Softmax，只计算 Argmax；TP 场景下每张 GPU 计算局部 Shard 的 MaxLoc，再执行 MaxLoc Reduction，完全不需要 All-Gather 完整 Logits

> [!warning] 避免 Softmax ≠ 避免完整 LM Head。为确认 Draft Token 是否是最大值，仍必须检查所有 Vocabulary Token。

**延迟 Residual Sampling（两阶段）：**

第一阶段只做 Acceptance，输出 `target_candidate_logprob: [B, γ]`（每位置一个标量），不保存 `target_probs: [B, γ, V]`。第二阶段只对第一个 Reject 位置计算残差分布 $p_{\text{res}}(v) = \frac{[p_r(v) - q_r(v)]_+}{\sum_u [p_r(u) - q_r(u)]_+}$，重算一行 LM Head，而非 $\gamma$ 个位置。

#### [Q12] CUDA Graph 如何处理投机采样的动态 Shape？

投机采样有大量动态 Shape（每请求 $\gamma$ 不同、Tree Size 不同、接受长度不同），CUDA Graph 直接 Capture 很困难。

常用方法：

- 固定最大 $\gamma$，不足部分 Padding
- 按 Batch Size 和 Draft Length 分桶，分别 Capture
- 使用固定地址的预分配 Buffer
- 将 accepted length 作为 Device Tensor（不走 CPU 控制流）
- 在 GPU 上完成 Prefix Scan、Compaction 和 KV Metadata 更新
- 罕见 Shape 回退 Eager Mode

> [!question] 为什么不能每次根据实际接受长度重新 Capture？
> Capture 本身有明显开销，且动态请求组合数量过多会导致 Graph Cache 爆炸。Graph 的意义是复用稳定执行路径。

#### [Q13] 分布式场景下有哪些特殊挑战？

**Draft Model 是否也做 Tensor Parallel？**

Draft Model 很小时使用高 TP Degree 会导致：通信占比迅速增大（All-Reduce 延迟不变，但计算很少）。可选设计：Draft 单卡、Target 多卡 TP；Draft 使用更小 TP Degree；使用 MTP/EAGLE 避免完整第二模型。

**Pipeline Parallel 的 Bubble 问题：**

Draft → Verify 存在顺序依赖，小 Verification Batch 在 PP 下容易造成严重 Pipeline Bubble。缓解方案：多请求 Interleaving、增大 Verification Batch、Microbatch Pipeline。

**MoE Target Model 的特殊问题：**

Verification 多 Token 输入时每个 Token 的 Expert 路由可能不同，导致 All-to-All Message Size 增大、被拒绝 Token 的 MoE 计算浪费、Draft 和 Target 路由行为差异大。但 Verification 增大每专家 Token 数，可能提高 Grouped GEMM 效率，实际影响取决于路由分布和 EP 通信占比。

#### [Q14] 如何正确衡量投机采样的性能？

| 指标 | 含义 |
|---|---|
| Acceptance Rate | 单个 Draft Token 被接受的比例 |
| Accepted Length | 每次 Verification 平均接受多少 Token |
| Target Calls per Output Token | 每生成一个 Token 需要多少次 Target Forward |
| Draft / Verification Latency | Proposal 和验证阶段耗时 |
| KV Waste | 被拒绝 Token 产生的无效 KV 和计算 |
| TTFT / TPOT / ITL | 首 Token 延迟 / 每输出 Token 延迟 / Token 间延迟 |
| P50/P99 | 在线服务尾延迟 |
| Goodput | 满足 SLO 的请求吞吐 |
| Reject Position Histogram | 通常在第几个 Token 拒绝 |
| HBM/SM Utilization | 是否仍然 memory-bound |

> [!warning] 正确 Benchmark 方法
> - 固定 Target Model、生成参数、输入输出长度分布、到达率
> - 分别测试低、中、高 QPS
> - 比较相同 SLO 下的 Goodput（不只是 tok/s）
> - 统计 Draft、Verify、Sampling、Scheduler 的**分项耗时**
> - Warmup CUDA Graph 和 Kernel 后再测

**高频面试追问：**

- Draft Model 越大越好吗？不是。大模型提高接受率，但也增加 Proposal Latency 和 KV Cache 开销。应最大化 $\frac{E[\text{accepted tokens}]}{T_{\text{draft}} + T_{\text{verify}} + T_{\text{overhead}}}$，而非接受率本身。
- $\gamma$ 越大越好吗？不是。增大 $\gamma$ 会增加 Draft 串行开销、Verification 计算、KV 预留和拒绝浪费。存在最优 $\gamma^*$，且随请求类型、负载、模型和硬件变化，应动态调整。
- 平均接受率相同，性能可能不同吗？会。`[5,5,0,0,0]` 和 `[2,2,2,2,2]` 虽均值相近，但 Verification Shape、KV 回滚量、Bonus Token 比例、调度 Batch 都不同。应看 accepted-length distribution，而非只有全局接受率。
- 量化 Draft Model 一定更快吗？不一定。缺少高效小 Batch 量化 Kernel、接受率因量化误差下降时，量化可能无益。

#### [Q15] Tree Attention Mask 如何实现？和 Radix Attention 有什么区别？

> [!note] 两者是完全独立的机制，经常被混淆
>
> | | Tree Attention Mask | Radix Attention (SGLang) |
> |---|---|---|
> | 作用域 | **单个请求内部** | **跨请求之间** |
> | 解决的问题 | 一次 Forward 验证候选 Token 树 | 不同请求共享相同前缀的 KV Cache |
> | 本质 | 自定义 Attention Mask | 前缀树结构的 KV Cache 管理 |

**为什么需要 Tree？**

Medusa / EAGLE 提出的不是一条线性的 $[d_1, d_2, d_3]$，而是一棵候选树。线性验证需要逐条路径跑 Target Forward；树状验证可以**一次 Forward 覆盖所有路径**，利用候选之间的共享前缀避免重复计算。

**Step 1：Flatten 树为线性序列**

按 DFS 或 BFS 顺序展平，同时记录每个节点的 parent 索引：

```
Flat:   [A, A1, A1a, A1b, A2, B, B1, B2]
Parent: [-1, 0, 1, 1, 0, -1, 5, 5]   # -1 表示直接挂在 context 上
```

**Step 2：构造 Attention Mask**

每个节点只能 attend 到完整的历史 KV Cache 以及自己在树中的祖先节点，不能 attend 到其他分支上的兄弟 / 表亲节点。

**Step 3：Position ID 按树深度而非 Flat 索引**

RoPE 是 position-dependent 的，**同一深度的节点共享相同 position ID**：

```
A, B            → pos = context_len
A1, A2, B1, B2  → pos = context_len + 1
A1a, A1b        → pos = context_len + 2
```

**Step 4：Verification 后选最长接受路径**

- Greedy：对每个节点，拿 Target logits 的 argmax 和该位置的 child Token 比较
- Sampling：对每个节点执行 acceptance sampling（和线性版相同的残差分布逻辑）
- 找从根到叶子的**最长连续接受链**，提交该路径的 KV，丢弃其余分支的 KV

**工程实现方案：**

标准 FlashAttention 只支持 causal mask，不支持任意稀疏 mask，需要特殊处理。

| 方案 | 实现方式 | 优缺点 |
|---|---|---|
| Additive bias | 不可 attend 的位置填 $-\infty$ | 实现简单，mask 内存开销 $O(\gamma^2)$ |
| 自定义 CUDA Kernel | 直接在 kernel 内部处理树结构 | 性能好，实现复杂 |
| Block sparse attention | 将树结构编码为 block-sparse pattern | 适合树结构规整的情况 |

> [!tip] vLLM 的做法
> vLLM 使用 additive attention bias，在 CPU 上构造 mask tensor，传给 attention kernel。动态树（EAGLE-2 风格）会导致 mask shape 每轮变化，需配合 Padding 或分桶策略兼容 CUDA Graph。
