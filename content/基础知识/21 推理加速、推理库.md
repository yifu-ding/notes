#### [Q1] do_sample 参数是什么？

- `do_sample=False`：确定性解码，对应 **greedy search**（每步取概率最高的 token）或 **beam search**（保留多个候选序列，按累积概率择优）。
- `do_sample=True`：随机采样解码，每步从概率分布中采样下一个 token，常用策略是 **top-k 采样** 或 **top-p（nucleus）采样**；此时不再使用 greedy/beam search。

#### [Q2] 大模型在 GPU 和 CPU 上推理速度如何？

以 **7B 量级** 模型为参考：

| 硬件 | 典型推理速度（decode 阶段） |
| --- | --- |
| 8 核 AMD CPU（llama.cpp） | ~10 token/s |
| 单卡 NVIDIA A6000（48 GB） | ~100 token/s |
| **GPU / CPU 比** | **≈ 10:1** |

**为什么 GPU 快这么多？**

自回归解码的瓶颈在于**内存带宽** 而非算术算力：每生成一个 token，需要把全部模型权重从显存/内存读到计算单元一遍。决定速度的核心指标是内存带宽：

- A6000 显存带宽：~768 GB/s
- 主流消费级 CPU 内存带宽：~50–100 GB/s（取决于 DDR4/DDR5 通道数）

带宽比约 8–15 倍，与实测 10:1 基本吻合。

> [!note] 大 batch 时情况不同
> decode 阶段（batch size = 1）几乎完全受内存带宽限制（memory-bound）。一旦 batch size 增大进入 prefill 阶段，算术强度提高，GPU 的 TFLOPS 优势才开始显现，此时 GPU/CPU 速度差会进一步拉大。

> [!tip] CPU 推理的适用场景
> CPU 推理（llama.cpp + GGUF）在以下场景仍有意义：单次低频推理、完全离线部署、极度资源受限的 edge 设备、或者模型小到 CPU 内存带宽不构成瓶颈时。

#### [Q3] 做了模型量化但推理速度仍然变慢，有哪些情况？

量化后速度不升反降是常见现象，主要有以下几种情况：

**情况 1：HuggingFace / bitsandbytes 的"伪量化"实现**

`bitsandbytes` 的 INT8/INT4 实现在推理时的实际路径是：

$$
\text{INT4 权重} \xrightarrow{\text{dequantize}} \text{FP16 权重} \xrightarrow{\text{GEMM}} \text{输出}
$$

模型权重存储在 INT4/INT8 节省显存，但 GEMM 计算本身仍在 FP16 下进行，**没有使用 INT8 算术单元** 。这样虽然减少了显存占用和权重加载的数据量，但如果模型较小、内存带宽不是瓶颈，反而因为多了 dequantize 步骤而变慢。

**情况 2：缺少底层量化算子（quantized kernel）支持**

真正快的 INT8 推理依赖 CUDA 中的 `INT8 GEMM` 算子（如 CUTLASS INT8、cuBLAS INT8）。这类算子对 GPU 型号有要求（Turing/Ampere 以上架构支持才好），且需要推理框架显式调用。如果框架没有集成这些内核，即便权重存成 INT8 也无法获得计算加速，最终仍回退到 FP16 计算路径。

**情况 3：Weight-Only 量化的本质目的是降带宽，不是加速**

GPTQ、AWQ、GGUF Q4_K_M 等 **weight-only 量化** 的核心动机是：

- **压缩模型体积**：4-bit 存储将 7B 模型从 ~14 GB（FP16）压缩到 ~4 GB
- **降低内存带宽压力**：decode 阶段每步加载权重的字节数减少 4× → 直接加速 memory-bound 的 decode

但是，这类量化**不量化 activations**，运算时仍需将权重 dequantize 回 FP16 再做乘加。因此：

| 场景 | 效果 |
| --- | --- |
| Decode（memory-bound，小 batch） | 通常有加速（带宽节省 > dequantize 开销） |
| Prefill（compute-bound，大 batch） | 可能持平甚至变慢 |
| 没有优化 kernel 的硬件/框架 | 大概率变慢 |

> [!summary] 一句话总结
> 量化后速度变慢，根本原因要么是**没有用到量化算术核**（仍走 FP16 GEMM），要么是 **dequantize 开销超过了带宽节省**，要么是场景本身不是 memory-bound 所以带宽优化无效。要真正加速需要选对量化格式、配合支持 INT8 GEMM 的 backend（如 ExLlamaV2、TensorRT-LLM、AutoGPTQ with Triton kernel）。

#### [Q4] Serving 与 Edge Deploy 两类场景的核心差异

| 维度 | Serving（服务端） | Edge Deploy（边端） |
| --- | --- | --- |
| 目标 | 高吞吐、多并发用户 | 低延迟、单用户、低资源占用 |
| 硬件假设 | 高端服务器 GPU（A100/H100/A6000） | 消费级 GPU、CPU、Apple Silicon、手机 |
| 批处理策略 | Continuous batching（动态批次） | 单请求或极小 batch |
| KV Cache 管理 | 复杂（PagedAttention 等） | 简单（无需跨请求共享） |
| 量化需求 | 可选（主要为省显存） | 必要（4-bit 才能在消费设备上跑） |

#### [Q5] 为什么两类场景使用的库不一样？

1. **批处理复杂度**：serving 需要 continuous batching（不同请求动态合并、不同序列长度混合）和 PagedAttention 解决 KV cache 内存碎片，这是 edge 单用户场景完全不需要的复杂度。

2. **硬件抽象层**：edge 库需要同时支持 CPU、Apple Metal、Android Vulkan、WebGPU 等碎片化硬件，故选择可移植的 C++（llama.cpp）或 TVM 编译（MLC-LLM）；serving 库可以假设 NVIDIA GPU，直接用 CUDA/TensorRT 深度优化。

3. **量化格式不同**：edge 侧的 GGUF 格式针对 CPU memory bandwidth 设计，支持混合精度按层量化；serving 侧的 AWQ/GPTQ/FP8 针对 GPU tensor core 利用率优化，两者格式和 kernel 实现完全不同。

4. **优化目标不同**：serving 优化** 吞吐量（tokens/s/GPU）**，edge 优化** 首 token 延迟（TTFT）和每 token 延迟（ITL）**，目标函数不同导致调度策略和 kernel 设计出发点就不一样。

> [!example] 典型选型
> - **API 服务（高并发）**：vLLM + A100，用 PagedAttention + continuous batching
> - **本地开发/测试**：Ollama（llama.cpp 封装），Q4_K_M 量化，M2 Mac 上 7B 约 40 token/s
> - **移动端/Web 端部署**：MLC-LLM，编译到 iOS/WebGPU
> - **消费级 GPU 极速推理**：ExLlamaV2，EXL2 格式 4-bit，RTX 3090 上 7B 约 150 token/s

#### [Q6] 如何准确衡量模型的推理速度？

衡量推理速度常用以下四个核心指标：

| 指标 | 全称 | 定义 |
| --- | --- | --- |
| **TTFT** | Time To First Token（首个词元生成时间） | 用户输入查询后，模型生成第一个输出 token 所需的时间，由处理 prompt（prefill）并生成首个输出 token 所驱动 |
| **TPOT** | Time Per Output Token（单个输出词元的生成时间） | 为每个用户生成一个输出 token 所需的时间，对应用户对模型“速度”的主观感知 |
| **时延（Latency）** | — | 模型为用户生成完整响应所需的总时间，可由前两个指标计算得出：`时延 = TTFT + TPOT × 待生成的词元数` |
| **吞吐量（Throughput）** | — | 推理服务器在所有用户和并发请求下，每秒可生成的输出 token 数 |

> [!note] TTFT 的适用场景
> 低时延首响应在**实时交互** 场景（如对话）中非常重要；在**离线批处理** 工作负载中则不太重要，因为用户不会逐字等待。

> [!tip] TPOT 与人类阅读速度的对比
> TPOT 为 100 ms/token 表示每个用户每秒可获得约 10 个 token，约合每分钟 450 个词，已远超普通人的阅读速度。TPOT 越低，用户感知的"打字机"输出越流畅。


> [!warning] 吞吐量与单 token 时延的权衡
> 提高并发（batch size）会拉高吞吐量，但会拉长单个用户的单 token 生成时间。例如同时处理 16 个用户的查询相比逐一处理：

| 处理方式 | 吞吐量 | 单用户 TPOT |
| --- | --- | --- |
| 依次处理（batch = 1） | 较低 | 较低（更快） |
| 并发处理（batch = 16） | 更高 | 更高（更慢） |

这与 [[21 推理加速、推理库#[Q2] 大模型在 GPU 和 CPU 上推理速度如何？\|Q2]] 中 decode 阶段 memory-bound、prefill/大 batch 阶段 compute-bound 的结论一致：batch 增大会把瓶颈从带宽逐渐转移到算力，从而推高吞吐量但拉长单请求时延。

#### [Q7] 当前优化模型最主要的技术手段有哪些？

模型优化不只是"把模型变小"，部署时通常要同时看四件事：**权重更小、每 token 计算更少、KV Cache/访存更省、GPU/集群利用率更高** 。一般可以分成算法、软件运行时、硬件系统三层理解，与 [[21 推理加速、推理库#[Q8] 推理加速框架有哪些？都有什么特点？\|Q8]] 的思路是一致的。

**1. 模型算法层面** 主要是直接减少参数、计算量和有效状态规模。最常见的是** 量化**，把权重、激活或 KV Cache 从 FP16/BF16 压到 INT8、INT4、FP8、FP4，常见配置有 W4A16、W8A8、FP8 等。部署里最常见的是 PTQ，典型方法包括 GPTQ、AWQ、SmoothQuant：GPTQ 更偏向逐层、基于二阶信息地压缩权重，AWQ 更关注保住少数对精度敏感的通道，SmoothQuant 则是把激活离群值“平滑”到权重里，方便落到更高效的 W8A8 kernel。QAT 也能做，但训练成本通常更高，所以大模型推理里还是 PTQ 更常见。

剪枝也是主力手段，但要区分清楚：**非结构化剪枝** 只是把一部分权重置零，压缩率高，却不一定能在通用 GPU 上换来真实提速；**结构化剪枝** 会直接删掉通道、attention head、FFN 维度、层或者 MoE expert，矩阵维度真的变小，才更容易得到显存、吞吐和延迟收益。像 SparseGPT 这类方法更适合做权重压缩本身，实际加速还要看硬件和稀疏 kernel 支不支持。

蒸馏、低秩分解和架构级优化通常是“把模型结构本身改轻”。蒸馏是让 student 学 teacher 的输出分布、中间特征或推理轨迹，适合做小模型、领域模型，或者给量化/剪枝后的模型补精度；低秩分解则是把大矩阵近似成两个更小矩阵的乘积，常见形式是 $W \approx UV$，其中 $r \ll \min(m, n)$；架构级优化则包括 GQA/MQA、稀疏注意力、滑窗注意力、线性注意力、早退和 MoE 路由。这里面尤其要记住：**MoE 只减少每 token 的活跃 FLOPs，不会自动减少总参数或显存**，所以常常还要配合专家剪枝、专家并行和路由优化。

> [!info] 和 [[21 推理加速、推理库#[Q3] 做了模型量化但推理速度仍然变慢，有哪些情况？\|Q3]] 的关系
> 低比特量化不一定等比例变快，decode 阶段常常卡在权重读取、KV Cache 访问和小 batch GEMM 上，所以必须有对应的 quantized kernel、权重打包格式和 runtime 配合。

**2. 软件与运行时层面** 重点是把“压缩后的模型”真正跑快。这里的关键不是再做一次算法压缩，而是减少 kernel launch、访存浪费和调度空转。常见手段包括：

- **计算图优化 / 模型编译**：算子融合、常量折叠、布局变换、内存复用、CUDA Graph、TensorRT、torch.compile。比如把若干逐元素操作融合成一个 kernel，能明显减少 launch 开销。
- **高性能算子**：FlashAttention、FlashInfer、fused RMSNorm / RoPE、量化 GEMM、MoE grouped GEMM。它们的作用是把注意力、归一化、位置编码、专家路由这些热点算子做成更少的内核调用和更少的 HBM 访问。
- **KV Cache 优化**：量化、分页、前缀复用、offload。对于自回归模型，长上下文和高并发时，KV Cache 往往比权重更先成为显存瓶颈；PagedAttention 就是把 KV Cache 切成块来减少碎片，prefix caching 则复用 system prompt、RAG 前缀或多轮对话里共享的前缀。
- **推理调度**：continuous batching、chunked prefill、prefill/decode 解耦、请求级 KV 路由、推测解码。这里的核心是让 prefill 和 decode 各自跑在更合适的资源上，减少空转，提高整体吞吐；推测解码则是先用 draft model 提多个 token，再由大模型验证，从而减少大模型逐 token 串行解码的次数。

这一层决定了算法层面的省算力，能不能真的转成 token/s 提升。很多时候，量化本身不是瓶颈，**有没有对应 kernel、KV Cache 管理是否合理、batch 是否组织得好**，才是最终速度差异的来源。

**3. 硬件与系统层面** 是让模型匹配真实硬件能力。这里主要看两类东西：一类是计算单元，另一类是存储和通信。

- **低精度数据格式与 Tensor Core**：FP16、BF16、INT8、FP8、FP4 都是为了把矩阵乘尽量落到硬件原生加速路径上。Hopper 的 H100 支持 FP8 Tensor Core，Blackwell 进一步引入 MXFP 格式，但能不能真快，还是取决于缩放、校准和 kernel 是否完整支持。（==面试有问到过 NVFP4 和 MXFP8 有什么区别==）
- **存储层次**：HBM 容量和带宽决定了权重、激活和 KV Cache 能不能顺畅访问；如果 HBM 不够，就只能考虑 CPU 内存甚至 SSD offload，但要靠预取和异步传输尽量藏掉延迟。
- **通信与并行**：NVLink、NVSwitch、InfiniBand 主要影响 tensor parallel、expert parallel、pipeline parallel 以及 KV Cache 跨卡/跨节点传输的成本。很多大模型不是“算不动”，而是“通信把收益吃掉了”。

这里还有一个常见误区：**FP8 不是“更稳的 INT8”** 。更准确地说，FP8 保留了浮点数的指数表示，动态范围比 INT8 更灵活，同时又能走专用 Tensor Core 路径，所以吞吐很高；但它的尾数位更少，通常仍要配合动态缩放、逐块缩放或者混合精度，敏感层也可能保留 BF16/FP16。（==面试考到手写量化反量化 FP8==）

按部署问题看，常见对应关系：**显存不够** 优先看 W4A16、AWQ、GPTQ、KV Cache 量化和 offload；**吞吐不够** 看 W8A8、FP8、FP4、量化 GEMM 和算子融合；**单请求延迟高** 看推测解码、CUDA Graph 和更小的 student；**长上下文爆显存** 看 GQA/MQA、PagedAttention 和 KV Cache 优化；**高并发吞吐低** 更多靠 batching、prefill/decode 调度和 prefix caching。

#### [Q8] 推理加速框架有哪些？都有什么特点？



| 层级 | 解决的问题 | 代表框架 |
| --- | --- | --- |
| 推理执行 / 服务引擎 | 模型执行、动态批处理、KV Cache 管理、并行推理、API 服务 | vLLM、SGLang、TensorRT-LLM、LMDeploy、TGI |
| 硬件专用编译 / 运行时 | 针对特定硬件做图优化、算子融合、量化执行 | llama.cpp、MLX-LM、ONNX Runtime GenAI、OpenVINO GenAI、MindIE |
| 大规模集群调度层 | Prefill/Decode 解耦、KV Cache 路由与跨节点传输、弹性扩缩容 | NVIDIA Dynamo |
| 底层算子库 | 高性能 GPU kernel，被上层框架调用，本身不是部署框架 | FlashAttention、FlashInfer、CUTLASS、Triton |

**第一层：推理执行 / 服务引擎**

| 框架 | 定位 | 核心特点 | 更适合的场景 |
| --- | --- | --- | --- |
| **vLLM** | 通用开源默认选择 | PagedAttention、continuous batching、chunked prefill、prefix caching、speculative decoding、多种量化与并行方式 | 新项目首选，模型类型多、要快速上线 |
| **SGLang** | 高性能 LLM/VLM/Agent 框架 | RadixAttention 前缀缓存、结构化输出、PD 解耦、MoE expert parallel、推测解码 | Agent、RAG、多轮共享前缀、MoE、RL rollout |
| **TensorRT-LLM** | NVIDIA 专用高性能 runtime | TensorRT 图优化、in-flight batching、paged KV cache、FP4/FP8/INT4、TP/PP/EP | 纯 NVIDIA 集群，追求极致性能 |
| **LMDeploy（TurboMind）** | 国产模型 / Ascend 友好 | persistent batch、blocked KV cache、TurboMind C++ backend | Qwen、InternLM、DeepSeek 等国内生态部署 |
| **TGI** | Hugging Face 早期服务框架 | continuous batching、TP、FlashAttention/PagedAttention | 存量 HF 项目维护，非新项目首选 |



**第二层：硬件专用编译 / 运行时**

| 框架 | 适合场景 |
| --- | --- |
| llama.cpp / MLX-LM | Mac、CPU、本地离线、显存不足的个人设备 |
| ONNX Runtime GenAI / OpenVINO GenAI | 跨平台工程集成、Intel 硬件、边缘端 |
| MindIE / vLLM-Ascend | 华为 Atlas / Ascend 集群、国产化部署 |


**第三层：大规模集群调度层**

**NVIDIA Dynamo** 不替代 vLLM / TensorRT-LLM，而是位于其上层的分布式控制平面，可接入多种 serving backend，核心做三件事：

- **Prefill/Decode 解耦**：把 prompt 编码和逐 token 解码分配到不同 GPU worker
- **KV cache-aware routing**：请求优先路由到已持有对应 prefix KV Cache 的 worker
- **KV Cache offloading / 跨节点传输**：在 GPU、CPU、磁盘或远端存储间管理与迁移 KV Cache

模型越大、上下文越长、并发越高，这一层的收益通常比单纯换个 kernel 更明显。

**第四层：底层算子库**

FlashInfer、FlashAttention、CUTLASS、Triton 等不是完整部署框架。做推理系统或 CUDA/Triton kernel 研究时通常会直接接触这一层。

#### [Q9]  推理加速框架在优化什么

| 优化点 | 解决的问题 | 典型机制 |
| --- | --- | --- |
| KV Cache 管理 | 长上下文/高并发下显存碎片、浪费 | PagedAttention、blocked KV cache、KV 量化 |
| 动态批处理 | 请求长度不一致，GPU 利用率低 | continuous batching、in-flight batching |
| Prefill/Decode 调度 | Prefill 计算密集、decode 带宽受限 | chunked prefill、SplitFuse、PD disaggregation |

| 推测解码 | decode 每步只生成一个 token，吞吐低 | draft model、EAGLE、MTP、n-gram speculation |
| 低比特推理 | 权重/KV Cache 占显存过大 | W4A16、W8A8、FP8、FP4、KV INT8/FP8 |

> - **MindIE / vLLM-Ascend**：Ascend NPU
>
> 没有绝对的"最快"框架：性能取决于模型结构、prompt/输出长度、batch、并发、KV Cache 命中率、量化格式、GPU 型号、是否 MoE/长上下文，以及 TTFT、TPOT、吞吐量三者的优化目标（见 [[21 推理加速、推理库#[Q6] 如何准确衡量模型的推理速度？\|Q6]]）。

#### [Q10] 大模型在 GPU 和 CPU 上推理速度如何？

大模型推理速度不能只看“芯片算力”或 TOPS，至少要先分清两段：**Prefill** 处理整段输入，主要受矩阵计算能力限制；**Decode** 逐 token 生成，主要受显存/内存带宽和 KV Cache 访问限制。也就是说，GPU 在 Prefill 阶段通常优势非常大，但在 batch=1 的 Decode 阶段，决定速度的往往不是 FLOPS，而是“每秒能从显存或内存搬运多少权重和 KV Cache”。

对于自回归生成，可以粗略理解为：

$$
\text{Decode TPS} \approx \frac{\text{有效内存带宽}}{\text{每生成一个 token 需要读取的权重和 KV Cache}}
$$

所以，**HBM 带宽、显存容量、KV Cache 管理、量化格式和推理框架**，往往比宣传页里的 NPU TOPS 更关键。

**1. GPU、CPU、NPU 的总体差异**

| 平台 | LLM 推理定位 | 优势 | 局限 |
| --- | --- | --- | --- |
| 数据中心 GPU | 高并发、大模型、长上下文 | HBM 带宽高、Tensor Core、并行能力强 | 成本高、功耗高、部署复杂 |
| 消费级 GPU | 本地 7B 到 32B 模型、轻量服务 | 性能高，软件生态成熟 | 显存通常只有 16GB 到 32GB |
| CPU | 小模型、低并发、CPU-only 服务、离线任务 | 内存容量大，成本低，部署简单 | Decode 通常明显慢于 GPU |
| APU / Apple Silicon | 本地大模型、统一内存部署 | 内存共享，能装下较大模型，功耗低 | 带宽仍远低于 HBM GPU |
| 手机 NPU / SoC | 端侧助手、小模型、语音、多模态特征 | 功耗极低，隐私好 | RAM、散热、框架支持限制明显 |

CPU 不是不能跑大模型。高端服务器 CPU 可以结合 AVX-512、AMX、INT8/INT4 kernel、speculative decoding 做推理；但这类结果通常是**高度优化后的集群吞吐**，不能直接等同于普通单机单请求速度。真正的差异仍然在带宽：EPYC 服务器最多是多通道 DDR5，Grace CPU 的 LPDDR5X 带宽约 546 GB/s，而数据中心 GPU 的 HBM3E 带宽则是数 TB/s 级别。

> **Prefill 看算力，Decode 看带宽。** 单请求生成阶段，GPU/CPU 的差距通常主要来自内存带宽和 KV Cache，而不是 TOPS 口径本身。

**2. 本地 GPU 的实际生成速度**

本地单卡推理里，7B 到 8B 量级模型的 decode 速度已经能比较直观地看出硬件差异。以 llama.cpp + Vulkan backend、Qwen3-8B-Q8_0、连续生成 128 token 的测试为例：

| GPU | 显存 | 生成速度 |
| --- | ---: | ---: |
| RTX 5090 | 32GB | 166.3 tokens/s |
| RTX 5080 | 16GB | 100.3 tokens/s |
| RTX 5070 | 12GB | 71.2 tokens/s |
| RX 9070 XT | 16GB | 68.4 tokens/s |
| RX 9070 | 16GB | 67.8 tokens/s |
| RTX 5060 Ti | 16GB | 50.2 tokens/s |
| RX 9060 XT | 16GB | 36.5 tokens/s |
| Intel Arc B580 | 12GB | 13.3 tokens/s |

这组测试里，RTX 5090 大约是 RTX 5060 Ti 的 3.3 倍，也是 RX 9070 XT 的约 2.4 倍。AMD RX 9070 XT 在 8B Q8 单流生成中接近 RTX 5070，但 NVIDIA 在 CUDA、TensorRT-LLM、vLLM、FlashInfer、量化 kernel 和服务部署生态上还是更成熟。

需要注意，这只是 **8B Q8 的 decode 速度** 。模型换成 32B、70B、MoE 或长上下文，结果会明显变化，因为显存容量、KV Cache、是否跨卡、量化方式都会变成新瓶颈。

**3. 当前数据中心 GPU 对比**

| 平台 | 当前代表芯片 | 关键参数 | 更适合的场景 |
| --- | --- | --- | --- |
| NVIDIA | Blackwell Ultra B300 / GB300 | 单 GPU 最高约 288GB HBM3E，NVFP4、FP8、强 NVLink/NVSwitch 互连 | 超大模型、长上下文、高并发、MoE、推理集群 |
| AMD | Instinct MI355X | 288GB HBM3E，8TB/s，FP4/FP6 支持，ROCm | 大模型服务、较高显存密度、开源软件栈 |
| 华为 | Ascend 950PR / 950DT | FP8/MXFP8/MXFP4，面向 Prefill 和 Decode 分工设计 | 国产化集群、昇腾软件栈、超节点部署 |
| NVIDIA 上一代 | H200 | 141GB HBM3E，4.8TB/s | 现有 Hopper 集群、成熟部署环境 |

**NVIDIA** 的 GB300 NVL72 是高端推理集群的重要代表，整机包含 72 张 Blackwell Ultra GPU 和 36 颗 Grace CPU，GPU 侧合计 20TB 高速显存、最高 576TB/s 显存带宽，并重点优化 FP4、注意力计算和大规模 NVLink 通信。

**AMD** 当前最直接的对手是 MI355X。单卡提供 288GB HBM3E 和 8TB/s 带宽，并支持 FP4/FP6。它更强的地方在于高显存密度和集群吞吐，单用户生成速度不一定完全等价于“TOPS 更高”。

**华为** 要把海思麒麟和昇腾分开看：麒麟是手机 SoC，适合端侧小模型；真正做数据中心大模型推理的是 Ascend。Ascend 950 系列明确区分 950PR 和 950DT，前者偏 Prefill 和推荐场景，后者偏 Decode 和训练，并支持 FP8、MXFP8、MXFP4。

> [!warning] 不要直接拿 TOPS 互比
> NVIDIA、AMD、Ascend 的公开 benchmark 往往不是同模型、同量化、同 batch、同上下文长度、同 SLA，因此不能简单说“某家芯片比另一家快几倍”。实际部署里，TensorRT-LLM、vLLM、SGLang、ROCm、CANN/MindIE 的成熟度差异，经常会放大或缩小硬件差距。

**4. 本地值得关注的芯片**

- **RTX 5090**：本地 LLM 推理最强的一档消费级 GPU，32GB 显存足够舒适运行 7B、14B、32B 的低比特模型；优势不只是算力，更是 CUDA、TensorRT-LLM、vLLM、FlashAttention、FP4/FP8、GPTQ/AWQ/EXL2/GGUF 路径都成熟。
- **AMD RX 9070 XT**：16GB 显存足以跑 7B 到 14B 量化模型，本地 llama.cpp/Vulkan 性能接近 RTX 5070，但 AMD 的重点优势还是数据中心 MI355X 和 ROCm 生态。
- **Ryzen AI Max+ 395**：APU 路线，核心价值不是绝对速度，而是** 统一内存容量**；可配置到 128GB 统一内存，并可把约 96GB 分给 GPU，适合本地跑 70B、120B 级低比特模型。
- **Apple M5 Max**：支持 128GB 统一内存和 614GB/s 带宽，适合 MLX、llama.cpp、LM Studio 等本地推理；它的优势是低噪声、低功耗、长时间交互稳定。

==面试有问最新 N 卡计算特性，做底层算子的话很可能会问==

**5. 手机 SoC / NPU**

手机 SoC 的 AI 能力主要面向语音助手、OCR、翻译、小模型和轻量 agent，不是完整 70B 或 120B 模型。Qualcomm、MediaTek、Intel PC NPU、华为麒麟这类平台更适合 1B 到 7B 的量化模型、语音和视觉小模型。

这里也要注意：NPU 标称的 “80 TOPS” 不等于能拿来跑任意大模型。原因通常有四个：

- 支持的算子和量化格式有限
- LLM Decode 更多受内存带宽和 KV Cache 限制
- 手机/PC 的内存容量有限
- 满载时会受温度和功耗墙限制
