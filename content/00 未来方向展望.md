### AI Infra 的未来发展

1. AI Infra 在整个 AI system 里的定位，可以比作操作系统在计算机系统中的位置，很多技术思想是一致的（下表列了一些一一对应）。过去操作系统做过怎样细粒度、全方位、极致优化到今天这个样子，未来 AI Infra 也会。
	1. **未来形态** 包括更动态、更细粒度流水线、更 task-specific、基于请求、更异构、灵活、软硬/云边端协同
	2. **历史规律** 有人会说，现在的推理框架都更加支持更规整的、可预测的推理时状态（比如模型形状固定、推理复杂度已知、计算图捕获后能复用，更少动态图，推理会更快）。当然是这样，原理上说这就是永恒不变的真理：规整性容易被转换为更高的利用率，可预测的计算通常比不可预测的计算更容易优化。但当前推理框架的舒适区受到当前基础设施发展现状的限制，包括算力限制、芯片架构限制、编译器设计等等，是当前阶段性的工程最优解，并不代表未来还是这样。在技术发展的历史中，很多“不可能”只是当时基础设施尚未成熟。今天一台机器可以同时维护成千上万个线程、连接和异步任务，Scaling也是算力、显存和分布式发展的产物，同样的，未来基础设施可能如何支持更动态的模型，这样未来的 AI 能同时处理大量动态任务，可能会有新的任务组织、管理方式，比如像操作系统管理进程一样，对 request 进行创建、暂停、恢复、调度、迁移和资源隔离。
	3. **目标区别：确定性调度 -> 决策** AI Infra 可以参考操作系统、网络和数据库的发展规律，但优化目标是不一样的。之前的目标比如是执行时间更短、recall 精度更高，这些任务可以用一些规则来评判结果正确性，标准更明确。但 AI 推理只能估计结果质量，而且很难精确估计单个请求。宏观上来说因为 AI 离人力更近，而人是更复杂的，不是仅用规则就能精确概括，所以 AI 也是一个决策系统。我们希望未来 AI 在训练的时候就涵盖这种决策路径的不确定性（这里的不确定性指的不是下一个 token 预测本身的不确定性，而是标准答案自身是不确定的）。现在其实也已经开始往这个方向做了，尤其是世界模型具身方向，但距离完全的决策驱动的系统还有一定距离。
2. 很多当今 Infra 涵盖的技术，比如训练后的压缩加速算法，会被转移到pretrain、SFT、RL中。越往上游移动，模型最终性能上限越高。其实本质优势有两点：训推一致和低成本做大模型。
	1. 但并不是完全移除训练后算法，因为 Infra 还包括下游的服务支持，下游 infra 团队需要负责更加特化的模型线上服务和并发推理。上游训练的时候可以考虑一部分能带来通用收益的技术，但不能把所有下游情况和需求都考虑进来，这会让上游目标混乱->不够纯粹追求AGI性能->性能不理想。
	2. 目前没这么做是因为：1. 带推理优化算法（例如压缩）的 pretrain 会比当前训练更不容易收敛，训练迭代周期更长；2.  要低成本做大模型需要做训练高效，架构设计难度比单纯做推理高效更大；3. 没有足够成本去验证架构创新收益有多大，多数公司的生存是先保证产品和市场，都不能承担试错风险。公司需要考虑成本收益和产品迭代，每个公司愿景和生存方式不同。ds 是例外，因为他有量化，同理有钱有卡的公司更有可能去做这些尝试。
	3. 把压缩加速技术往上游也是为了低成本，在坚持 Scaling 的前提下，用更少资源完成相同规模的训练和推理。
3. Harness 级训推一致。Agentic Harness 是多个模型组成的推理系统，也是当前 AI 系统的范式。
	1.  **发展趋势** 第三条Scaling曲线（Andrew在WAIC讲过）：GPT-3 更多参数，DS R1 更长推理token，现在是*更多模型组成一个系统，更多模型之间的协作带来更高智能上限*
	2. **需要 Infra 做什么支持**
		1. 动态任务图调度：任务数量和依赖关系事先未知，调度器需要支持动态队列管理。
		2. 异构模型路由：多模型组合在一个系统中，Router 要根据任务类型、延迟预算、成本和当前负载选择模型，支持模型fallback 和级联。
		3. 资源调度分配：多请求并发时的资源额度管理、工具调用额度、子 agent 数量上限、任务级公平调度、抢占...
		4. 面向 Agent 的 Continuous Batching：seed 已经用了流式 data buffer 和 trainer 异步的生产消费者队列
		5. 上下文、KV Cache 和状态管理：多 Agent 共享上下文前缀（Prefix Cache）、子 Agent fork 父 Agent 上下文、多级存储 KV Cache、状态恢复、上下文压缩...
		6. 工具运行时与沙箱：需要做容器或轻量 VM 隔离； CPU、内存、网络和执行时间限制； 权限控制； Secret 管理； 幂等调用； 工具超时和重试； 结构化 Observation； 工具结果缓存。*-> 模型推理快不代表系统快，很多 Agent 的主要延迟来自浏览器、代码执行和外部 API。*
		7. 状态一致性：多 agent 并发时修改同一份文件需避免互相覆盖


### 具体QA


**Q：什么是 AI infra**

支撑 AI 模型从数据处理、大规模分布式训练到高并发推理、线上服务全生命周期的软硬件协同系统工程。在于硬件感知与成本约束，核心目标是提升GPU利用率、优化显存并降低推理成本。

AI Infra 是一个多层协同的系统体系：

| 层级      | 主要内容                                        | 典型问题                       |
| ------- | ------------------------------------------- | -------------------------- |
| 物理资源层   | GPU、NPU、HBM、CPU、网络、存储、电力、散热                 | 如何构建高带宽、高可靠、低功耗的算力集群       |
| 系统软件层   | CUDA、通信库、编译器、算子、运行时、资源调度                    | 如何让模型高效使用硬件                |
| 训练与后训练层 | 数据加载、并行训练、Checkpoint、RL Rollout、容错恢复        | 如何提升训练 goodput，降低训练时间和故障损失 |
| 推理服务层   | Batching、KV Cache、路由、Prefill/Decode、并行、弹性伸缩 | 如何满足 TTFT、TPOT、吞吐和成本 SLO   |
| 平台与运维层  | 部署、监控、Profiling、评测、数据血缘、安全、故障诊断             | 如何让 AI 系统稳定、可观测、可迭代        |


**Q：操作系统和 AI Infra 的对应思想**

==本质上就是把操作系统的资源管理思想，迁移到 AI 模型、加速器和分布式状态上==

| 操作系统概念     | AI Infra 中的对应物                          |
| ---------- | --------------------------------------- |
| 进程、线程      | 请求、会话、Agent 任务、Rollout                  |
| CPU 调度     | GPU 请求调度、Batching、Prefill/Decode 调度     |
| 虚拟内存       | KV Cache 虚拟化、Paged Attention            |
| 页面换入换出     | KV 在 HBM、DRAM、SSD 间迁移                   |
| 内存分配器      | KV Block、Activation、Workspace 分配        |
| 缓存系统       | Prefix Cache、Feature Cache、Expert Cache |
| 抢占         | 暂停长请求，保存状态，让高优请求先执行                     |
| 上下文切换      | 切换不同请求或不同模型的执行状态                        |
| NUMA 感知    | GPU 拓扑、NVLink、PCIe、跨节点拓扑感知              |
| 资源隔离       | 多租户显存、算力、带宽隔离                           |
| 公平调度       | 不同用户、会话和优先级之间的公平性                       |
| Checkpoint | 训练状态、Agent 状态、长会话状态恢复                   |
| 文件系统       | 模型权重、Checkpoint、数据集和缓存管理                |
| 设备驱动       | CUDA、NCCL、通信后端、加速器 Runtime              |


**Q：未来具体研究点**

==关键词：动态、细粒度、task-specific、无损、端侧、持续学习==（可参考 deepseek v4、kimi k3 等新发布模型 feature 寻找规律，但每个厂的愿景和目的不同，不能直接 copy 别人的技术）

1. **动态弹性** 强化学习，导致思维链长度不等，计算图不固定。未来的 Infra 必须具备极强的动态弹性。
2. **云-边-端协同** 端侧需要实现 低延迟、低功耗的动作执行与环境感知，并在本地完成轻量级模型微调。
3. **自动算子编写/优化**  根据想要的功能，自动反向设计最适合该算法的虚拟芯片架构，或自动生成定制化的高性能算子 
4. **状态管理与长短期记忆**
5. **Agent 级算力调度** 类似于时间片概念


未来可以研究：


**有状态推理：** 
- 跨请求和跨会话的 KV Cache 复用

- HBM、DRAM、SSD、远端内存的多级缓存
- Agent 工作流感知的请求路由
- 长会话的抢占、恢复与迁移
- Prefix、Encoder Feature、Tool Result 的联合缓存
- Session 级公平性和资源隔离


**推理阶段多级解耦：**
- 阶段级拆分和独立扩缩容
- 异构设备放置
- 中间状态缓存
- DAG 感知调度
- 流式流水线执行
- 跨模型动态批处理
- 请求级和组件级容错

**RL 和后训练：**
- Rollout 和 Training 的资源比例如何动态调整

- 权重如何高效广播

- Verifier 如何批处理和调度

- KV Cache 与 Expert 参数的联合调度
- 远端 GPU Memory Pool
- 基于未来访问预测的 Prefetch
- 显存碎片与动态内存整理
- 跨节点零拷贝传输
