
**HRBP 面** 看是否匹配团队，通常会问：
- 为什么选这个团队/方向
- Offer、薪资预期、地点、入职时间
- 其他公司进展
- 职业规划、稳定性
- 性格、沟通、团队协作
- 有时也会进一步确认职级、人才计划档位

**HRVP 面：HR Vice President** 不是所有候选人都会有。一般出现在高潜人才、特殊人才计划、较高职级或需要特殊审批的候选人。通常会问：
- 候选人的长期潜力和上限
- 为什么值得给特殊 package / 人才计划
- 动机是否可信，是否真想来
- 职业目标和公司是否一致
- 综合素质、成熟度、价值观
- 最终 offer 的风险，例如是否容易被其他公司截胡


> [!NOTE] 需要体现出的特质
> 1. 研究积累和深度 -> 体现多年深耕某个领域
> 2. 广度（有算法、框架、系统、算子视角贯通）-> 体现对 infra 的整体 scope 理解

## 具体问题准备

### 科研和工业界 gap 问题

##### Q：之前没有实习，你觉得和有实习经历的同学相比，优势和劣势在哪里？

我之前确实没有正式的业界实习经历，这是我和有实习经历的同学相比最明显的短板。

**缺点：**
1. 我还没有在真正的大规模生产系统中经历过完整的需求评审、代码 Review、灰度发布、线上监控和故障处理
2. 缺少在明确的业务 Deadline、资源限制和稳定性要求下做技术取舍的经验
3. 业务系统还要同时考虑可维护性、兼容性、交付周期和线上风险

**优势：**
1. *科研领域不局限。* 实习的同学可能会专注于自己这个岗位的方向和工作内容，如果涉及其他技术的话会有专门懂这个方向的同学进行合作。但我的科研经历是很自由的，我的导师对我的选题自由度很高，所以之前我上层的压缩算法到底层的高性能算子都有做过，这在公司里可能是两波不一样的团队分别负责的事情。遇到性能或精度问题时，我会继续从不同的层次，比如模型、框架、算子和硬件层定位，而不是只停留在自己擅长的模块里。这样就形成了我现在上层算法和底层视角兼备的交叉的知识储备。
2. *定义问题的能力。* 科研面对的通常不是一个已经定义清楚、有成熟方案的问题。很多时候需要自己判断什么问题值得做、为什么现有方法不好，以及怎样把一个比较模糊的想法变成可以验证、可以复现的方案。我认为这种独立拆解问题，是我的一个优势。
3. *科研培养了我的独立性。* 大部分时间都是自己在独立地进行观察分析、算法设计、代码实现、性能分析、Kernel 优化、Benchmark 和论文。这个过程让我形成了独立发现问题、解决问题、完善思路、不断迭代优化的能力。
4. *自我驱动力。* 前段时间菲尔兹奖得主王虹接受采访的时候说过，如果在一个团队中，只要有一个人还在努力推进，他的动力就会感染其他人。在公司中，会有很多优秀的同事互相督促，还有绩效奖金等外部利益，会促使人不断努力。但在做科研的时候，完全是自己自我驱动地去争取。争取更好的效果、争取更厉害的合作者、争取更多的关注度和领域内的认可等。没有人强迫我这样做，完全是自己给自己设置目标。

**其他：**
1. *团队合作方面*，我虽然没有正式实习，但长期和不同学校、不同研究方向的合作者共同推进项目，也经历过很多意见不一致的情况。我知道科研协作和企业协作并不完全相同，但至少我已经形成了比较明确的合作习惯：尽早对齐目标和接口，明确负责人和时间点，遇到风险和难题要及时披露给合作者。

所以我的判断是，我的短板主要是对生产环境和企业工作流程不够熟悉，这是比较具体、也可以通过入职后的项目迅速补齐的；我的优势则是技术深度、跨层分析能力、独立推进能力，以及对复杂问题持续负责的习惯。

入职之后，我会优先熟悉团队的代码库、开发流程、性能指标和线上约束，先完成一个边界清晰、可衡量的小任务，再逐渐承担更大的模块，而不是把科研中的工作方式直接照搬到业务团队。

### 未来方向类问题

##### Q：你觉得 Infra 这个方向未来还能做哪些？发展空间怎么样？

我认为 Infra 的发展空间依然很大，但它的定位正在发生根本性变化：从相对静态的模型执行系统，逐步演变为动态、异构、面向任务的智能系统基础设施。

1. 系统会从追求规整走向支持动态。
	- 当前的推理框架偏好规整、可预测的执行形态，因为规整更容易转化为高利用率，但这只是算力与硬件约束下的阶段性最优，并非未来的必然形态。随着 Flash Attention、MoE 稀疏执行等技术的成熟，模型架构本身会变得更加动态，Infra 需要像操作系统管理进程一样，对请求进行创建、暂停、恢复、调度、迁移与资源隔离，实现更细粒度的任务管理。
	- 整个过程会变得明显更动态：不同样本的计算量不同，Rollout 的长度不同，MoE 里不同专家的负载不同，甚至数据生成与参数更新都不再严格同步。相应地，异步 RL 的支撑、MoE 通信与计算的流水线重叠、长上下文训练、容错恢复，以及动态并行策略与资源调度，都会是持续演进的方向。

2. 优化目标会从确定性走向决策性。
	- 传统系统的优化目标可以用明确规则评判，而 AI 推理在资源消耗与输出质量两端都存在不确定性：一个请求消耗多少计算、回复质量如何，都只能估计。因此未来的 AI 系统本质上是一个决策系统，需要结合请求复杂度、模型能力与成本进行权衡，而不是简单的确定性调度。

3. 训练与推理正在趋于一致。
	- 有损压缩等下游技术正向训练阶段迁移，例如量化感知训练使低比特成为模型的原生能力，从而获得更好的训推一致性。
	- 未来的模型会更稀疏、更多模态、上下文更长，训练也会越来越多地引入强化学习和在线数据闭环。
	- 异步 RL 的支撑、MoE 通信与计算的流水线重叠、长上下文训练、容错恢复，以及动态并行策略与资源调度，都会是在训练的时候就需要考虑的 infra 问题。


4. 以多模型协作为核心的 Agent 会带来新一层的 Infra。*从围绕 request 做优化 -> 围绕一整个 workflow*
	 - *复杂调度* 对调度器有一层新的要求。比如可能有 agent 并发、agent 调度、模型调度、环境调度等。
	- *长程长时间* 传统的推理请求通常在几十秒内结束，而 Agent 任务可能持续几分钟甚至几个小时，过程中包含状态保存、失败重试、环境隔离、工具调用和多模型协作。
	- *环境维持* 要求底层基础设施支持长生命周期任务、可恢复执行、Trace 与 Replay、权限控制、沙箱隔离和成本预算，并对动态任务图调度、异构模型路由与长轨迹状态管理提出了新的要求。这部分本质上已经是分布式系统、云计算与模型推理的结合。

5. 软硬件协同设计会越来越重要，根本原因在于系统会变得更加异构。
	- 训练和推理会使用不同的硬件，不同 Worker 承担的任务不同、对应的计算单元也不同；推理侧为了降低成本，也会越来越多地使用 NPU 这类专用芯片，而不是统一用 GPU。
	- 在这种局面下，模型结构不太可能完全确定之后再交给 Infra 团队被动适配。量化格式、稀疏模式、Attention 结构、MoE 路由方式与硬件计算单元之间会相互影响。Infra 团队需要更早地参与模型设计，判断某种模型结构在现有或下一代硬件上是否真的能带来收益。

因此，评价一个 Infra 方案不能只看单个 Kernel 快了多少，而要看整体吞吐、尾延迟、资源利用率与成本之间的协同。这个方向的门槛会越来越高，高价值的 Infra 工程师往往需要同时理解模型算法、框架、分布式系统、编译器、算子和硬件；但反过来说，它不是一个很快就能做完的局部优化问题，而是会随着模型形态与硬件形态持续演进，这也是它吸引我的地方。

### 认知广度问题

##### Q：你觉得中美两国在 AI 上的差距在哪里？短时间内能赶上吗？

【AI：100%】

我认为这个问题要*区分模型能力、算力供给、基础研究、工程生态和商业产品*几个维度。

单看公开模型的能力差距，中美之间已经非常接近。Stanford 2026 AI Index 的统计认为，中美头部模型的性能差距已经基本消失，双方模型从 2025 年开始多次交替领先，截至 2026 年 3 月，统计中的美国头部模型领先幅度约为 2.7%。因此，继续认为国内模型在能力上整体落后一代，我觉得并不准确。

但是，模型 Benchmark 接近不代表整个 AI 体系已经完全对等。美国目前仍然在先进芯片、算力供给、全球云计算平台、基础软件生态、前沿人才密度和全球开发者影响力方面具有结构性优势。美国头部实验室也更容易进行高成本、高风险、长周期的前沿探索。

国内的优势主要体现在工程效率、成本控制、开放模型生态、快速迭代和大规模应用场景。尤其在硬件资源受到限制的情况下，国内公司会更重视 MoE、低比特训练与推理、稀疏计算、蒸馏和系统优化，以更低的成本实现接近前沿的能力。近期中国开放权重模型在全球开发者中的影响力明显提升，也说明成本和开放生态本身可以形成竞争优势。

因此，能否在短时间内赶上，需要分维度讨论。在模型能力、成本效率和开放模型生态上，双方已经处在交替领先的状态，国内完全可能在某些模型和任务上领先。但在先进芯片、算力基础设施、全球平台生态和部分原创研究能力上，不太可能在一两年内整体补齐。这些是需要长期投入的结构性问题，而不是再训练一代模型就能解决的问题。


##### Q：国内不同公司的模型迭代方式和发展路径有什么区别？

【每个公司的技术路径、生存方式不同，没有绝对优劣，要根据面的公司和岗位调整答案。】

对于国内不同公司的发展路径，要根据公司的资源和商业模式来分析。

- *DeepSeek 更接近==研究==和算法效率驱动的路径*，强调前沿能力、训练推理效率和开放模型，通过技术突破建立影响力。其公开的 V4 路线仍然强调大规模 MoE、长上下文、Agent 能力和成本效率。

- *阿里 Qwen 更接近“基础模型加开源生态加==云平台==”的路径*。它不仅需要追求旗舰模型能力，还需要覆盖不同参数规模、不同模态和不同开发场景，通过开放模型、开发工具和云服务建立开发者生态。因此，其模型系列通常会更加完整，也更强调通用性、可部署性和企业服务能力。

- *字节 Seed 更接近产品和大规模==应用驱动==的路径。* 字节拥有丰富的==内容、推荐、广告和创作场景==，因此模型能力会和具体产品快速形成反馈闭环，在多模态生成、视频、Agent 和用户产品方面推进得比较积极。同时，它有能力把模型、云服务和消费级产品同时推进。

- *腾讯和百度更适合概括为==既有业务场景==和全栈能力驱动。* 腾讯可以结合社交、游戏、内容、企业服务和云业务，百度则可以结合搜索、知识、智能云和自动驾驶。它们不一定只追求一个统一模型在公开榜单上的排名，还会考虑模型如何进入原有业务、如何控制部署成本以及如何形成稳定收入。腾讯近期的 Hy3 路线强调 Agent、开源和产品集成，百度 ERNIE 5.1 则同时强调 Agent 能力和训练成本效率。

- *Moonshot、智谱等创业公司则需要保持更强的==聚焦==。* 以 Moonshot 为例，其公开路线集中在长上下文、编程、知识工作和 Agent 产品，模型和用户产品之间的迭代链路比较直接。相对于大型平台公司，创业公司需要同时解决技术突破、算力投入、用户增长和商业化问题，因此更需要在少数方向形成明显差异。

整体来看，国内公司的模型迭代方式大致可以分成三类。

- 第一类是研究驱动，先追求模型能力或者算法效率上的突破，再将能力扩展到产品。

- 第二类是产品驱动，根据用户数据、业务需求和产品反馈来定义模型下一阶段需要提升的能力。

- 第三类是平台和生态驱动，通过模型家族、开源社区、云服务和开发工具建立长期生态。

这三条路径没有绝对优劣。最终还是要看模型、Infra、产品和商业模式之间能否形成稳定闭环。对我个人而言，我更关注的是团队在算法和 infra 协同的深度，以及技术路径选择、结果能否真正进入模型迭代和线上系统。

### 团队协作类问题

##### Q：入职之后，你希望几个月内带多少人的团队，完成多大的任务？

*在 HR 面可能不要过多强调自己想进入决策领导层，还是要从基层做起，如果详细问了这个的话可以简单提一下，但别透露太多野心。*

我对前几个月的规划会分成三个阶段。

1. 入职前一到三个月，我希望先作为一个可靠的团队成员：
	- 熟悉团队的系统架构、开发流程、对指标的拆解方式、历史技术决策
	- 这个阶段的目标是建立可信度，证明我能够快速进入现有系统，并且交付符合团队标准的代码和结果

2. 三到六个月，我希望能够独立负责一个中等规模的工作流
	- 协调两到四名相关同学共同完成
	- 承担技术负责人的角色，不一定是带领团队，只是负责这一项工作流的问题拆解、确定接口、推进进度、识别风险和对最终结果负责
	- 任务规模上，我认为比较合理的是*一个季度左右*能够完成闭环的核心模块。例如围绕一个模型或推理场景，从性能分析开始，完成模型结构适配、框架实现、Kernel 优化、Benchmark 和部署验证，最终在精度和稳定性不退化的前提下，实现明确的吞吐提升或者两位数百分比的单位请求成本下降

3. 六到十二个月，如果前面的交付比较顺利，我希望能够成为*某一个细分方向的稳定技术负责人*，例如低比特推理、MoE 执行、KV Cache 系统或者高性能算子，能够对这个方向的技术路线和项目结果负责。

4. 更长期来看，我希望先沿着技术专家和技术负责人的路线发展。两到三年内，如果业务需要、个人能力也得到团队认可，我希望能够负责一个五到八人的小团队或者跨团队项目。我不会把人数本身当作职业目标。对我来说，更重要的是负责的问题是否足够关键，以及团队能否持续、稳定地交付结果。

5. 在这个基础上，我希望不只是被动承接已经定义好的优化任务，而是*能够逐渐参与到更前期的技术讨论中*。例如，在下一代模型设计阶段，我希望能够*提供自己的技术判断*，帮助团队更早识别哪些方向值得投入，哪些方案可能在模型指标上有效。
	- 这几年我一直在培养自己对未来方向的预判能力（这里可以举几个例子，就是早于知名大厂的一些技术探索、方向选择）
	- 我不会认为自己的预判一定正确，技术方向判断本身就有很强的不确定性，我们只能根据当前的认知去猜测未来。但是历史发展的规律是有很强的借鉴意义的，看谁有更厉害的类比迁移的能力，发掘当下和某一段历史的内在关联（这里可以举一些自己想的内在关联例子）
	- 提出观点、给出实验依据、设计可靠的低成本实验验证方案
	- 能够影响团队的决策：在选择什么问题、为什么现在做、采取什么技术路径，这些问题上能够给出可验证的实验证据（不一定要讲说服团队其他人，容易显得你预设自己的判断高于现有团队）
	- 比如未来团队发布下一代旗舰模型时，其中某个关键组件，是我在早期提出并推动验证的，并且最终证明它提升了模型能力或系统效率。我觉得这比单纯带多少人的团队，更能代表我希望达到的职业目标。

##### Q：你入职以后最希望做什么？

【不要主动讲自己想带团队。】

1. 尽快熟悉团队现有的技术栈，熟悉团队的系统架构、开发流程，对指标的理解对任务的拆解和合作的方式，还有历史技术决策。然后找到一个自己能够长期负责的一个子方向。

2. 如果让我现在选择，我比较希望做推理引擎算法和 Serving 交界的 codesign。因为我认为未来的 Infra 的效率的提升不是单点的优化，*所以希望能够参与整体推理架构的设计和端到端技术路线的讨论。*

### 个人倾向问题

##### Q：你最大的优势是什么？

- *核心标签* 跨模型算法、Kernel 和推理系统的 co-design 能力
- 做局部最优是很容易的，但在实际业务问题上去做推理 Infra 的实际优化，从瓶颈的判断到方案的设计，想要最终降低线上的成本，其实需要跨层的分析和视角。


##### Q：你为什么更想做推理，而不是训练？

1. *能力和研究积累都是推理相关* 包括推理的性能优化、成本控制，以及面向不同模型和不同任务做适配。如果要做训练的话，积累比较少，优势也发挥不出来。
2.  *实际业务价值* 推理能够节省每 token 的成本，比训练更直接带来收益。推理是长期的、持续的成本的消耗，所以推理的业务价值会比训练更多。现在的行业也已经到了这个阶段，大家都在往更低的落地部署成本在努力，打价格战。推理效率直接决定了在价格战上的优势，产品能不能规模化，以及盈利率。所以做推理是当前最实际、最能产生直接收益的地方。


##### Q：你为什么想做基模，而不是偏下游产品？

【一般不会问，上下游鄙视链很清晰】

这个问题可以从两个层面来看：一是工作内容本身，二是对长期积累的价值。

先说工作内容。偏下游的产品工作很锻炼人，它要求对用户需求、业务指标和场景细节足够敏感，反馈链路也直接。但对我来说，我更希望把主要精力放在决定行业上限的那一层：*即模型能力本身，以及支撑它的整个系统*。下游产品的大量优化空间，其实受制于模型的能力边界和底层系统效率；产品层能做的，很多时候是在给定模型之上做适配和组合。而基模这一层的工作是直接推动模型和系统往前走，这是更本质、也更难被替代的环节。

第二个层面和我自己的积累有关。我的工作横跨算法和系统两端，从模型压缩、量化这类算法工作，到引擎、算子、内核这些底层优化都做过，也一直关注训推一致性、软硬件协同和动态执行系统这些方向。做这些方向有个前提：模型结构、训练方式、执行系统和硬件是绑定在一起演进的，而*这几件事只有基模公司会放在一起考虑*。算法与 Infra 协同到什么程度，直接决定了模型能做到什么程度。如果去做偏下游的产品，我的积累更多是被使用，而不是被放大。

从长期积累来看，模型形态和硬件形态都还在快速演进，*基模这一层的工作会持续沉淀可迁移的技术深度，而不是绑定在某个具体的业务形态上*，这也是我判断自己更适合基模方向的原因。当然，我并不是在否定下游产品的价值，产品化能力同样重要；只是从我已有的技术积累和兴趣出发，基模是我更想投入精力的方向。

### 京东云


##### Q：为什么选择京东云，而不是一个做基础模型的公司？

【背景：京东只做别家开源模型的推理infra，不太会自己训模型，也不需要做训练的 Infra】

1. *基模是固定的形式* 基模围绕一个模型，经常会围绕一个固定的模型或者架构去做优化。
2. *实际业务场景* 但我想接触更实际的业务场景，高并发在线推理、大批量离线任务，面对更动态的问题、不同模型、不同请求、不同资源或者并发模式。
3. *挑战更大，机会更多* 有机会用到各种各样优化技术，包括 PD 分离、异构调度、分布式 KV Cache 存储等等，在各种现实约束下，把一个系统整体做好，挑战要比基础模型的推理做到极致难度更大，也贴近更真正的实际问题。
4. *用户体量* 这种做端到端全栈优化的机会其实很难得。如果用户量、请求量、流量比较小的话，如果没有足够的用户体量的话，问题规模就比较小，做优化的空间也比较少。只有当用户体量和流量峰值比较高的时候，一些 kernel 级或者 engine 里的调度问题才会真正暴露出来，才有优化的空间和动机。
	- 京东恰好是这种体量的公司。（2025 年的年度活跃用户数已经超过 7 亿，全年收入破 1.3 万亿）每天都有海量、真实、混合的业务流量在跑。云上要同时调度超过 1000 万个计算核心、200 多万个容器实例。尤其是 618、双十一，峰值流量是日常的十几二十倍。这个峰值流量是很多纯做基础模型的公司很难碰到的。


##### Q：来京东云想做什么？

- 希望做端到端的大模型推理 Infra
- *我的优势* 是能够理解模型结构对系统行为的影响，也能深入到量化、Attention、MoE 和 Kernel 这一层，同时从 Engine 和 Serving 层考虑实际的效率收益和成本平衡。
- *长期* 我比较希望负责一个推理 Infra 子方向，真正把算法和系统 co-design 的优化转化为线上 latency、throughput 和 cost 的改善。
- *价值观* 因为我认为未来的 Infra 的效率的提升不是单点的优化，*所以希望能够参与整体推理架构的设计和端到端技术路线的讨论。*


##### Q：开源已经有 vLLM 和 SGLang，为什么京东还需要自己做 Infra？

1. 云厂商没有必要重新实现所有的 feature，如果当前开源的框架已经支持了比较好的一些特性，直接沿用现有的即可，无需自己维护，减少维护更新成本。
2. 但真正困难、也真正有价值的部分，是*开源框架覆盖不到的真实业务*
	- vLLM、SGLang 这类开源项目追求的是尽快支持新模型、集成新技术，不会专门考虑某家公司的用户体量、流量峰值和具体硬件构成。
	- 而现实约束，有限的算力、特定的业务需求、如何把现有资源的价值尽量发挥出来，恰恰需要针对性的适配，这也是云服务厂商在开源框架和开源模型之上继续投入优化的原因。

##### Q：京东云做推理 Infra 最大的机会在哪里？

1. *模型多->创新空间大*。不只是服务单一的自研模型，需要面向不同模型、不同业务和不同硬件提供优秀的推理能力。模型的多样性、算力资源的多样性、硬件多样性，给推理引擎和框架带来了很多优化和创新的空间。有机会用到各种各样优化技术。
2. *业务体量大、有足够的真实场景和优化动机*。根据 workload 自动找到接近最优的部署和执行方案。【参考上面的 [[HR 面问题准备#Q：为什么京东云，而不是一个做基础模型的公司？]] ->  *4. 用户体量*】


##### Q：京东云 AI 的业务有哪些？

1. 大模型 MaaS / 推理云平台。JoyBuilder 模型开发平台 2.0，大语言模型在线部署和调用，自定义模型部署，AI 算力节点池、异构计算资源管理，多种模型统一服务，API
2. 企业 Agent 平台。Agent 知识库 / RAG Workflow Plugin MCP Skill Agent 商店。企业级 infra 的调度。
3. 京东内部最大的实际 AI 业务：零售和供应链。AI 数字人 JoyStreamer 使用商家超过 5 万，2025 年双 11，AI 客服处理 超过 42 亿次咨询，京东内部系统已有 超过 5 万个 AI Agent，AI 已经被京东定义为深入“超级供应链”的基础能力。
4. 客服、数字人、营销 AIGC，是目前非常成熟的外部商业化业务。
