### Expert Parallel 通信与计算重叠

#### [Q1] 为什么 Expert Parallel 的通信开销很大？

一个 MoE 层的粗略耗时可以写成：

$$
T_{\text{MoE}} = T_{\text{router}} + T_{\text{permute}} + T_{\text{dispatch}} + T_{\text{expert}} + T_{\text{combine}} + T_{\text{unpermute}}
$$

串行执行时，通信完全暴露在关键路径上：

$$
T_{\text{serial}} = T_{\text{dispatch}} + T_{\text{expert}} + T_{\text{combine}}
$$

All-to-All 尤其容易成为瓶颈的原因：
- 通信量与 token 数、hidden size、Top-k 成正比。
- 每张 GPU 需要与多张其他 GPU 交换数据。
- token 路由不均匀，导致每个 peer 的消息大小不同。
- 跨节点时需要经过 InfiniBand 或 RoCE，远慢于节点内 NVLink。
- 小消息过多时，通信启动开销明显。
- All-to-All 会竞争 GPU copy engine、NVLink、PCIe 和网络带宽。
- 某个专家过载形成 straggler，所有 GPU 都需要等待最慢的 GPU。

> [!tip] MoE 系统优化的重点
> 不是只优化 GEMM，而是整体优化整条链路：
> **Routing → Packing → Communication → GEMM**

#### [Q2] Communication-Compute Overlap 的基本思想是什么？

核心思想是把 batch 中的 $N$ 个 token 分成 $C$ 个 chunk，对每个 chunk 独立执行 Dispatch → Expert Compute → Combine，让不同 chunk 的通信与计算流水重叠。

理想时间线：

```
Communication Stream:
Dispatch 0 | Dispatch 1 | Dispatch 2 | Combine 0 | Combine 1 | Combine 2

Compute Stream:
             Expert 0  | Expert 1  | Expert 2
```

稳定流水线后，同一时间可能并发三类任务：
- 前一个 chunk 执行返回通信（Combine $i-1$）
- 当前 chunk 执行专家计算（Expert $i$）
- 后一个 chunk 执行发送通信（Dispatch $i+1$）

时间复杂度从串行求和变为取最大值：

$$
T_{\text{serial}} = T_{\text{communication}} + T_{\text{computation}}
\quad\longrightarrow\quad
T_{\text{overlap}} \approx \max(T_{\text{communication}},\ T_{\text{computation}})
$$

> [!example] 数值示例
> 假设 Dispatch + Combine 通信共 4ms，Expert GEMM 为 6ms：
> - 串行：$4 + 6 = 10\text{ ms}$
> - 理想重叠：$\max(4, 6) = 6\text{ ms}$
>
> 实际因 pipeline bubble、同步和 kernel launch 开销，不会完全达到理论值。

#### [Q3] Pipeline 调度如何划分 chunk？chunk size 如何取舍？

最直接的方式是按 token 序列切分，每个 chunk 分别独立执行 routing、packing、All-to-All 和 expert GEMM：

```
Chunk 0: token    0 ~ 1023
Chunk 1: token 1024 ~ 2047
Chunk 2: token 2048 ~ 3071
Chunk 3: token 3072 ~ 4095
```

> [!warning] chunk size 的权衡
> **chunk 太大：** 每阶段耗时长，可重叠机会少，pipeline 粒度太粗。
>
> **chunk 太小：**
> - NCCL 调用次数增加，kernel launch 开销上升。
> - 小消息网络带宽利用率低。
> - Grouped GEMM 矩阵太小，Tensor Core 利用率下降。
>
> 因此 **chunk size 是重要的性能调优参数**，需要实际 benchmark 确定。

#### [Q4] Pipeline 调度如何用 CUDA Stream 和 Event 实现？

通常至少需要两个 stream：`communication_stream` 和 `compute_stream`；更复杂时分为 `dispatch_stream`、`compute_stream`、`combine_stream`。

依赖关系通过 CUDA Event 在必要位置建立：

```cpp
ncclAllToAll(..., dispatch_stream);

cudaEventRecord(dispatch_done, dispatch_stream);
cudaStreamWaitEvent(compute_stream, dispatch_done);

expert_gemm<<<..., compute_stream>>>(...);

cudaEventRecord(compute_done, compute_stream);
cudaStreamWaitEvent(combine_stream, compute_done);

ncclAllToAll(..., combine_stream);
```

> [!question] 上面每个函数分别是什么作用？
> 整体逻辑：三条 stream 各司其职，用 Event 传递依赖信号。
>
> ```
> dispatch_stream ──[AllToAll dispatch]──▶ 记录 dispatch_done
>                                               │
> compute_stream  ◀── 等待 dispatch_done ────────┘
>                 ──[expert_gemm]──▶ 记录 compute_done
>                                         │
> combine_stream  ◀── 等待 compute_done ──┘
>                 ──[AllToAll combine]──▶
> ```
>
> **`ncclAllToAll(..., dispatch_stream)`**：NCCL 集合通信，把各 GPU 的 token 按路由目标发送到对应 GPU。第二个参数将操作提交到 `dispatch_stream`，异步执行，CPU 立即返回。
>
> **`cudaEventRecord(dispatch_done, dispatch_stream)`**：在 `dispatch_stream` 上插入一个标记点。当 stream 执行到这里时，将 `dispatch_done` 这个 Event 标为"已完成"。Event 排队进 stream，会等前面的操作跑完才触发。
>
> **`cudaStreamWaitEvent(compute_stream, dispatch_done)`**：让 `compute_stream` 阻塞，直到 `dispatch_done` 触发才继续。这是 **GPU 侧的等待**，CPU 不阻塞，可以继续提交后续命令。保证 GEMM 不会在 dispatch 完成前读数据。
>
> **`expert_gemm<<<..., compute_stream>>>(...)`**：标准 CUDA kernel launch，三角括号指定 grid/block 配置和 stream。排队在 `compute_stream` 里，等 `dispatch_done` 触发后才真正执行。
>
> **`cudaEventRecord(compute_done, compute_stream)`**：同理，在 `compute_stream` 上标记"GEMM 已完成"的 Event。
>
> **`cudaStreamWaitEvent(combine_stream, compute_done)`**：让 `combine_stream` 等待 GEMM 完成后再启动 Combine 通信，保证读取的是 GEMM 写出的完整结果。
>
> **`ncclAllToAll(..., combine_stream)`**：把专家计算结果发回 token 原始所在的 GPU，完成 Combine 阶段。
>
> 为什么不用 `cudaStreamSynchronize`？它会阻塞 **CPU**，导致无法继续提交其他 chunk 的命令。Event 的依赖只在 GPU 侧按需等待，不同 stream 仅在交接点同步，其余时间并发执行，流水线才能形成。

> [!important] 关键原则
> 不是取消所有同步，而是把**全局同步改成局部依赖**：Chunk $i$ 的 GEMM 只依赖 Chunk $i$ 的 dispatch 完成，不应等待所有 chunk 的 dispatch 全部完成，否则流水线无法形成。

> [!question] "全局同步"和"局部依赖"代码上有什么区别？
> **全局同步：阻塞直到某条 stream 上所有操作都完成**
>
> ```cpp
> // 多 chunk 的 dispatch 全部提交
> for (int i = 0; i < C; i++) {
>     ncclAllToAll(chunk[i], ..., dispatch_stream);
> }
>
> // 全局同步：等待 dispatch_stream 上所有 C 个 AllToAll 都完成
> cudaStreamSynchronize(dispatch_stream);
>
> // 这之后才能开始所有 chunk 的 GEMM
> for (int i = 0; i < C; i++) {
>     expert_gemm<<<..., compute_stream>>>(chunk[i], ...);
> }
> ```
>
> 问题：Chunk 0 的 dispatch 可能早就完成了，但代码必须等 Chunk C-1 也完成才能开始任何 GEMM，前面所有完成的通信结果白白空等，流水线无法形成。
>
> ---
>
> **局部依赖：每个 chunk 只等自己的 dispatch 完成**
>
> ```cpp
> for (int i = 0; i < C; i++) {
>     // 提交 chunk i 的 dispatch
>     ncclAllToAll(chunk[i], ..., dispatch_stream);
>
>     // 只为 chunk i 插入一个 Event 标记
>     cudaEventRecord(dispatch_done[i], dispatch_stream);
>
>     // compute_stream 只等 chunk i 的 dispatch_done，不等其他 chunk
>     cudaStreamWaitEvent(compute_stream, dispatch_done[i]);
>
>     // 立即提交 chunk i 的 GEMM（排队等上面的 Event 触发即可）
>     expert_gemm<<<..., compute_stream>>>(chunk[i], ...);
> }
> ```
>
> Chunk 0 的 GEMM 在 Chunk 0 的 dispatch 完成后立即启动，与此同时 Chunk 1 的 dispatch 已经在 `dispatch_stream` 上并发执行，流水线得以形成。
>
> ---
>
> **核心区别对比**
>
> | | 全局同步 | 局部依赖 |
> | --- | --- | --- |
> | 阻塞对象 | CPU 线程或整条 stream | GPU 侧的跨 stream 信号 |
> | 等待范围 | 所有 chunk 的 dispatch 都完成 | 只等当前 chunk 自己的 dispatch |
> | CPU 是否阻塞 | 是（`cudaStreamSynchronize` 阻塞 CPU） | 否（CPU 继续提交后续命令） |
> | 流水线效果 | 通信与计算完全串行 | 不同 chunk 的通信与计算可以重叠 |
> | 典型 API | `cudaStreamSynchronize` / `cudaDeviceSynchronize` | `cudaEventRecord` + `cudaStreamWaitEvent` |

由于通信和计算同时进行，需要**双缓冲（Double Buffering）** 防止读写冲突：

```python
for i in range(num_chunks):
    recv_buffer = buffers[i % 2]
    launch_dispatch_async(chunk=i, output=recv_buffer, stream=comm_stream)
    wait_dispatch_done(i)
    launch_expert_gemm_async(input=recv_buffer, stream=compute_stream)
```

更完整的三阶段流水线通常需要三组 buffer，分别支持 dispatch 输入输出、expert 中间结果、combine 输入输出。

#### [Q5] Pipeline 的 Warmup、Steady State、Drain 各阶段有什么特点？

| 阶段 | 内容 | 特点 |
| --- | --- | --- |
| **Warmup** | `Dispatch 0` | 没有可计算的数据，通信无法隐藏，形成初始 bubble |
| **Steady State** | `Dispatch 2 \|\| Expert 1 \|\| Combine 0` | 三阶段并行，吞吐率最高 |
| **Drain** | `Expert C-1` + `Combine C-1` | 尾部通信也无法完全隐藏 |

若 chunk 数为 $C$，三阶段 pipeline 的粗略总时间为：

$$
T \approx T_D + T_E + T_C + (C-1)\max(T_D,\ T_E,\ T_C)
$$

其中 $T_D$、$T_E$、$T_C$ 分别为单个 chunk 的 dispatch、expert compute、combine 时间。

> [!tip]
> $C$ 越大，warmup 和 drain 占比越低，但 chunk 太小会降低通信与 GEMM 效率，因此 $C$ 不能无限增大。

#### [Q6] 两种常见 Pipeline 方案有什么区别？

**方案一：Dispatch 与 Expert Compute 重叠（2 阶段）**

```
Chunk 0 Dispatch
Chunk 0 Compute  ||  Chunk 1 Dispatch
Chunk 1 Compute  ||  Chunk 2 Dispatch
Chunk 2 Compute
```

只隐藏第一次 All-to-All（Dispatch），Combine 仍串行暴露在关键路径上。

**方案二：Dispatch、Compute、Combine 三阶段重叠**

```
时间段 0:  Dispatch 0
时间段 1:  Compute 0   ||  Dispatch 1
时间段 2:  Combine 0   ||  Compute 1  ||  Dispatch 2
时间段 3:  Combine 1   ||  Compute 2  ||  Dispatch 3
```

尝试同时隐藏两个方向的 All-to-All。

> [!warning] 三阶段方案的实际限制
> Dispatch 和 Combine 都占用同一套 NVLink 或网络资源，两者可能**相互竞争带宽**，理论上的三路并发不一定更快。
>
> 有些系统会避免 dispatch 和 combine 同时执行，采用有优先级的调度策略：
> - **优先保证关键路径上的 Combine**
> - **空闲网络带宽再执行后续 Dispatch**

#### [Q7] Expert Parallel 中的负载不均衡如何影响流水线？常见解决方案有哪些？

设专家 $e$ 接收的 token 数为 $N_e$，专家计算时间近似正比于 $N_e$。整个 MoE 阶段由最慢的专家决定：

$$
T_{\text{expert}} \approx \max_e\ T_e
$$

即使通信与计算已经重叠，热点专家仍会导致所有 GPU 等待：

```
Expert 0: 100 tokens
Expert 1: 110 tokens
Expert 2: 105 tokens
Expert 3: 500 tokens   ← straggler，其他 GPU 完成后只能空等
```

常见解决方案：

> [!note] 6.1 Auxiliary Load Balancing Loss
> 训练时约束专家接收 token 的分布更均衡，典型目标：
>
> $$
> N_e \approx \frac{Nk}{E}
> $$
>
> 负载均衡损失会干预 router 的自然选择，可能影响模型质量，需要在均衡程度和模型性能之间权衡。

> [!note] 6.2 Capacity Factor
> 为每个专家设置容量上限：
>
> $$
> C_{\text{expert}} = \left\lceil \frac{Nk}{E} \cdot \alpha \right\rceil
> $$
>
> 其中 $\alpha$ 为 capacity factor（如 1.1、1.2、1.25）。超出容量的 token 可以被丢弃、路由到备选专家、放入溢出 buffer，或由共享专家处理。**训练时 token dropping 比较常见，推理时通常不希望丢 token。**

> [!note] 6.3 Expert Replication
> 热点专家可以在多张 GPU 上复制，Router 或 runtime 将其 token 分配给不同副本。代价是占用额外显存、参数更新需要同步、调度逻辑更复杂。

> [!note] 6.4 Token-Level Dynamic Scheduling
> 根据当前专家 token 数、GPU 空闲状态、通信拥塞状态、GEMM 尺寸等，动态安排专家计算顺序，本质上是一个 runtime scheduling 问题。

#### [Q8] All-to-All 本身有哪些常见优化手段？

> [!note] 7.1 Hierarchical All-to-All
> 跨节点通信远慢于节点内通信。将 All-to-All 拆成三步：
>
> ```
> Intra-node gather
>       ↓
> Inter-node all-to-all
>       ↓
> Intra-node scatter
> ```
>
> 减少跨节点消息数量，提高网络利用率。

> [!note] 7.2 Topology-Aware Expert Placement
> 将通信频繁的专家或热点专家放在拓扑上更近的位置。本质上是一个图划分问题：
> - token 路由关系为边，专家为节点，通信量为边权，GPU / 节点为分区。
>
> 典型策略：优先让常被共同激活的专家位于同一 NVLink domain，将共享专家放在每个节点内部。

> [!note] 7.3 Fused Permutation and Communication
> 朴素实现需要多次独立步骤（Router → Sort → Pack buffer → All-to-All）。优化实现将多步骤融合：
>
> ```
> Router output
>   ↓
> Histogram + prefix sum
>   ↓
> 直接写入通信 send buffer
> ```
>
> 减少中间 buffer、显存读写、kernel launch 和 token gather/scatter 次数。

> [!note] 7.4 Low-Precision Communication
> 发送 token hidden states 时使用 FP8 或 INT8：
>
> | 精度 | 通信量 |
> | --- | --- |
> | BF16 | $2NHk$ bytes |
> | FP8 | $NHk$ bytes |
>
> 理论通信量减少一半，但需要考虑 quantization / dequantization 开销、scale 的存储与通信、精度损失，以及小消息场景下可能被固定启动开销抵消。

#### [Q9] 为什么简单地使用异步 NCCL 不代表实现了重叠？

即使代码写成两个独立 stream：

```python
ncclAllToAll(..., comm_stream)
expert_gemm<<<..., compute_stream>>>()
```

也不一定真正重叠，原因有四：

> [!warning] 8.1 数据依赖
> Expert GEMM 必须等待对应 token 通信完成。如果没有 chunking，整个 GEMM 仍需要等待完整 All-to-All 完成，两个 stream 在逻辑上串行。

> [!warning] 8.2 GPU 资源竞争
> NCCL 并非只使用 copy engine，可能启动 GPU SM kernel 执行通信。Expert GEMM 同样占用 SM。若 GEMM 已占满 SM，NCCL kernel 没有足够 SM 执行；反过来 NCCL 也会降低 GEMM 性能。实际时间变为：
>
> $$
> \max(T'_{\text{comm}},\ T'_{\text{compute}})
> $$
>
> 其中两者都因资源竞争而比单独运行时慢，而不是理想的 $\max(T_{\text{comm}},\ T_{\text{compute}})$。

> [!warning] 8.3 隐式同步
> 某些操作可能引入全局同步，破坏重叠：
> - 默认 stream 操作、`cudaDeviceSynchronize`、blocking collective
> - buffer 复用时的强制等待、动态内存分配
> - 统计 token 数时的 CPU-GPU 同步

> [!warning] 8.4 通信消息太小
> chunk 切得太细后，每次 NCCL 操作的 payload 太小，通信启动延迟占主导。时间线上看似重叠，但总体吞吐反而下降。

#### [Q2] 多卡环境下如何并行计算 MoE Expert？

最常见的方案是 **Expert Parallelism（EP，专家并行）**：将不同 Expert 放置在不同 GPU 上，每张 GPU 只保存并计算部分 Expert。

假设有 4 张 GPU 和 8 个 Expert，可以进行如下放置：

| GPU | 本地 Expert |
| --- | --- |
| GPU 0 | Expert 0、1 |
| GPU 1 | Expert 2、3 |
| GPU 2 | Expert 4、5 |
| GPU 3 | Expert 6、7 |

一个 MoE 层通常按照以下顺序执行：

1. **Router 在 MoE 层入口进行路由。**  
   每个 GPU 最初持有自己本地 batch 或 sequence shard 中的 token hidden states。Router 为每个 token 计算各 Expert 的分数，并选择 Top-$k$ Expert：

   $$
   p_t=\operatorname{softmax}(x_tW_r)
   $$

2. **根据目标 Expert 重排本地 token。**  
   系统按照"目标 GPU 和目标 Expert"对 token 分组，同时保存 token 的原始位置和路由权重。

3. **第一次 All-to-All：Dispatch。**  
   将 token hidden states 发送到持有目标 Expert 的 GPU。不同源 GPU 可以同时向不同目标 GPU 发送不同 token，因此通常使用 `All-to-All`，而不是普通 `All-Gather`。

4. **各 GPU 并行计算本地 Expert。**  
   每张 GPU 将收到的 token 按 Expert 再次分组，本地多个 Expert 可通过 grouped GEMM 等方式高效计算：

   $$
   y_{t,e}=\operatorname{Expert}_e(x_t)
   $$

5. **第二次 All-to-All：Combine。**  
   Expert 输出被发送回 token 原先所在的 GPU。系统恢复原始 token 顺序，并根据 Router 权重合并 Top-$k$ Expert 输出：

   $$
   y_t=\sum_{e\in\operatorname{TopK}(t)}p_{t,e}y_{t,e}
   $$

6. **继续执行后续 Transformer 层。**

因此，标准 Expert Parallelism 的核心通信模式是：

$$
\text{Router}
\rightarrow
\text{All-to-All Dispatch}
\rightarrow
\text{Expert Compute}
\rightarrow
\text{All-to-All Combine}
$$

这里第二次通信在功能上类似"gather 回结果"，但通常仍通过**逆向 All-to-All** 实现，而不是让所有 GPU 都得到全部 Expert 输出的 All-Gather。每个 GPU 最终只取回自己原来持有的 token 输出。

#### [Q3] 为什么使用 All-to-All，而不是 All-Gather？

- **All-Gather：** 每张 GPU 收集其他 GPU 的全部数据，会产生大量无用复制。
- **All-to-All：** 每张 GPU 只将某个 token 发送到真正持有其目标 Expert 的 GPU，并只取回属于自己的输出，更符合稀疏路由。

> [!question] All-to-All 是什么？不同 GPU 如何同时发送不同 token？
> All-to-All 是分布式系统中的一种集合通信操作。假设一个通信组中有 $P$ 张 GPU，每张 GPU 都把自己的发送缓冲区切成 $P$ 份，并将第 $j$ 份发送给 GPU $j$；同时，它也会接收来自所有 GPU、目标为自己的数据。
>
> 例如，4 张 GPU 上的 Router 已经确定 token 应前往的 Expert，并将 token 按目标 GPU 打包：
>
> | 源 GPU | 发往 GPU 0 | 发往 GPU 1 | 发往 GPU 2 | 发往 GPU 3 |
> | --- | --- | --- | --- | --- |
> | GPU 0 | $A_{00}$ | $A_{01}$ | $A_{02}$ | $A_{03}$ |
> | GPU 1 | $A_{10}$ | $A_{11}$ | $A_{12}$ | $A_{13}$ |
> | GPU 2 | $A_{20}$ | $A_{21}$ | $A_{22}$ | $A_{23}$ |
> | GPU 3 | $A_{30}$ | $A_{31}$ | $A_{32}$ | $A_{33}$ |
>
> All-to-All 完成后，GPU $j$ 会收到整列数据：
>
> $$
> \operatorname{recv}_j
> =
> [A_{0j},A_{1j},\ldots,A_{(P-1)j}]
> $$
>
> 实际执行流程通常为：
>
> 1. Router 产生每个 token 的目标 Expert、目标 GPU 和路由权重。
> 2. GPU 上的 permutation kernel 按目标 GPU 对 token hidden states 排序并写入连续发送缓冲区。
> 3. 交换每个目标需要接收多少 token 的元数据，以便确定可变长度消息的 offset。
> 4. 调用 NCCL、DeepEP、MPI 或 TPU collective 实现的 `all_to_all` / `all_to_all_single`，通过 NVLink、NVSwitch、PCIe 或 InfiniBand 传输数据。
> 5. 目标 GPU 收到 token 后，再按本地 Expert 排序并执行 grouped GEMM。
> 6. Expert 计算完成后，通过一次逆向 All-to-All 将输出发送回 token 的源 GPU，再恢复原始顺序。
>
> "同时发送"并不一定意味着每对 GPU 都有独立物理线路。通信库会根据硬件拓扑，将数据切成 chunk，使用多个通信 channel，并通过 ring、direct exchange、分层 All-to-All 等调度算法并发传输。GPU 可以通过 GPUDirect RDMA 在不经过 CPU 拷贝的情况下直接跨节点发送显存数据。
>
> 在代码层面，PyTorch 常使用：
>
> ```python
> torch.distributed.all_to_all_single(
>     output,
>     input,
>     output_split_sizes=recv_counts,
>     input_split_sizes=send_counts,
> )
> ```
>
> 其中 `send_counts[j]` 表示本 GPU 要发送给 GPU $j$ 的 token 数量。MoE 路由通常负载不完全均匀，因此需要支持不同 split 大小的可变长度 All-to-All。

#### [Q4] MoE 并行方案组合

不一定。常见方案包括：

1. **纯 Expert Parallelism：** 每个 Expert 完整放在一张 GPU 上，不同 GPU 计算不同 Expert。
2. **Expert Parallelism + Tensor Parallelism：** 不同 Expert 分布在不同 GPU 组中，但单个大型 Expert 的矩阵权重又切分到组内多张 GPU；Expert 内部还需要 All-Reduce 或 Reduce-Scatter 等 Tensor Parallel 通信。
3. **Expert Parallelism + Data Parallelism：** 将整组 Expert 复制多份，每个副本处理不同数据；训练时再同步副本梯度。
4. **Expert Parallelism + Pipeline Parallelism：** 不同 Transformer 层分布在不同流水线阶段，每个阶段内部再使用 Expert Parallelism。
5. **Expert 复制或动态放置：** 对热门 Expert 创建副本，或根据负载调整 Expert 到 GPU 的映射，以减少负载不均衡和跨节点通信。

实际大规模 MoE 通常组合 EP、TP、DP、PP、Sequence/Context Parallelism，而不是只使用一种并行方式。

> [!example] 不同 MoE 并行方案有哪些代表性工作或框架？
> | 方案 | 代表性工作或框架 | 说明 |
> | --- | --- | --- |
> | 纯 Expert Parallelism | GShard、Switch Transformer、Fairseq-MoE、FastMoE | 将不同 Expert 分布到不同设备，并使用 All-to-All 路由 token。GShard 曾在 2048 个 TPU 上训练超过 600B 参数的 MoE 翻译模型。 |
> | EP + TP | DeepSpeed-TED、Megatron-Core MoE | DeepSpeed-TED 明确结合 Tensor、Expert 和 Data Parallelism；Megatron-Core 也支持 Expert Tensor Parallel，使单个 Expert 的大型矩阵由多张 GPU 共同计算。 |
> | EP + DP | DeepSpeed-MoE、DeepSpeed-TED | 多个数据并行副本分别处理不同 batch；每个副本内部再用 EP 分布 Expert。DeepSpeed 还可使用 ZeRO 对优化器状态和梯度进行分片。 |
> | EP + PP | DeepSpeed Pipeline + MoE、Megatron-Core MoE | 不同 Transformer 层被切分到流水线阶段，每个阶段内部的 MoE 层再使用 EP；常用于层数多、单阶段无法容纳整个模型的训练。 |
> | 自适应并行与流水 | Tutel | 根据运行时 token 路由负载，在不同并行和流水策略之间自适应选择。 |
> | Expert 复制或动态放置 | DeepSeek EPLB、FlexMoE 等 | 根据历史负载重新安排 Expert；对热门 Expert 建立冗余副本，使多个设备可以共同承接其 token。 |
>
> 这些类别并不互斥。例如一个实际训练任务可能同时使用 PP 切层、TP 切 Attention 和大型 Expert、EP 分布不同 Expert、DP 复制整个模型分片，并使用 Expert 复制缓解热点。

#### [Q5] MoE 多卡并行的主要瓶颈是什么？

1. **All-to-All 通信量大。** 每个 MoE 层通常需要一次 Dispatch 和一次 Combine。
2. **负载不均衡。** 若大量 token 被 Router 分配给少数 Expert，其他 GPU 会空闲，而整个层必须等待最慢的 GPU。
3. **跨节点通信较慢。** 通常尽量让频繁通信发生在具有 NVLink/NVSwitch 的节点内部，并减少经过较慢网络的 All-to-All。
4. **Expert 容量限制。** 系统可设置每个 Expert 接收 token 的最大容量；超出容量时可能丢弃、重新路由或使用更复杂的负载均衡策略。

常见优化包括负载均衡辅助损失、限制 Expert capacity、Grouped GEMM、通信与 Expert 计算重叠，以及拓扑感知的 Expert 放置。
