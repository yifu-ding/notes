#### [Q1] 高效 CoT 的核心挑战：为什么思维链越长代价越不线性？

截至 2026 年中，高效 CoT 可以概括为四个方向：

$$
\text{高效 CoT}
=
\underbrace{\text{减少需要思考的内容}}_{\text{压缩显式 CoT}}
+
\underbrace{\text{加速思考 token 的生成}}_{\text{speculative / parallel decode}}
+
\underbrace{\text{改变思考的表示形式}}_{\text{latent / diffusion / program}}
+
\underbrace{\text{按路径价值管理 KV Cache}}_{\text{CoT-aware scheduling}}
$$

---

**为什么长 CoT 的代价不是线性的？**

设输入前缀长度为 $P$，思维链长度为 $R$。Decode 阶段每步 attention 的读取总量近似为：

$$
\text{单步 attention cost} \approx O(P + R_{\text{current}})
$$

对全部 $R$ 步求和，**总 KV 读取量** 约为：

$$
O(PR + R^2)
$$

| 分量 | 含义 | 当 $R \gg P$ 时 |
| --- | --- | --- |
| $PR$ | 每步都要读完整 prefix | 线性于 $R$ |
| $R^2$ | 后半段的每步都要读前半段所有 CoT token | **二次增长** |

> [!important] Memory-bound 转折点
> 当 $R$ 足够大，decode 阶段从 **compute-bound**（矩阵乘法决定速度）转为 **memory-bound**（HBM 带宽决定速度）。此时增加计算并不能提速，而必须从** 减少需要读的 KV**入手。
>
> 对 ToT、自一致性、多分支验证，问题进一步升级为**树状 KV cache 的调度问题**：不同 branch 的 KV 不能共享尾部，但可以共享 trunk；低价值分支的 KV 驻留 GPU 是纯浪费。

---

**四类方法对应的成本削减点：**

| 方向 | 降低的量 | 代表方法 |
| --- | --- | --- |
| 压缩显式 CoT | $R$ 本身 | CoD、Sketch-of-Thought、F-CoT |
| 加速 token 生成 | 每步的 wall-clock 时间 | Speculative decoding、Medusa、SCoT |
| 改变表示形式 | $R$ 和 per-step cost 同时变化 | Latent CoT、Masked diffusion、PAL/PoT |
| KV Cache 调度 | 实际驻留 GPU 的 KV bytes | ThinKV、ArborKV、RadixAttention |

---

#### [Q2] 显式思维链压缩有哪些代表方法？

"显式 CoT 压缩"不是截断输出，而是**让模型只输出真正有决策价值的中间状态** 。

| 方法 | 核心思路 | token reduction | 是否需要微调 | 适用场景 |
| --- | --- | --- | --- | --- |
| **Chain-of-Thought** | 逐步自然语言推理 | 基线 | 否（few-shot）| 通用推理，必须掌握的起点 |
| **Chain-of-Draft（CoD）** | 只写关键变量、计算和决策，不写完整解释 | ~92%（保留约 7.6% token）| 否 | 算术、逻辑、短推理 |
| **Sketch-of-Thought（SoT）** | 根据任务动态选择 Conceptual Chaining / Chunked Symbolism / Expert Lexicons 等草图风格 | 平均约 76% | 是（路由器）| 多任务、跨语言 |
| **Focused CoT（F-CoT）** | 先将题目相关变量和关系结构化，再只在结构化表示上推理 | 约 2–3× | 否 | 数学应用题、冗余上下文 |
| **Draft-Thinking** | Curriculum 训练模型内化"draft-style reasoning"，再用 adaptive prompting 控制推理深度 | 约 82.6%（MATH500）| 是 | 长 CoT reasoning model |

---

**Chain-of-Draft（CoD）具体做法**

标准 CoT 要求模型写完整解释，例如：
> "John has 3 apples and buys 2 more, so he now has 3 + 2 = 5 apples."

CoD 只需要保留：
> "3 + 2 = 5"

**实现方式**：在 few-shot prompt 中把 demonstrations 替换为极简的 draft 格式，约束模型每步只输出关键计算、变量和决策，不写散文解释。论文报告在多个任务上用约 7.6% 的 token 量达到接近甚至更高的准确率。

> [!tip] 实用价值
> CoD 是**无需微调** 的效率基线，特别适合作为"已有 CoT 模型的 prompt 级提效"的第一步尝试。代价几乎为零，收益在短推理任务上很显著。

---

**Sketch-of-Thought（SoT）具体做法**

SoT 不固定使用一种压缩格式，而是通过一个**轻量路由器**（基于任务类型和语言）在三种草图风格之间选择：

1. **Conceptual Chaining**：以概念链接代替逐步论证（适合常识推理）。
2. **Chunked Symbolism**：以符号块代替散文计算（适合数学）。
3. **Expert Lexicons**：以领域术语缩写代替完整解释（适合专业问答）。

效果依赖路由器是否能为任务选对表达形式。跨语言场景下效果明显优于单一格式的 CoD。

---

**Focused CoT（F-CoT）具体做法**

F-CoT 的核心逻辑是**在推理前做信息提炼**，而非在推理中压缩：

1. **Extraction step**：从题目中抽取关键事实、变量和约束，形成紧凑结构化上下文。
2. **Reasoning step**：模型只基于这个结构化上下文推理，而不再扫描原始题目。

与 CoD 的区别：CoD 压缩的是 CoT 的输出，F-CoT 压缩的是**输入 attention 的有效范围**，减少无关 token 对 attention 的干扰。在 arithmetic word problems 上报告约 2–3× reasoning token reduction。

---

**Draft-Thinking 具体做法**

Draft-Thinking 是"**训练阶段直接塑造简洁思维分布**"的路线：

1. **Curriculum 训练**：从长 CoT 数据出发，逐步引入 draft-style 短推理 demonstration，让模型内化"我只需要写精华"的行为习惯，而非用 RL 惩罚输出长度（后者容易导致思维质量下降）。
2. **Adaptive prompting**：推理时根据题目难度估计动态指定推理深度提示，简单题少想，难题多想。

论文在 MATH500 上报告 reasoning budget 降低 82.6%，准确率损失约 2.6%。

> [!warning] 注意区分
> Draft-Thinking ≠ 简单的"输出长度惩罚 RL"。后者容易让模型跳过必要推理步骤，直接猜答案；而 Draft-Thinking 的训练目标是让模型学会**用更少的词表达同等深度的思维** 。

#### [Q3] 如何自适应分配 reasoning budget？

固定给所有样本相同的思维预算通常效率极差——简单题用了大量不必要的 token，难题反而可能预算不足。

**核心抽象**：将 reasoning budget 建模为样本特征的函数：

$$
B(x) = f\bigl(\text{difficulty}(x),\ \text{uncertainty}(x),\ \text{latency target}\bigr)
$$

其中 $B(x)$ 是样本 $x$ 分配的最大思维 token 预算。

---

**Token-Budget-Aware Reasoning**

在 prompt 中**动态注入 budget 约束**：系统估计当前题目难度（如通过 length predictor 或 reward model score），然后在 system prompt 或前缀中告诉模型"请在 $K$ token 内完成推理"，并用 RL 或 RLHF 训练模型学会遵守这一约束。

---

**DAST（Difficulty-Aware Step-level Training）**

不在 prompt 层面操控，而是在**训练时** 加入 difficulty signal：

1. 对每道训练题，用一个 difficulty predictor（可以是题目难度标注或解题成功率）估计难度 $d(x)$。
2. 训练模型在简单题（$d$ 低）时优先输出短 CoT，在难题（$d$ 高）时允许更长推理。
3. Budget preference optimization：用 preference data（短 CoT 与长 CoT 在简单题上的对比）训练模型的偏好，使其在简单任务上"自愿"缩短。

---

**UnCert-CoT（代码任务）**

对代码生成，不是所有题目都需要展开推理。UnCert-CoT 用**不确定性信号** 决定是否激活 CoT：

1. 先让模型直接生成代码（无 CoT）。
2. 计算生成结果的不确定性（如多次采样的多样性、top-1 vs top-2 log-prob 差、entropy）。
3. 若不确定性低 → 直接使用；若不确定性高 → 重新触发 structured CoT 生成，再做候选选择。

> [!note] 实践中的 early stopping 信号
> 可用于决定"是否继续思考"的信号：
> - **Entropy**：当前 token 分布的熵，熵低说明模型确定，可以停
> - **Top-1/Top-2 margin**：两个最高概率 token 之差，差大说明当前步置信高
> - **Verifier score**：外部 PRM/verifier 对当前 reasoning state 的评分
> - **Lightweight difficulty predictor**：在推理前预测是否需要长思维

---

#### [Q4] Speculative decoding 在 CoT 场景有哪些扩展？

**标准 Speculative Decoding 原理**

用**小 draft model** $M_q$ 连续生成 $\gamma$ 个候选 token，再由** 大 target model** $M_p$ 并行验证：

- 若 draft token $x_i$ 满足接受条件（$M_p$ 的概率足够高），则保留；
- 否则从 $M_p$ 的分布中采样一个修正 token，丢弃后续 draft。

关键性质：**输出分布完全等同于直接用 $M_p$ 采样**，不损失任何质量；加速来源是 $M_q$ 的 draft 往往大部分被接受，而 $M_p$ 的并行验证比串行生成快。

---

**Medusa 具体做法**

不引入额外 draft model，而是在同一模型上**增加多个并行 decoding heads**：

- 在原始 LM head 旁边增加 $K$ 个额外 head，分别预测后续第 $k$ 个 token（$k=1,\ldots,K$）。
- 生成时用 **tree attention** 对所有可能的 $K$ 步组合并行打分，选出置信度最高的接受序列。
- 训练：冻结原始模型，只训练这 $K$ 个新 head（轻量微调）。

Medusa-2 进一步联合训练原始模型和 heads（EAGLE 风格），接受率更高。

> [!tip] Medusa 与 Speculative Decoding 的区别
> - **Speculative Decoding**：需要额外一个 draft model，两个模型都要加载（内存 overhead 大），但对原始模型** 零修改**。
> - **Medusa**：只有一个模型，但需要微调添加 heads；适合固定 target 模型的服务场景。

---

**EAGLE 具体做法**

EAGLE 的关键创新：draft model 不直接预测 token，而是预测 target model 的**倒数第二层 hidden feature**：

$$
\hat{h}_{t+1} = F_{\text{draft}}(h_t, e_t)
$$

其中 $h_t$ 是 target model 第 $L-1$ 层的输出，$e_t$ 是当前 token 的 embedding。预测 feature 再喂给 target model 的最后一层得到 logits，用于验证。

优势：feature space 的分布比 token space 更平滑，draft model 更容易学，接受率比 token-level 直接 draft 高得多。在对话、代码和数学推理场景均报告明显加速。

---

**SCoT（Speculative Chain-of-Thought）具体做法**

SCoT 将 speculative decoding 从 **token 级** 提升到 **thought 级**：

1. 轻量 draft model 先生成一条完整的 thought-level draft（若干个推理步骤的草稿）。
2. Target model 对 draft 的各个 thought 节点做并行验证和修正，而非逐 token 接受。
3. 被拒绝的 thought 节点从 target model 重新生成，并触发后续 thought 的重新 draft。

论文在 DeepSeek-R1-Distill-Qwen-32B 上报告约 **48%–66% reasoning latency reduction** 。这与 token-level speculative decoding 正交，可以叠加使用。

---

**Skeleton-of-Thought（SoT）具体做法**

SoT 利用答案或计划中**子部分相互独立** 的结构：

1. **Skeleton 生成**：先让模型生成一个简洁的 skeleton（框架/骨架），列出所有需要展开的子部分（如多个论点、代码模块、推理分支）。
2. **并行展开**：对 skeleton 的各个节点同时发起独立的 API 请求或 token 生成，并行填充细节。
3. **合并**：将各部分合并为完整输出。

> [!warning] SoT 的适用限制
> SoT 只适合子任务**逻辑上相互独立** 的场景，例如说明类文章的多个论点、代码中独立的函数模块。**严格因果依赖的数学证明不适合 SoT**——后续推理步骤依赖前一步的结论，强行并行会破坏逻辑链。

#### [Q5] Masked / Diffusion LM 推理路线是什么？有哪些代表工作？

这条路线试图摆脱 token-by-token 的严格左到右生成，转向**迭代并行填充** 。

**基本形式**（Masked Diffusion Language Model）：

$$
x^{(0)} = [\texttt{MASK}]^n
\xrightarrow{\text{K 轮迭代}}
x^{(1)}
\rightarrow
\cdots
\rightarrow
x^{(K)}
$$

每一轮选择部分 masked position，网络预测其内容并 unmask；也可以 remask 低置信度位置进行修正。理论优势：**同一轮并行更新多个 token，允许双向依赖** 。

> [!warning] 并行生成 ≠ 一定更快
> Masked Diffusion LM 通常需要 **多轮 refinement**，且每轮使用 **bidirectional attention**（每个 token 都能看到全部 context）。在实际硬件上，** 迭代次数 × 双向 attention 的成本**可能抵消 token-level 并行的收益。这与 AR LLM 只做单向 causal attention 相比并不总是有优势。

| 工作 | 关键点 | 适用场景/评价 |
| --- | --- | --- |
| **理论分析论文** | 有限精度设定下 Masked DLM 可解决 CoT Transformer 能解决的问题 | 理论基础 |
| **DCoLT** | 将每个 reverse diffusion step 视为 latent thought action，用 outcome RL 优化 unmask 顺序 | 数学/代码 reasoning 的工程代表，最值得精读 |
| **Prophet** | 利用"答案在完全解码前已内部收敛"的观察，按 top-2 置信差决定提前停止 | 减少冗余 refinement step |
| **DiffCoT** | 保留 token 级 AR，在 reasoning-step 层引入 sliding-window denoising 允许回溯修正 | 偏 reasoning 鲁棒性，不是纯 latency 优化 |
| **LLaDA 系列** | Masked Diffusion LM 的主流实验载体 | 关注 unmask policy 和推理速度 |

---

**DCoLT 具体做法**

DCoLT 是 Masked Diffusion LM 路线中**工程化程度最高** 的代表：

1. 将 LLaDA 的每个 reverse diffusion step（从全 MASK 逐步 unmask 到完整输出）视为一系列 **latent thought action** 。
2. 训练一个 **policy**（即控制 unmask 顺序和位置的策略），用 **outcome-supervised RL**（以最终答案正确性为 reward）优化整条 diffusion reasoning trajectory。
3. 特别优化 token 的 **unmask 顺序**：先 unmask 高置信度的关键 token（如答案中的关键数字），再逐步填充细节。

论文在 GSM8K、MATH、MBPP、HumanEval 上报告了提升。

---

**Prophet 具体做法**

Prophet 的核心观察：在 Masked LLM 的迭代解码过程中，**正确答案区域（尤其是最终答案 token）通常在中途已经内部收敛**，后续的 refinement step 对其影响极小。

策略：每轮 refinement 后计算 top-1 和 top-2 candidate 的置信差。若差值超过阈值，则认为该位置已收敛，**提前 commit** 并从后续 refinement 中移除。这样可以提前完成部分 token 的解码，减少总迭代轮数。论文报告最多约 **3.4× decoding-step reduction** 。

#### [Q6] Latent CoT 和连续思维是什么路线？现实局限在哪？

这条路线的核心假设：**大量自然语言 CoT token 主要服务于可读性，而非计算必要性** 。于是模型不把每一步 thought 解码为文本，而是直接将 hidden state 作为下一步推理的输入：

$$
h_{t+1} = F_\theta(h_t, x)
$$

| 工作 | 核心思路 | 优势 | 局限 |
| --- | --- | --- | --- |
| **Coconut** | 将最后隐状态回灌为下一输入 embedding，跳过 text decoding | 一次前向可表达多条潜在分支 | 需改模型接口，不可插入现有 serving |
| **PLaT** | Latent state 负责规划，独立 decoder 仅按需将 thought 映射为文本 | 动态决定何时 verbalize | greedy accuracy 并非全面优于基线 |
| **CIRF** | 将显式 CoT 切成可复用 functional token（变量定义、方程建立、条件检查） | 保留一定可解释性 + token 效率 | 依赖 functional token 类型设计 |

---

**Coconut（Chain of Continuous Thought）具体做法**

标准 autoregressive CoT：每步 thought 被解码为文字 token（如 "so we have x = 3"），写入 context window，下一步 attention 读取。

Coconut 做法：
1. 模型生成一个思维步骤后，**不解码为 token，而是直接取最后 hidden state $h_L$** 。
2. $h_L$ 直接作为下一步的输入 embedding，进入下一次前向传播。
3. 重复 $K$ 次"连续思维"后，再解码最终答案。

**优势**：$h_L$ 处于高维连续空间，可以隐式地表示** 多条可能的后续推理分支的叠加**，而不必强迫在单一离散 token 上做决策。对某些逻辑规划任务体现出比显式 CoT 更好的准确率-效率折中。

> [!warning] Latent CoT 的现实问题
> 这类方法通常需要：
> - **重新训练或修改模型接口**（回灌 hidden state 需要改 forward pass）
> - **不兼容现有 reasoning model serving pipeline**（vLLM、SGLang 均基于 token-level 生成）
> - **调试困难**：latent thought 不可读，难以判断模型在"想什么"
>
> 因此目前更适合作为**下一代 reasoning architecture 的研究方向**，而非 DeepSeek-R1、Qwen 等现有 checkpoint 的直接部署优化。

#### [Q7] 数学推理中 CoT 的核心方法有哪些？

数学推理要区分两种本质不同的操作：

$$
\text{semantic planning（语义规划）} \quad \text{vs.} \quad \text{symbolic / numerical execution（符号/数值执行）}
$$

最高效的系统往往把两者**分开处理**：LLM 负责语义规划，外部工具负责确定性执行。

---

**Self-Consistency 具体做法**

对同一题采样 $N$ 条独立 CoT，然后对**答案空间做边缘化投票**（majority voting 或加权投票），而不是只取第一条推理链的结果。

$$
\hat{a} = \arg\max_{a} \sum_{i=1}^N \mathbf{1}[\text{answer}(c_i) = a]
$$

Self-Consistency 显著提升 GSM8K、SVAMP、AQuA 等数学基准的准确率（相比 greedy CoT），但成本约为 $N \times$ 单次 CoT。**它是准确率基线，不是效率基线**，适合离线 evaluation 或对准确率要求极高的场景。

---

**Least-to-Most Prompting 具体做法**

两阶段 prompting：
1. **分解（Decomposition）**：用 LLM 将复杂问题分解为一系列逐步简单的子问题序列 $q_1, q_2, \ldots, q_k$（每个子问题比原问题简单）。
2. **顺序解决**：依次解决 $q_1, q_2, \ldots$，每次把前面的解答作为上下文，再解决下一个子问题。

对**组合泛化** 任务尤其重要：这类任务的测试样本难度超出 few-shot demonstrations 的范围，但分解后每步难度仍在 demonstrations 覆盖范围内。

---

**STaR（Self-Taught Reasoner）具体做法**

一种 self-bootstrapping 的 reasoning 能力提升方法：

1. 对训练题目让模型生成 rationale（CoT 推理过程）。
2. **筛选**：只保留最终答案正确的 rationale（即"有效推理路径"）。
3. 用筛选出的 (题目, rationale, 答案) 三元组**微调模型** 。
4. 重复以上过程，模型的 reasoning 能力在迭代中提升。

这是 reasoning trace distillation 与自训练的重要起点，也是 RL-based reasoning training（如 RLHF on CoT、RLVR）的前身。

---

**PAL / PoT（Program-of-Thought）具体做法**

$$
\text{LLM 负责建模、分解、写程序}
\xrightarrow{}
\text{interpreter 负责确定性执行}
$$

- **PAL（Program-Aided Language Model）**：让 LLM 生成 Python 程序（而非用自然语言一步步计算），再把计算交给 Python runtime 执行得到答案。
- **PoT（Program-of-Thought）**：明确区分"language model 做 semantic reasoning/planning"和"interpreter 做 computation"，将最容易出错、最 token-heavy 的算术过程移出 LLM。

> [!important] PAL/PoT 的本质意义
> 对于数值计算任务，这往往比"压缩自然语言 CoT"更本质：
> $$
> \text{CoT} = \text{计划} + \text{计算}
> $$
> **PAL/PoT 保留"计划"部分，把"计算"外包给确定性执行器**，同时消除了 LLM 做算术时的固有误差。

---

**Let's Verify Step by Step（PRM）具体做法**

OpenAI 的这篇工作将**监督信号下放到每个 intermediate reasoning step**，而非只监督最终答案。

- **Outcome Reward Model（ORM）**：只看最终答案对不对，给整条 CoT 打分。训练简单，但无法指示哪个步骤出了问题。
- **Process Reward Model（PRM）**：对 CoT 中的** 每一步** $s_t$ 单独打分（正确/错误/中性），用 PRM800K 数据集训练。

PRM 对高效数学推理的价值不只是提升准确率，而是为 reasoning search 提供**每步的价值函数**：

$$
V(\text{partial reasoning prefix}) \rightarrow \text{当前路径是否值得继续}
$$

有了 PRM，系统才能做 best-of-N 搜索、MCTS 式 beam search、branch pruning 和基于 process reward 的 RL 训练。

---

#### [Q8] 代码生成中高效 CoT 的策略

代码生成与纯数学不同：**代码既是推理表达，也是可执行、可测试、可验证的对象** 。最有效的 CoT 往往遵循这一流程：

$$
\text{需求约束}
\rightarrow
\text{算法计划}
\rightarrow
\text{接口/不变量}
\rightarrow
\text{代码}
\rightarrow
\text{执行反馈}
$$

---

**Chain of Code（CoC）具体做法**

CoC 允许模型将推理过程切分为两类子任务：

1. **可执行部分**：直接交给 Python interpreter 运行（算术、排序、字符串操作等）。
2. **语义判断部分**（无法精确执行的子过程）：交给 **LMulator**（LLM 模拟 interpreter）输出结果。

这样混合了算法推理、语义判断和工具调用的代码型问题都可以在统一框架下处理。

---

**CodeCoT 具体做法**

将 CoT 与**测试样例生成 + 实际执行 + self-examination** 结合：

1. 先用 CoT 生成初始代码。
2. **生成测试样例** 并实际运行代码。
3. 若有 runtime error 或测试失败，将**执行反馈（错误信息）** 注入 context，触发模型自检和修正。
4. 迭代直到通过所有测试或达到最大轮数。

解决了"逻辑看起来正确但语法或运行时失败"的问题，是代码 CoT 中执行反馈驱动修正的经典做法。

> [!tip] 代码 CoT 的五条实践策略
> 1. **简单题直接 code generation**，不强制展开 CoT。
> 2. **不确定性高时才触发 structured plan**（参考 UnCert-CoT）。
> 3. **算术、枚举、测试、约束验证交给 executor**（PAL/CoC 思路）。
> 4. **对失败候选做局部 repair**，而不是整段 CoT 重生成（减少 token 浪费）。
> 5. **多候选只共享 problem 和 plan prefix**，后续 code branch 分页管理 KV。

---

#### [Q9] CoT、ToT、GoT 结构差异与分支搜索的真正瓶颈

| 范式 | 结构 | 准确率潜力 | 主要成本 |
| --- | --- | --- | --- |
| **CoT** | 单链 | 中等 | 长 decode；单路径错误不可逆 |
| **Self-Consistency** | 多条独立链 | 高 | 采样数倍增 |
| **ToT** | 树搜索、回溯 | 更高 | branch KV 爆炸 |
| **GoT** | 图结构、节点合并与反馈 | 高 | 调度复杂、状态依赖复杂 |
| **Algorithm of Thoughts** | 用算法化 prompt 替代显式大规模 tree search | 中高 | 依赖 prompt 与任务结构 |
| **Latent CoT** | 隐状态轨迹 | 潜力高 | 需要训练和架构改变 |

---

**Tree of Thoughts（ToT）具体做法**

ToT 将推理过程组织为一棵显式的搜索树，在 **thought 粒度**（而非 token 粒度）做决策：

1. 在每个 thought node，生成多个候选下一步 thought。
2. 用 LLM 或 value function 对每个候选打分（评估当前状态是否有希望）。
3. 根据分数进行 **BFS 或 DFS**，对低分路径剪枝，对高分路径优先扩展。
4. 允许**回溯**：若某条路径走入死角，可以回到父节点尝试另一个分支。

这是从线性 CoT 到显式 search 的经典转折点，在 Game of 24 等需要试错的任务上比 CoT 提升显著。

---

**Graph of Thoughts（GoT）具体做法**

GoT 在 ToT 的基础上进一步放开约束，将 thought 组织为**有向图**（允许非树结构）：

1. **节点合并（Aggregation）**：多条不同分支的中间结论可以** 合并为一个新节点**（如取两条推理链的交集答案）。
2. **反馈循环**：节点可以接收外部反馈（如代码执行结果、验证器输出）并更新状态。
3. **摘要节点**：可以对多个子推理生成摘要，减少 context 膨胀。

适合多分支**共享中间结果** 的任务（如对多个假设的共同前提做一次验证）。

---

**Algorithm of Thoughts（AoT）做法**

AoT 的核心思路：在 **prompt 中直接提供算法化搜索流程**（如 DFS 框架、回溯标记），让单次 LLM 调用模拟更广的思考空间，而非触发多次独立 API 请求。

目标：避免显式 tree search 的大 token 消耗和多请求 overhead，用更少的调用次数模拟搜索过程。

---

> [!important] 分支搜索的真正瓶颈
> 多路径 CoT（ToT/GoT/SC）的实际瓶颈不是"每条路径如何更快生成"，而是以下四个调度问题：
> $$
> \underbrace{\text{path value estimation}}_{\text{哪条路径值得继续？}}
> +
> \underbrace{\text{parallelism allocation}}_{\text{几条路径同时展开？}}
> +
> \underbrace{\text{KV residency}}_{\text{哪些 KV 留在 GPU？}}
> +
> \underbrace{\text{branch eviction / reactivation}}_{\text{低价值分支何时驱逐、何时恢复？}}
> $$

---

#### [Q10] CoT 场景下 KV Cache 的调度挑战：单路径与多路径

### 基础 serving 层

**PagedAttention / vLLM**：必须建立的系统基线。

- 将 KV cache 切成固定大小的 **logical block**（如每块 16 token），通过 logical → physical block mapping 分配物理内存。
- **Copy-on-write**：当多个请求 share 同一 prefix 时，物理 KV block 被共享，只在写入时复制。
- 减少碎片，支持不同请求或分支间的 prefix 复用。

**SGLang / RadixAttention**：

- 用 **radix tree** 管理共享前缀，可自然支持 structured program、agent、few-shot、多轮对话和分支推理中的 **prefix reuse** 。
- 当两个 ToT 分支的 trunk prefix 相同时，trunk 的 KV 只存储一份，两个分支共享物理 block，fork 时 copy-on-write。

**Hydragen**：

- 在 attention kernel 层面进一步优化 shared-prefix batch：将 **shared prefix attention** 与 **unique suffix attention 分开计算**，以更高效的矩阵乘法（batch matmul）减少对同一 prefix KV 的重复读取。
- 特别适合 self-consistency（多条链共享 system prompt 和题目前缀）和 AlphaCode 风格多候选采样。

---

### 单路径长 CoT 的 KV 压缩

对单条很长的 reasoning chain，简单的 attention-score-based eviction（如 H2O、SnapKV）在 CoT 场景效果有限，原因：

> [!warning] CoT KV 压缩的特殊难点
> ==低 attention score 的 token 不一定不重要==。某些早期定义的变量、假设、分支条件会在很后面的推理步骤中**重新被引用**（如"let $x = 3$"在第 50 步被再次用到）。纯 attention-score eviction 会错误淘汰这些"低频高价值"的 KV。

**ThinKV（ICLR 2026 Oral）具体做法**：

1. **Thought-type-aware 重要性估计**：按 thought 的类型（变量定义、中间计算、局部结论、最终答案前缀）分配不同的保留优先级，而非对所有 token 一视同仁。
2. **联合量化 + 逐步淘汰**：在 PagedAttention 框架上设计可复用被驱逐 slot 的 kernel，避免 compact cache 的额外内存 move。
3. **渐进式驱逐**：越近期的 reasoning step 越不驱逐（局部 reasoning flow 需要），越早期的已"固化"的中间结论可以逐步淘汰为低 bit 或摘要状态。

**合理的单路径 CoT cache policy**：

$$
\text{保留} = \underbrace{\text{recent local tokens}}_{\text{局部 reasoning flow}} + \underbrace{\text{critical variables/constraints}}_{\text{早期定义的关键量}} + \underbrace{\text{verified milestones}}_{\text{已确认正确的中间结论}} + \underbrace{\text{answer-relevant states}}_{\text{最终答案依赖的状态}}
$$

其余历史推理按低 bit、摘要状态或可恢复 token sequence 存储。

---

### 多路径 CoT（ToT/Self-Consistency）的分支 KV 调度

多路径 CoT 的 cache **不应** 按"每个分支一份完整 KV"处理，而应按 **prefix DAG** 管理：

$$
\text{shared prompt} \rightarrow \text{shared reasoning trunk} \rightarrow \text{branch-specific suffix}
$$

**SpecInfer**：通过 **token tree** 并行验证多个 speculative candidate，是树状并行 verification 的经典系统工作。每个候选路径共享 root（prompt + tree trunk），只有叶子节点（各个候选 token）的 KV 需要独立存储。

**ArborKV（2026 年）**：直接针对 ToT 的 KV 管理，核心观察：

- **近期 decode 主要依赖 active branch 及其 ancestors**，inactive subtree 短期复用概率低。
- 但 inactive subtree 的 KV 必须**可恢复**（支持回溯）。

因此设计 **tree-aware allocation + token-extractive eviction + lazy rehydration**：
- Active branch 及 ancestor trunk：驻留 GPU，BF16/FP8。
- 高价值 sibling（可能回溯到的兄弟节点）：GPU low-bit 或 CPU DRAM。
- 低概率 revisit subtree：仅保留 token sequence（可重新 prefill）或压缩 KV，存 CPU/SSD。
- 已验证失败的 branch：释放 KV，只保留摘要、分数和 parent pointer。

---

#### [Q11] 长 CoT 的 serving 系统设计：Prefill-Decode 分离与层级存储

长 CoT 场景的 serving 挑战与普通 QA 不同：

| 特征 | 普通 QA | 长 CoT |
| --- | --- | --- |
| Decode 长度 | 数十到数百 token | 数千到数万 token |
| 瓶颈 | Prefill TTFT 为主 | **Decode TPOT** 为主（memory-bound）|
| KV cache 大小 | 适中 | 极大（随 $R$ 线性增长）|
| 多路径需求 | 少 | ToT/SC 需要大量分支 KV 管理 |

---

**DistServe（Prefill-Decode 分离）**

将 **Prefill** 和 **Decode** 部署在** 不同 GPU resource pool**，分别独立优化：

- **Prefill GPU 池**：优化 TTFT（Time to First Token），批量化 prefill，高计算利用率。
- **Decode GPU 池**：优化 TPOT（Time Per Output Token），专注 memory-bandwidth 效率。

对长 CoT，decode 阶段远长于普通 QA（数千步 vs 数十步），更偏 memory-bound，**disaggregation 使两阶段可以独立扩缩容**，显著提升整体吞吐和 SLO 达成率。

KV cache 在 prefill 结束后需要从 prefill GPU **迁移** 到 decode GPU，这一传输成本是 DistServe 的主要工程挑战，由 CacheGen 解决。

---

**CacheGen（压缩 KV 传输）**

面向跨机器或远端 KV transfer 场景，将 KV cache 编码为**压缩 bitstream**：

- KV tensor 经过 token-wise 量化（如 FP8/INT4）后压缩为 bitstream。
- 传输时按**网络带宽自适应调整压缩率**：带宽充足时少压缩（快传快解）；带宽受限时激进压缩（慢传快用）。
- 对"prefill 产生 cache，decode 在另一组 GPU 继续长 CoT"的模式（DistServe 场景）尤其有用。

---

**Mooncake（集群级 KV cache 调度）**

Mooncake 把 **KV cache 视为集群级资源**，而非单机单请求的临时内存：

- 利用 **CPU DRAM、SSD 和 GPU HBM** 构建三层存储（从热到冷）。
- **KV-centric scheduler**：在接受新请求前，先查询是否有可复用的 KV cache（来自历史请求、prefix 共享、相似 prompt 等），最大化 KV reuse。
- 在 throughput（最大化 KV reuse 以减少 prefill 计算）和 SLO（保证 TTFT/TPOT）之间调度。

---

#### [Q12] 如何为 reasoning node 设计 KV cache 优先级？

在多路径搜索（ToT、GoT、Self-Consistency）场景中，需要动态决定哪些 node 的 KV cache 应该：
- 驻留 GPU（热层）
- 降 bit 或迁移 CPU（温层）
- 序列化到 SSD（冷层）
- 彻底释放（释放层）

**优先级公式**：

$$
\text{Priority}_i = \frac{p_i^{\text{reuse}} \cdot V_i^{\text{future}} \cdot C_i^{\text{verify}}}{M_i^{\text{KV}} + \lambda R_i^{\text{rehydrate}}}
$$

| 符号 | 含义 | 估计来源 |
| --- | --- | --- |
| $p_i^{\text{reuse}}$ | 节点 $i$ 短期内被继续展开或回溯的概率 | 搜索算法（BFS/DFS 深度、beam score） |
| $V_i^{\text{future}}$ | 对最终答案的潜在价值 | PRM、verifier、self-evaluation、path score |
| $C_i^{\text{verify}}$ | 保留该分支能**节省** 的未来验证成本 | 已验证步骤越多，$C$ 越高 |
| $M_i^{\text{KV}}$ | 节点当前占用的 KV memory（bytes） | 直接测量 |
| $R_i^{\text{rehydrate}}$ | 被驱逐后**重新构建** 的成本（重新 prefill 或远端加载） | 节点深度 × 单步 prefill 成本 |

---

**四层 KV 存储策略**：

| 层级 | 存储内容 | 建议位置 |
| --- | --- | --- |
| **热层** | active path、ancestor trunk、即将验证的 branch | GPU，BF16/FP8 |
| **温层** | 高价值 sibling、高概率回溯节点 | GPU low-bit 或 CPU DRAM |
| **冷层** | 低概率 revisit subtree | CPU/SSD，仅保留 token sequence 或压缩 KV |
| **释放层** | 已验证失败、低价值终止 branch | 释放 KV，仅保留摘要、分数和 parent pointer |

> [!note] 与 LRU 的对比
> 纯 **LRU（Least Recently Used）** 驱逐在 reasoning search 场景下会系统性地驱逐"很久没被 access 但价值极高"的 ancestor trunk（搜索树共享的早期推理前缀）。这是分支搜索场景中 LRU 失效的根本原因——** 访问频率 ≠ 价值**，需要结合 $V_i^{\text{future}}$ 和 $p_i^{\text{reuse}}$ 才能正确决策。
